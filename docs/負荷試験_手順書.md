# SP-PS 負荷試験 手順書

何人もの生徒が同時に使ったときに、**どこで重くなるか**（サーバーの Mac・Wi-Fi・Cloudflare）を切り分けるための手順です。
仕組みの説明と過去の測定結果は README §5.4「同時に使う人が多いとき」にあります。

---

## 0. はじめに決めておくこと

試験のたびに、次を **記録シート（§9）** に書いておきます。あとで原因を比べるときに必要です。

- サーバーの Mac の機種・CPU・メモリ、つないでいる回線（有線 / Wi-Fi・どのアクセスポイントか）
- サーバーの起動のしかた（**必ず `scripts/server.sh start`**。`python app.py` は開発用で、1つのプロセスしか使わないので負荷試験には使わない）
- 公開のしかた（Quick Tunnel `trycloudflare.com` / 名前付き Tunnel / 使わない）
- 人数・時間・口の動画を送るか

> **守ること**
> - **1人に1つの利用者 ID を使う。** 同じ ID の処理は記録が壊れないよう1つずつ順番に行うので、同じ ID を何人も使うと「1人分の速さ」を測ってしまい、50 秒待つと「混み合っています」になります。
> - **本番の参加者の ID（A01 など）で試験しない。** 練習記録に試験の結果が混ざります。試験用の `LT01`〜 を使います（§2）。
> - 試験中はサーバーの Mac で、ほかの重いアプリ（動画・ブラウザのたくさんのタブなど）を閉じる。電源につなぎ、ふたを開けておく。

## 1. 準備（サーバーの Mac で、最初の1回）

1. リポジトリを最新にして、仮想環境が使えることを確かめる。

   ```bash
   cd SP-PS-2026-
   git pull origin main
   source .venv/bin/activate
   pip install -r requirements.txt
   ```

2. 単語とお手本を登録済みの参加者を1人決める（例：`A01`）。試験用の参加者はこの人の単語とお手本をコピーして作ります。お手本の口の形（録画）がある単語が入っていると、口の解析の重さも含めて測れます。

---

## 2. 試験用の参加者を作る

```bash
python scripts/loadtest_accounts.py create --count 30 --from A01
```

- `LT01`〜`LT30` ができます（パスワードは `loadtest123`）。
- 人数を増やして試すときは、試す最大の人数分だけ作っておきます（例：`--count 80`）。
- 作った ID は `DATA_DIR/run/loadtest_accounts.json` に記録され、§8 の `delete` はその ID だけを消します。

---

## 3. サーバーを起動する

```bash
scripts/server.sh start      # 起動して、公開 URL と QR を表示する
scripts/server.sh status     # 動いているか・今の公開 URL を見る
```

- 既定はワーカー 2・スレッド 16 です。変えて比べるときは前に付けます：`WEB_CONCURRENCY=3 scripts/server.sh start`
- 起動直後は裏でライブラリの準備をしているので、**起動してから 30 秒ほど待ってから**試験を始めます。

試験中に、**別のターミナル**でサーバーのログを流しておきます。

```bash
tail -f .tmp/serve/gunicorn.log
```

あわせて **アクティビティモニタ**（CPU・メモリのタブ）を開き、CPU 使用率とメモリプレッシャーの色を見ておきます。

---

## 4. 試験 A：Mac の中だけで測る（Wi-Fi・Cloudflare を通さない）

**サーバーの Mac 自身**で次を実行します。Wi-Fi も Cloudflare も通らないので、**サーバーの力だけ**を測れます。

```bash
python scripts/loadtest.py --url http://127.0.0.1:5000 --users 10 --minutes 2 --json result_A_10.json
python scripts/loadtest.py --url http://127.0.0.1:5000 --users 20 --minutes 2 --json result_A_20.json
python scripts/loadtest.py --url http://127.0.0.1:5000 --users 30 --minutes 2 --json result_A_30.json
```

- 人数を少しずつ増やし、遅くなり始める人数を探します。1回ごとに 1 分ほど休ませてから次を始めます。
- 10 秒ごとに途中経過が出て、最後に要求の種類ごとの **成功・失敗・503 の回数** と **応答時間（中央値・90%・99%・最大）** の表が出ます。この表をそのまま記録シートに貼ります。
- 負荷をかける側も同じ Mac の CPU を使うので、結果は少し悪めに出ます。

主なオプション：

| オプション | 意味 | 既定 |
|-----------|------|------|
| `--users` | 同時に練習する人数（`LT01` から順に使う） | 10 |
| `--minutes` / `--practices` | 続ける時間（分）／1人あたりの練習回数 | 3 分 |
| `--think` | 操作と操作の間の待ち時間（秒）。実際の生徒に近づけるなら 5〜10、限界を見るなら 0 | 2 |
| `--ramp` | 全員がそろうまでの秒数（0 で全員が同時に始める） | 10 |
| `--no-video` | 口の動画を送らない（口の解析を除いた重さを見る） | 送る |
| `--json` | 各要求の時間を JSON に保存する | 保存しない |

---

## 5. 試験 B：公開 URL で測る（Wi-Fi と Cloudflare を通す）

**サーバーとは別の PC** を、実際に生徒が使う Wi-Fi につなぎ、`scripts/server.sh status` で出た公開 URL に対して実行します。
（この PC にもリポジトリを入れておきます。`loadtest.py` は Python の標準ライブラリだけで動きます。）

```bash
python scripts/loadtest.py --url https://xxxx.trycloudflare.com --users 10 --minutes 2 --json result_B_10.json
python scripts/loadtest.py --url https://xxxx.trycloudflare.com --users 20 --minutes 2 --json result_B_20.json
```

- **試験 A と同じ人数・同じオプション**で行い、結果を並べて比べます。
- Quick Tunnel（`trycloudflare.com`）は同時に処理できる要求が **200 件まで** です。大人数はここで詰まるので、試験 B は少なめの人数で行います。大人数を試すなら名前付き Tunnel を使います。
- Cloudflare は 100 秒で応答を打ち切ります（エラー 524）。

---

## 6. 試験 C：実際のスマホで試す（任意）

試験 A・B で問題が無いときの最後の確認です。

- 1台に1つの ID（`LT01`、`LT02`、…）を割り当てて配る。**同じ ID を2台以上で使わない。**
- 生徒が実際に使う Wi-Fi・場所で、「単語を選ぶ → 録音 → 結果を見る」を合図で同時に始める。
- 「どの端末で・何時何分に・どんな画面になったか（ずっと読み込み中 / 混み合っています / Cloudflare のエラー画面）」をメモする。

## 7. 結果の見方と原因の切り分け

### まず A と B を比べる

| 試験 A（Mac の中） | 試験 B（公開 URL） | 考えられる原因 |
|---|---|---|
| 速い | 速い | 問題なし（試験 C へ） |
| 速い | **遅い・失敗する** | **Wi-Fi か Cloudflare**。サーバーの Mac を有線にする、Wi-Fi のアクセスポイントを分ける、名前付き Tunnel にする、など |
| **遅い** | 遅い | **サーバー側**。下の「ログとアクティビティモニタ」で中身を見る |

### ログ（`.tmp/serve/gunicorn.log`）とアクティビティモニタ

| 見えたもの | 意味 | 次にやること |
|---|---|---|
| `[capacity] 解析の順番を ○秒待ちました` が増える、503 が出る | 採点の順番待ち（**CPU が足りない**） | 人数の上限の目安にする。CPU の多い Mac にする、`SP_PS_HEAVY_SLOTS` を調整して比べる |
| CPU が 100% に張り付く | 同上 | 同上 |
| メモリプレッシャーが黄色・赤、スワップが増える | **メモリ不足** | ワーカーを減らす（`WEB_CONCURRENCY=1`）か、メモリの多い Mac にする |
| `WORKER TIMEOUT`、ワーカーが何度も起動し直している | ワーカーが止まっている（メモリ不足など） | ログのその前後を記録シートに貼る |
| ログに要求がほとんど出ていない | 要求が **サーバーまで届いていない** | Wi-Fi・Cloudflare 側を疑う（試験 B の結果と合わせて見る） |
| 「混み合っています」が特定の人だけ | 同じ ID を複数の端末で使っている | §0 の「1人に1つの ID」を守る |

### 目安（README §5.4 の測定。開発用 PC の WSL2・CPU 8 個・サーバーと同じ PC から測定）

| 人数 | 採点の中央値 | 採点の 90% | 失敗 |
|-----:|-----:|-----:|----:|
| 10 | 0.31 秒 | 0.43 秒 | 0 |
| 40 | 0.51 秒 | 0.91 秒 | 0 |
| 80 | 2.44 秒 | 3.74 秒 | 0 |

機械が違うので数字はそのまま比べられませんが、サーバーの Mac の結果がこれより大きく悪いときは、Mac の性能か起動のしかたを見直します。

---

## 8. 後片付け

```bash
python scripts/loadtest_accounts.py delete   # 試験用の参加者を、練習の記録ごと消す
```

- 試験 C で配った ID のメモも回収します。
- サーバーを止めるときは `scripts/server.sh stop`。
- `result_*.json` と記録シートは、原因の比較のために残しておきます（参加者の個人情報は含みません）。
