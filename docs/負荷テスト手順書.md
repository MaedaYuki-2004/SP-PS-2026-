# 負荷テスト手順書（重くなる原因を切り分ける）

サーバーの Mac で、負荷テストを決まった手順でやり直し、「重くなって動かなくなる」原因を切り分けるための手順書です。
上から順に、コマンドをコピーしてターミナルに貼りつけて実行してください。**アプリのプログラムは変えません。**

- 対象：サーバーの Mac（リポジトリの場所 `~/Desktop/spps/SP-PS-2026`）
- 所要時間：約 1 時間（試験 A だけなら約 30 分）
- 2026-10-20 作成

> GitHub で開くと表や枠が見やすく表示されます（`docs/負荷テスト手順書.md`）。

## 1. この手順書でわかること

「重くなる」原因の候補は、次の 4 つです。

| | 候補 | どういうことか |
|---|---|---|
| ① | **サーバーの起動のしかた** | `python app.py` で起動すると、Flask の開発用サーバー（プロセス 1 つ）で動く。重い採点が同時に 1 つずつしか進まず、人数が増えるとすぐ詰まる。正しい起動（デスクトップの「SP-PS 起動」・`scripts/server.sh start`）では gunicorn（ワーカー 2・スレッド 16）で動き、同時に受け付けられる |
| ② | **Mac の力（CPU・メモリ）** | 採点の計算が CPU を使い切る。メモリが足りずスワップ（ディスクへの書き出し）が起きると、すべてが遅くなる |
| ③ | **ネットワーク（Wi-Fi）** | 練習のたびに、録音・口の動画・お手本の動画・結果の画面が行き来する。混んだ Wi-Fi では詰まる。Mac 自体が Wi-Fi のときは特に |
| ④ | **Cloudflare（公開 URL）** | Quick Tunnel（`https://〜.trycloudflare.com`）を通る分の遅れや制限（同時 200 件まで） |

**同じ負荷を、通り道を変えて**かけ、どこで遅くなるかを比べて切り分けます。

```
試験 A  負荷をかける Mac ──────────────────────────────→ サーバー（同じ Mac の中）        ①②だけ
試験 B  負荷をかける Mac → Mac の回線 → Cloudflare → Mac の回線 → サーバー             ①②＋Mac の回線＋④
試験 C  別の PC（同じ Wi-Fi）→ Wi-Fi → Cloudflare → Mac の回線 → サーバー              ①②③④（授業と同じ通り道）
試験 D  別の PC（スマホのテザリングなど別の回線）→ Cloudflare → Mac の回線 → サーバー   生徒側の Wi-Fi を外したもの
```

- **A で遅い** → 原因はサーバー側（①か②）
- **A は速いのに C で遅い** → 原因は通り道（③か④）。B・D と比べて、どこかを決める

## 2. 始める前に

- **生徒が使っている時間には行わないでください。** 試験中はサーバーがとても重くなります。
- 試験には **試験用の参加者（LT01〜LT40）** を作って使います。本物の参加者の記録・単語・お手本には触れません。最後に消します（[9. 片付け](#9-片付け)）。
- 結果は `.tmp/loadtest/` に保存します（GitHub には上がりません）。
- 用意するもの
  - サーバーの Mac（必須）
  - もう 1 台の PC（試験 C・D に使う。Windows でも Mac でもよい。Python 3 が入っていること）
  - スマートフォンのテザリング（試験 D に使う。無ければ D は省いてよい）
- **前回うまくいかなかった試験の条件**を、わかる範囲でメモしておいてください（あとで比べます）。
  - 人数・実行したコマンド
  - URL（`http://127.0.0.1:5000` か `https://〜.trycloudflare.com` か）
  - 負荷をかけた PC と、その PC・Mac のつなぎ方（同じ Wi-Fi か、有線か）
  - サーバーをどう起動したか（「SP-PS 起動」か `python app.py` か）
  - 何が起きたか（止まった画面、出たエラー、どのくらいで遅くなったか）

> **ターミナルでの注意**
> - コマンドは枠の中を**そのまま**コピーして貼り、Enter キーを押します。
> - ターミナルを閉じたり新しく開いたりしたら、[3-1](#3-1-フォルダへ移動する) のコマンドをもう一度実行してください（フォルダの移動と、使う Python の指定が消えるため）。

## 3. 準備（Mac）

### 3-1 フォルダへ移動する

ターミナル（アプリケーション → ユーティリティ → ターミナル）を開き、次を実行します。

```bash
cd ~/Desktop/spps/SP-PS-2026
mkdir -p .tmp/loadtest
PY=.venv/bin/python
[ -x "$PY" ] || PY=python3
echo "使う Python: $PY"
```

### 3-2 最新の版にする

```bash
git pull
git log -1 --oneline
```

最後の行に、いちばん新しいコミット（GitHub の main と同じもの）が表示されれば大丈夫です。

> 2026-10-16 に「ログインのたびに全員が 1 人ずつ順番に待たされる」不具合を直しています（コミット e243a55）。それより前の版で試験していた場合は、この不具合も遅さの原因の 1 つです。

### 3-3 Mac の性能とつなぎ方を記録する

次をまとめて貼りつけて実行します。結果は `.tmp/loadtest/mac_info.txt` にも保存されます。

```bash
{
  echo "== 日時"; date
  echo "== Mac"; sysctl -n hw.model; sysctl -n machdep.cpu.brand_string
  echo "CPU の数: $(sysctl -n hw.ncpu)"
  echo "メモリ: $(( $(sysctl -n hw.memsize) / 1073741824 )) GB"
  echo "macOS: $(sw_vers -productVersion)"
  echo "== アプリの版"; git log -1 --oneline
  echo "== インターネットへのつなぎ方"
  IF=$(route get default 2>/dev/null | awk '/interface:/{print $2}')
  networksetup -listallhardwareports | grep -B1 "Device: $IF" | head -1
  echo "== ディスクの空き"; df -h . | tail -1
  echo "== メモリの空き"; memory_pressure | tail -1
  echo "== スワップ"; sysctl vm.swapusage
} | tee .tmp/loadtest/mac_info.txt
```

- 「インターネットへのつなぎ方」が `Hardware Port: Wi-Fi` なら Mac は Wi-Fi、`Ethernet` や `USB 10/100/1000 LAN` などなら有線です。

続けて、Mac の回線の速さを測ります（20 秒ほどかかります。macOS 12 以降）。

```bash
networkQuality -v | tee .tmp/loadtest/network_quality.txt
```

- `Uplink capacity`（上り）と `Downlink capacity`（下り）を記録します。**上り**は、Mac から生徒へ画面・お手本の動画を送る速さです。
- Mac が Wi-Fi のときは、メニューバーの Wi-Fi のマークを **option キーを押しながらクリック** し、表示される「RSSI」「ノイズ」「送信レート」「チャンネル」も記録してください。

### 3-4 サーバーの起動のしかたを確かめる

候補 ①（起動のしかた）を確かめます。

```bash
ps aux | grep -E "gunicorn|app\.py" | grep -v grep
```

| 表示 | 意味 | すること |
|---|---|---|
| `gunicorn app:app -c gunicorn.conf.py` が **3 行**（親 1・ワーカー 2） | 正しい起動 | そのまま次へ |
| `python app.py`（または `Python app.py`）が出る | **Flask の開発用サーバー**で動いている（①） | その画面で Ctrl+C を押すなどして止め、下の手順で起動し直す |
| 何も出ない | サーバーが動いていない | 下の手順で起動する |

前回の試験が `python app.py` で動いていた場合、**それだけで「重くなって動かない」原因になりえます**。メモしておいてください。

最新の版で動かすため、サーバーを起動し直します。

```bash
scripts/server.sh stop
scripts/server.sh start
```

- 1〜2 分で「起動しました。」と表示されます。**公開 URL は起動のたびに変わります。** 生徒に配った QR コードは使えなくなるので、試験が終わったら印刷し直してください。

動いていることを確かめます。

```bash
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:5000/login
grep -c "Booting worker" .tmp/serve/gunicorn.log
```

- 1 行目が `200` なら動いています。
- 2 行目は、ワーカーが起動した回数です。この数を覚えておき、試験のあとにもう一度見ます（増えていたら、試験中にワーカーが落ちて起動し直したということです）。

### 3-5 試験用の参加者を作る

単語とお手本を登録してある参加者をコピーして、試験用の参加者を 40 人分作ります。まず、お手本の動画がある参加者を探します。

```bash
for d in data/users/*/; do echo "$(basename "$d"): お手本の動画 $(find "$d" -path '*library/sound*' -name '*.webm' | wc -l | tr -d ' ') 本"; done
```

お手本の動画が多い参加者を 1 人選びます（以下、`A01` を選んだ例です。**実際の ID に置きかえてください**）。コピーする前に、その参加者のデータの大きさを確かめます。

```bash
du -sh data/users/A01/library
```

この大きさ × 40 人分の空きが、[3-3](#3-3-mac-の性能とつなぎ方を記録する) の「ディスクの空き」にあれば大丈夫です。作ります。

```bash
$PY scripts/loadtest_accounts.py create --count 40 --from A01
```

- `LT01: 作りました（単語 ○ 個）` が 40 行出れば完了です。パスワードはすべて `loadtest123` です。
- 作った ID は先生モードの「参加者アカウントの管理」にも表示されます。試験のあとで消します。

## 4. 試験 A：Mac の中だけで（Wi-Fi と Cloudflare を通さない）

サーバーそのものの力を測ります。ネットワークを通らないので、**ここで遅ければ原因は ① か ②** です。

### 4-1 Mac の様子を見る・記録する

1. アクティビティモニタ（アプリケーション → ユーティリティ）を開き、「CPU」と「メモリ」のタブを見えるところに置きます。試験中、**CPU の使用率**と、メモリのタブの下にある**メモリプレッシャーのグラフの色**（緑・黄・赤）を見ておきます。
2. ターミナルで、CPU・メモリ・ネットワークの様子を 5 秒ごとにファイルへ記録し始めます。

```bash
top -l 0 -s 5 -n 0 | grep --line-buffered -E "^([0-9]{4}/|CPU usage|PhysMem|Load Avg|Networks)" > .tmp/loadtest/top_A.txt &
```

### 4-2 人数を増やしながら試験する

1 回 3 分です。**少ない人数から順に**行い、各回のあいだは 1 分あけます。1 回ごとに結果の表が出ます。

```bash
$PY scripts/loadtest.py --url http://127.0.0.1:5000 --users 5 --minutes 3 --json .tmp/loadtest/A_05.json | tee .tmp/loadtest/A_05.txt
```

```bash
$PY scripts/loadtest.py --url http://127.0.0.1:5000 --users 10 --minutes 3 --json .tmp/loadtest/A_10.json | tee .tmp/loadtest/A_10.txt
```

```bash
$PY scripts/loadtest.py --url http://127.0.0.1:5000 --users 20 --minutes 3 --json .tmp/loadtest/A_20.json | tee .tmp/loadtest/A_20.txt
```

```bash
$PY scripts/loadtest.py --url http://127.0.0.1:5000 --users 30 --minutes 3 --json .tmp/loadtest/A_30.json | tee .tmp/loadtest/A_30.txt
```

```bash
$PY scripts/loadtest.py --url http://127.0.0.1:5000 --users 40 --minutes 3 --json .tmp/loadtest/A_40.json | tee .tmp/loadtest/A_40.txt
```

- **失敗が出た、または採点の 90% が 10 秒を超えたら、その人数で止めて**かまいません。そこが、この Mac で（仮想の生徒で）耐えられる人数の目安です。
- 試験中は 10 秒ごとに `採点 ○ 回・直近の採点の中央値 ○秒・失敗 ○・503 ○` と表示されます。途中でやめるときは Ctrl+C を押します（そこまでの結果が表示されます）。

### 4-3 記録を止めて、ログを確かめる

```bash
pkill -f "top -l 0"
grep -c "Booting worker" .tmp/serve/gunicorn.log
grep -nE "WORKER TIMEOUT|Traceback|Error|Killed" .tmp/serve/gunicorn.log | tail -20
grep "\[capacity\]" .tmp/serve/gunicorn.log | tail -10
sysctl vm.swapusage
```

- `Booting worker` の数が [3-4](#3-4-サーバーの起動のしかたを確かめる) のときより増えていたら、試験中にワーカーが落ちています（メモリ不足などの疑い）。
- `WORKER TIMEOUT`・`Traceback`・`Killed` などが出ていたら、その行を記録してください。ログには前の日のものも残っているので、行の頭の日時（`[2026-10-20 14:05:00 +0900]` のような部分）や前後の行を見て、試験中のものか確かめます。
- `[capacity] 解析の順番を ○ 秒待ちました` は、採点などの重い処理が順番待ちになったときに書かれます（1 秒以上待ったときだけ）。`[capacity] 40秒待っても順番が来なかったため 503 を返しました` は、混み合って断ったときです。たくさん出ていれば、**CPU の力の限界**です（②）。行の終わりの `slots` は 1 つのワーカーで同時に動かせる重い処理の数、`waiting` はそのとき順番を待っていた数です。
- スワップの `used` が試験前より大きく増えていたら、メモリが足りていません（②）。

## 5. 試験 B：Mac から公開 URL へ（Cloudflare を通す）

公開 URL を通すと、Mac の回線と Cloudflare を通ります。まず今の公開 URL を確かめます。

```bash
scripts/server.sh status
```

表示された `https://〜.trycloudflare.com` を、下のコマンドの `https://xxxx.trycloudflare.com` のところに入れて実行します。

```bash
$PY scripts/loadtest.py --url https://xxxx.trycloudflare.com --users 10 --minutes 3 --json .tmp/loadtest/B_10.json | tee .tmp/loadtest/B_10.txt
```

```bash
$PY scripts/loadtest.py --url https://xxxx.trycloudflare.com --users 20 --minutes 3 --json .tmp/loadtest/B_20.json | tee .tmp/loadtest/B_20.txt
```

- 試験 A で問題がなかった人数までにしてください（A で 20 人が限界なら、B も 20 人まで）。
- Quick Tunnel は同時に処理できる要求が 200 件までなので、人数は 40 人までにしてください。

終わったら、Cloudflare 側のログにエラーが出ていないか確かめます。

```bash
grep -inE "error|ERR |429|502|524" .tmp/serve/cloudflared-quick.log | tail -20
```

## 6. 試験 C・D：別の PC から公開 URL へ（Wi-Fi を通す）

授業と同じ通り道で測ります。負荷をかける PC には、`scripts/loadtest.py` だけがあれば動きます（Python 3 の標準の機能だけで動きます）。

### 6-1 別の PC の準備

次のどちらかで、`loadtest.py` を用意します。

- **リポジトリを取ってくる**（GitHub にアクセスできる場合）

  ```bash
  git clone https://github.com/Smart-Agent-and-Intelligence-Labs/SP-PS-2026.git
  cd SP-PS-2026
  ```

- **ファイルを 1 つだけコピーする**：Mac の `scripts/loadtest.py` を、USB メモリや AirDrop などで別の PC の `scripts` フォルダにコピーし、その 1 つ上のフォルダで実行します。

### 6-2 試験 C：Mac と同じ Wi-Fi から

別の PC を、**生徒が使うのと同じ Wi-Fi** につないで実行します。URL は [5](#5-試験-bmac-から公開-url-へcloudflare-を通す) で確かめたものです。

- **Mac・Linux の場合**

  ```bash
  python3 scripts/loadtest.py --url https://xxxx.trycloudflare.com --users 10 --minutes 3 --json C_10.json | tee C_10.txt
  ```

  ```bash
  python3 scripts/loadtest.py --url https://xxxx.trycloudflare.com --users 20 --minutes 3 --json C_20.json | tee C_20.txt
  ```

- **Windows の場合（PowerShell）**

  ```powershell
  $env:PYTHONIOENCODING = "utf-8"
  python scripts\loadtest.py --url https://xxxx.trycloudflare.com --users 10 --minutes 3 --json C_10.json | Tee-Object C_10.txt
  python scripts\loadtest.py --url https://xxxx.trycloudflare.com --users 20 --minutes 3 --json C_20.json | Tee-Object C_20.txt
  ```

あわせて、その PC の回線の速さも記録してください（Mac なら `networkQuality -v`、Windows ならブラウザで速度テストのサイトを開く）。

### 6-3 試験 D：別の回線から（任意）

別の PC を **スマートフォンのテザリング** など、学校（研究室）の Wi-Fi ではない回線につないで、試験 C と同じコマンドを実行します（ファイル名の `C_` を `D_` に変えてください）。

- C だけ遅く、D は速い → **生徒側の Wi-Fi** が混んでいます。
- C も D も遅い → **Mac 側の回線**か **Cloudflare** です（A・B と比べます）。

## 7. 試験 E：実際の授業に近い速さで（任意）

`loadtest.py` の仮想の生徒は、既定（`--think 2`）では **1 人 1 分に約 6 回** 採点します。実際の生徒は、お手本を見る・録音する・結果を読むのに時間を使うので、1 分に 1〜2 回ほどです。**仮想の生徒 1 人は、実際の生徒 3〜6 人分の重さ**です。

`--think 6` にすると、1 人あたり約 30 秒に 1 回の採点になり、実際の生徒に近くなります。授業で同時に使う人数（例：30 人）で、生徒と同じ Wi-Fi の PC から実行します。

```bash
python3 scripts/loadtest.py --url https://xxxx.trycloudflare.com --users 30 --minutes 5 --think 6 --json E_30.json | tee E_30.txt
```

（Windows では、[6-2](#6-2-試験-cmac-と同じ-wi-fi-から) と同じ書き方で `--think 6` を足します。）

これで問題がなければ、その人数の授業では使えると考えてよいです。

## 8. 結果の見方と、原因の決め方

### 8-1 結果の表の読み方

試験が終わると、次のような表が出ます。

```
人数 10・190 秒・採点が終わった練習 61 回（1分あたり 19.3 回）
                           成功  失敗   503   中央値      90%      99%     最大
ログイン                     10     0     0    0.12s    0.15s    0.15s    0.15s
ホーム（/select）            30     0     0    0.03s    0.05s    0.08s    0.08s
録音ページ                   61     0     0    0.02s    0.04s    0.06s    0.06s
口の動画を送る               61     0     0    0.30s    0.52s    0.61s    0.61s
録音を送る（Julius）         61     0     0    0.40s    0.70s    0.85s    0.85s
結果を見る（採点）           61     0     0    0.31s    0.43s    0.55s    0.55s
記録（/history）             20     0     0    0.05s    0.09s    0.10s    0.10s
CSS・JS                     420     0     0    0.00s    0.01s    0.02s    0.02s
お手本の取り出し             20     0     0    0.01s    0.02s    0.03s    0.03s
```

（数字は例です。）

| 列 | 意味 |
|---|---|
| 成功・失敗 | その要求がうまくいった回数・失敗した回数 |
| 503 | 「いま混み合っています」が返った回数（自動で送り直して、成功・失敗のどちらかに数え直す） |
| 中央値・90%・99%・最大 | 応答にかかった秒数。**90%** は「10 回のうち 9 回はこれより速い」という値 |

- **重い要求**：「口の動画を送る」「録音を送る（Julius）」「結果を見る（採点）」。CPU をたくさん使います。
- **軽い要求**：「ホーム」「録音ページ」「記録」「CSS・JS」「お手本の取り出し」。CPU をほとんど使いません。

**目安**（授業で快適に使えるか）

| 項目 | 快適 | 待たされる感じが強い |
|---|---|---|
| ホームの 90% | 1 秒未満 | 3 秒以上 |
| 結果を見る（採点）の 90% | 5 秒未満 | 10 秒以上 |
| 失敗 | 0 | 1 件でもあれば内容を確かめる |

### 8-2 原因の決め方

| 見えたこと | 原因 | 次に確かめること |
|---|---|---|
| [3-4](#3-4-サーバーの起動のしかたを確かめる) で `python app.py` が動いていた | ① **Flask の開発用サーバー** | 正しい起動（`scripts/server.sh start`）で試験 A をやり直す |
| **試験 A** で、重い要求だけが遅く、503 が出る。軽い要求（ホーム・CSS・JS）は速い。CPU が 100% 近い。ログに `[capacity]` が多い | ② **CPU の力の限界**（作りどおり順番待ちになっている） | 何人から遅くなるか ＝ この Mac で同時に使える目安。試験 E の速さに直すと何人分か |
| **試験 A** で、軽い要求（ホーム・CSS・JS）まで遅い。メモリプレッシャーが黄・赤、スワップが増えている | ② **メモリ不足** | アクティビティモニタのメモリの使用量。ほかのアプリを閉じてやり直す |
| **試験 A** で `Booting worker` が増えた・`Killed` が出た | ② ワーカーが落ちた（メモリ不足など） | [4-3](#4-3-記録を止めてログを確かめる) のログ |
| **試験 A は速い**のに、試験 B で遅い・失敗 | Mac の回線（③）か Cloudflare（④） | Mac が Wi-Fi か有線か。`networkQuality` の上り |
| **試験 A・B は速い**のに、試験 C で遅い・失敗 | ③ **生徒側の Wi-Fi** | 試験 D（別の回線）が速ければ確定 |
| 試験 B・C・D すべて遅い（A は速い） | Mac の回線か Cloudflare | Mac を有線 LAN にして試験 B をやり直す（速くなれば Mac の Wi-Fi が原因） |

### 8-3 失敗の内訳の読み方

表の下に `失敗の内訳:` が出たときは、次を見ます。

| 内訳 | 意味 | すること |
|---|---|---|
| `HTTP 401`（ログイン） | 試験用の参加者が無い・パスワードが違う | [3-5](#3-5-試験用の参加者を作る) をやり直す |
| `単語がない` | `--from` に指定した参加者に単語が無い | 単語のある参加者で作り直す |
| `HTTP 503` | 6 回送り直しても混み合ったまま | ②（CPU の限界） |
| `HTTP 429` | Quick Tunnel の同時 200 件の制限 | 人数を減らす |
| `HTTP 502`・`HTTP 530` | Cloudflare から Mac のアプリにつながらない（アプリが止まった・トンネルが切れた） | `scripts/server.sh status`、[5](#5-試験-bmac-から公開-url-へcloudflare-を通す) の cloudflared のログ |
| `HTTP 524` | Cloudflare の待ち時間（100 秒）を超えた | ②（順番待ちが長すぎる） |
| `TimeoutError`・`URLError`・`RemoteDisconnected`・`ConnectionResetError` など | 応答が 120 秒以内に返らない・接続が切れた | 軽い要求でも出るなら③④、重い要求だけなら② |

## 11. 困ったとき

| 困ったこと | すること |
|---|---|
| `command not found: networkQuality` | macOS 11 以前です。省いてかまいません（ブラウザで速度テストのサイトを使う） |
| `loadtest_accounts.py` で「単語が見つかりません」 | `--from` の ID が違うか、その参加者に単語がありません。[3-5](#3-5-試験用の参加者を作る) の一覧から選び直す |
| 試験中に Mac が固まったようになった | 数分待つ。戻らなければ、試験のターミナルで Ctrl+C を押す。それでもだめなら `scripts/server.sh stop` → `scripts/server.sh start` |
| `scripts/server.sh start` で「ポート 5000 は使用中です」 | 前のサーバーが残っています。`scripts/server.sh stop` を実行し、それでも出るときは [3-4](#3-4-サーバーの起動のしかたを確かめる) の `ps` の結果で `python app.py` が動いていないか確かめる |
| `zsh: no such file or directory: .venv/bin/python` | [3-1](#3-1-フォルダへ移動する) を実行していないか、別のフォルダにいます。[3-1](#3-1-フォルダへ移動する) をやり直す |
| 実際のスマートフォンで試したい | **1 台に 1 つの利用者 ID** を使ってください。同じ ID を何台もで使うと、その人の処理は 1 つずつ順番に行われるので、サーバーの力ではなく 1 人分の速さを測ってしまいます |

## 12. 参考：サーバーの作り

試験の結果を読むときの手がかりです。くわしくは README §5.4「同時に使う人が多いとき」を見てください。

- **起動のしかた**：「SP-PS 起動」・`scripts/server.sh start` は、gunicorn を **ワーカー 2（プロセス）× スレッド 16** で動かします（`gunicorn.conf.py`）。声の高さの計算などの Python の処理は、1 つのプロセスの中では同時に 1 つしか進まないので、プロセスを分けて CPU のコアを使います。`python app.py` はプロセス 1 つの開発用で、大勢では使えません。
- **重い処理の順番待ち**：採点（結果を見る）・録音の受け取り（Julius）・お手本の登録は、1 つのワーカーで同時に動かす数を決めています（CPU の数 ÷ ワーカー数。2〜4。`core/capacity.py`）。超えた分は順番を待ち、40 秒待っても順番が来ないときは 503「いま混み合っています」を返します。ホームなどの軽い画面は、順番待ちと関係なくすぐ返ります。
- **同じ人の処理は 1 つずつ**：同じ利用者 ID の送信は、1 つずつ順番に処理します（作業フォルダが 1 人に 1 つのため）。
- **Quick Tunnel**：`https://〜.trycloudflare.com` は Cloudflare の試験用の公開のしかたで、同時に処理できる要求は 200 件までです。起動のたびに URL が変わります。
- **前に測った数字**（2026-10-15、開発用の PC の Linux・CPU 8 個、ネットワークを通さずに測定）：40 人で採点の 90% が 0.9 秒、ホームの最大 0.08 秒、失敗 0。80 人で CPU を使い切ると採点は順番待ち（中央値 2.4 秒）になりましたが、失敗はありませんでした。**サーバーの Mac では、まだ測っていません。**
