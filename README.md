# SP-PS — 日本語発音練習・評価システム

> 「声（口）のかたちを綺麗にする一歩を踏める嬉しさを届ける」

録音した日本語単語の発音をお手本の録画と比較し、**アクセント（声の高さ）・モーラ長（長さ）・母音品質（口の形）の3軸**で 100 点満点のスコアとフィードバックを返す Flask ベースの Web アプリケーションです。

- 音声は **Julius 強制アライメント**でモーラ単位に区切り、**Praat（parselmouth）**でピッチ（F0）とフォルマント（F1/F2）を測ります。
- 口の動きは **MediaPipe Face Mesh** で数値化し、声と口のタイミングのズレを調べる**音映像クロスチェック**を備えます。
- 単語は**テキストとお手本録画（動画）をセットで登録**し、その動画から音声と口の動きの両方を取り込みます。
- 聴覚に障害のある中学部・高等部の生徒の発音練習を主な想定利用者とし、研究参加者ごとに練習記録を分けて保存します（倫理審査資料 SP-PS 準拠）。

この README は、引き継ぎのための手順書であると同時に、**論文・研究発表で手法を記述するときの参照資料**として書いています。数値や式はすべて現在のソースコードと一致させてあり、どのファイルのどの関数に書かれているかを併記しています。論文で使うときは、まず [§11 研究で参照するときのまとめ](#11-研究で参照するときのまとめ) を見てください。

## 1. プロジェクト概要

### 何ができるシステムか

SP-PS は、学習者が**自分の発音をお手本と客観的に比較する**ためのシステムです。
お手本は、指導者が単語登録時に録画した音声・映像をそのまま使います（合成音声は使いません）。

| 機能カテゴリ | 内容 | 詳細 |
|------------|------|------|
| **発音スコアリング** | アクセント・モーラ長・母音品質の3軸を数値化（100点満点）し、音ごとのできばえとフィードバック文を返す | [§6](#6-発音評価スコアに入るもの) |
| **口形分析** | 唇の形のベクトル列を DTW で比べた唇スコアと、モーラごとの口の開き（縦横比）をお手本と比較 | [§7.2](#72-口形分析mediapipe-face-mesh) |
| **音映像クロスチェック** | 声と口の動きが同じ瞬間を指しているかを照合し、同期のズレをミリ秒で表示（試験運用中） | [§7.3](#73-音映像クロスチェック口と声の同期) |
| **音色評価** | MFCC + DTW で、登録済みの全単語のお手本とのスペクトルの近さを並べる | [§7.4](#74-音色評価mfcc--dtw) |
| **お手本動画の再生** | 登録時に録画した口の動きを、録音ページ・母音トレーナーで見ながら練習できる | [§4](#4-起動方法と画面の使い方) |
| **参加者ログイン** | 研究者が割り当てた利用者 ID でログインし、練習記録を参加者ごとに分離して保存 | [§10](#10-参加者アカウントとデータの分離) |
| **学習分析** | 練習履歴から上達速度・停滞・アクセント型ごとの難しさを統計的に集計 | [§8.4](#84-学習曲線分析) |
| **今日のレッスン** | 履歴から当日の練習メニュー（復習・苦手音・口の形・挑戦）を自動編成 | [§8.3](#83-今日のレッスン) |
| **苦手音ドリル・クイズ** | モーラ別スコアから弱点の音を特定し、段階的な集中ドリルとことば当てクイズを出す | [§8.2](#82-苦手な音の分析集中ドリルことば当てクイズ) |

### スコアに入るもの・入らないもの

論文でスコアの意味を説明するときに混同しやすいため、はじめに整理しておきます。

| 項目 | 合計点に入るか | 計算する場所 |
|------|:------------:|------------|
| アクセント（声の高さ） | ○ 50点 | `core/evaluate.py` `calc_accent_score()` |
| モーラ長（長さ） | ○ 30点 | `core/evaluate.py` `calc_length_score()` |
| 母音品質（口の形＝フォルマント） | ○ 20点 | `core/formant.py` `calc_vowel_score()` |
| モーラ別スコア（音ごとのできばえ） | × 合計点とは別に計算（苦手音分析に使う） | `core/evaluate.py` `calc_mora_scores()` |
| 発話速度・声の揺れ（ジッター・シマー） | × 表示のみ | `core/evaluate.py` `calc_speaking_rate()`、`core/formant.py` `calc_voice_quality()` |
| 唇スコア・モーラ別の口の開き | × 表示のみ | `app.py` `_compute_lip_score()` ほか |
| 音映像クロスチェック | × 表示のみ | `core/sync.py` `compute_av_sync()` |
| 音色（MFCC + DTW） | × 表示のみ | `core/timbre.py` `dtw_ascending_order()` |
| 信頼区間 | × 表示のみ（過去の合計点から計算） | `core/confidence.py` `bootstrap_ci()` |

「口の形」は、合計点では**音声のフォルマント**から、表示の唇スコアや口の開きでは**映像**から測っています。同じ言葉で呼んでいますが別の測り方です。

## 2. 動作環境と必要ソフトウェア

### OS・ハードウェア

| 項目 | 要件 |
|------|------|
| OS | Windows 10/11（推奨）・Ubuntu 22.04 LTS |
| Python | **3.10 〜 3.12**（3.13 は不可。理由は下記） |
| カメラ | お手本の登録と口形分析に必要（内蔵または外付け USB カメラ） |
| マイク | 内蔵マイクでも動作するが、外付けコンデンサーマイク推奨 |
| ブラウザ | カメラ・マイクを使うため HTTPS または `localhost` で開く（[§4](#スマートフォンで使うngrok)） |

### 外部ソフトウェア

| ソフトウェア | 役割 | 必須/任意 |
|------------|------|---------|
| **Julius 4.3.1** | 音素強制アライメント | **必須**（Windows 版は `engine/bin/` に同梱） |
| **Perl** | Julius を呼び出すセグメンテーションスクリプト（`scripts/segment_julius.pl`）の実行 | **必須** |
| **FFmpeg** | お手本録画（WebM）から音声を取り出す（pydub が内部で使う） | **必須**（単語登録にお手本録画が必要なため） |
| MeCab + UniDic | 単語登録時のアクセント型自動取得 | 任意（取得できなくても登録・採点は可能） |
| MediaPipe + OpenCV | 口形分析・音映像クロスチェック | 任意（無ければ該当の表示が出ないだけ） |

> **Perl について：** Windows では Strawberry Perl と Git 同梱の msys perl のどちらでも動作します。
> どちらが使われるかで内部的に必要なパス形式が異なりますが、アプリ側が自動判別して切り替えます
> （`core/alignment.py` `_run_alignment_process()`）。
>
> **VOICEVOX について：** 初期データセットのサンプル音声生成に使用していましたが、
> **現在の単語登録・採点では使用しません**（お手本録画の音声をそのまま使うため）。インストール不要です。

> **Python 3.13 では口形分析が動きません。**
> MediaPipe は 3.13 向けビルドで旧 API（`mp.solutions.face_mesh`）を廃止しており、
> 本アプリはこの API を使っています。3.13 で入手できる MediaPipe（0.10.30 以降）には
> いずれもこの API がなく、映像アップロード時に 500 エラーになります。
> **Python 3.12 を使ってください。** 3.12 では `mediapipe==0.10.21` が旧 API を持っており、正常に動作します。
>
> 複数の Python が入っている場合は `python -V` で 3.12 が使われているか確認してください。
> `py -3.12 app.py` のようにバージョンを明示して起動することもできます。

> **UniDic 辞書のダウンロードについて（Windows）：**
> `python -m unidic download` は Windows では
> `ValueError: cannot find context for 'fork'` で失敗します（`fork` は Unix 専用のため）。
> 失敗するのはコマンドライン部分だけなので、次のように内部関数を直接呼べば取得できます（約 526MB）。
>
> ```bash
> python -c "from unidic.download import download_version; download_version('latest')"
> ```

### Python パッケージ

`requirements.txt` に記載されています。アプリが実際に使っている用途は次のとおりです。

| パッケージ | 役割 | 使っている場所 |
|-----------|------|--------------|
| `flask` | Web サーバー | `app.py` |
| `gunicorn` | 本番用 WSGI サーバー（Docker / Railway） | `Dockerfile`・`Procfile` |
| `praat-parselmouth` | Praat による F0・フォルマント・ジッター/シマーの測定 | `core/pitch.py`・`core/formant.py` |
| `librosa` | 音声の読み込みと MFCC 抽出 | `core/timbre.py`・`scripts/regenerate_mfcc.py` |
| `numpy` / `scipy` | 数値計算、Pearson 相関、線形回帰、WAV 入出力 | `core/` 全般 |
| `fastdtw` | DTW（音色・唇スコア・クロスチェック） | `core/timbre.py`・`core/sync.py`・`app.py` |
| `pydub` | WAV のサンプリング変換、WebM → WAV（FFmpeg 経由） | `core/audio.py`・`app.py` |
| `mediapipe==0.10.21` / `opencv-python` | 顔ランドマーク検出と動画フレームの読み込み（任意） | `app.py` |
| `mecab-python3` / `unidic` | アクセント型の自動取得（任意） | `core/accent.py` |
| `audioop-lts` | Python 3.13 以降で pydub を動かす互換モジュール | （3.13 のみ） |

`requirements.txt` にある `noisereduce`・`soundfile`・`matplotlib` は、現在のアプリから直接は使っていません
（`noisereduce` は `core/audio.py` の `reduce_noise_wav()` だけが使いますが、この関数はどこからも呼ばれていないため、**録音にノイズ除去はかけていません**）。
`scripts/md_to_docx.py`（倫理審査資料の Word 変換）は `python-docx` が必要ですが、`requirements.txt` には入っていません。

ブラウザ側では Chart.js（グラフ）と、母音トレーナー用の MediaPipe Face Mesh（JavaScript 版）を CDN から読み込みます。

### ステップ 3 ― Julius をセットアップ

Julius は発音の各音素がいつ発音されているか（タイムスタンプ）を特定するために使います。

**Windows の場合**

`engine/bin/` に Julius の実行ファイルが同梱されています。

```
engine/
├── bin/
│   └── julius-4.3.1.exe      ← Windows 用実行ファイル（同梱）
└── models/
    └── hmmdefs_monof_mix16_gid.binhmm   ← 使用する音響モデル（monophone）
```

Julius は以下の順に自動検出されます（`config.py` の `_detect_julius()`）。

1. 環境変数 `JULIUS_BIN`
2. `engine/bin/julius*.exe`（Windows 自動検出）
3. `/opt/homebrew/bin/julius`（Mac Apple Silicon）
4. `/usr/local/bin/julius`（Mac Intel / Linux）
5. PATH 検索

**Ubuntu / Debian の場合**

```bash
sudo apt-get install -y julius
```

### ステップ 7 ― 先生用パスワードを決め、参加者アカウントを作成する

アプリはログインが必要です。研究者が管理画面から参加者アカウントを作成します。
管理画面と、単語・お手本を変える操作は**先生用パスワード**を入れた「先生モード」でだけ使えます。

1. 先生用パスワードを設定する（最初の1回。変えるときも同じコマンド）

   ```bash
   python scripts/set_teacher_password.py
   ```

   8〜128文字。生徒に知られないものにします。ハッシュだけが `data/config/teacher.json` に保存されます
   （クラウドなどでは、代わりに環境変数 `SP_PS_TEACHER_PASSWORD` に設定しても構いません。こちらが優先されます）。
2. `python app.py` で起動し、[http://127.0.0.1:5000/admin/accounts](http://127.0.0.1:5000/admin/accounts) を開き、先生用パスワードを入力する
3. 「新しい参加者を登録」で以下を入力する

| 項目 | 内容 |
|------|------|
| 利用者 ID | 研究者が割り当てる。英字始まりの半角英数（`-` `_` 可）1〜32文字。例：`A01` |
| 学年 | 中学部 / 高等部 / 未回答 |
| 聴覚障害の程度 | 軽度難聴 / 中等度難聴 / 高度難聴 / 重度難聴 / 未回答 |

4. 参加者に利用者 ID を伝える。**パスワードは参加者本人が初回ログイン時に設定**する
   （6〜128文字。`werkzeug` でハッシュ化して保存し、平文は保持しない）

> **設計上の理由：** 本人が ID を自由に決めると氏名やあだ名が混入し、データ内に
> 個人を識別できる文字列が残ってしまいます。そのため ID は研究者が割り当て、
> 本人が決めるのはパスワードのみとしています（倫理審査資料 §6.1）。
>
> 学年・聴覚障害の程度は調査票由来の情報のため、研究者のみが管理画面から入力します。
> 聴覚障害の程度は**要配慮個人情報**にあたるため、dB 値などの詳細は持たず区分で保持します。

パスワードを忘れた場合は、管理画面の「パスワードをリセット」で未設定状態に戻せます。
参加者が撤回した場合は「削除」でアカウントごと削除できます。

### ステップ 8 ― 単語を登録する

ホーム右上の設定 → 先生モードを ON → 「単語を追加」から、表示テキスト・ひらがな読みを入力し、お手本を録画します
（処理の中身は [§9](#9-単語登録とお手本データ)）。アクセント型・MFCC・口形データは登録時に自動で作られるので、別途スクリプトを実行する必要はありません。

> **読みの書き方：** 長音は「がっこう」のように「う」「い」で書いても、「がっこー」のように「ー」で書いてもかまいません。

### スマートフォンで使う（ngrok）

本アプリはスマートフォンでの利用を主に想定していますが、**PC の IP アドレスに
直接アクセスする方法では録音・録画ができません**。ngrok で HTTPS の URL を
作って接続します。

#### なぜ ngrok が必要か

ブラウザはカメラとマイク（`getUserMedia`）を**セキュアコンテキストでしか許可しません**。

| アクセス方法 | ページ表示 | カメラ・マイク |
|------------|:--------:|:------------:|
| `http://127.0.0.1:5000`（PC 自身） | ○ | **○**（localhost は例外的に許可される） |
| `http://192.168.x.x:5000`（同じ Wi-Fi のスマホ） | ○ | **×** ← 録音ボタンが動かない |
| `https://xxxx.ngrok-free.app`（ngrok） | ○ | **○** |

同じ Wi-Fi につないでも `http://` では録音できません。**HTTPS が必要**なため
ngrok を使います。ngrok はインターネット経由でトンネルするので、
**スマホが別のネットワーク（4G/5G 回線など）でも接続できます**。

#### 手順

**1. ngrok を用意する**（初回のみ）

```bash
# Windows
winget install ngrok.ngrok

# macOS
brew install ngrok
```

[ngrok.com](https://ngrok.com/) で無料アカウントを作り、認証トークンを登録します。

```bash
ngrok config add-authtoken <あなたのトークン>
```

**2. アプリを起動する**（1つ目のターミナル）

```bash
python app.py
```

`app.py` は `host="0.0.0.0"` で待ち受けるため、追加の設定は不要です。

**3. ngrok を起動する**（2つ目のターミナル。アプリは起動したままにする）

```bash
ngrok http 5000
```

次のように表示されるので、`Forwarding` の **https:// から始まる URL** を使います。

```
Forwarding    https://xxxx-xx-xx-xxx-xx.ngrok-free.app -> http://localhost:5000
```

**4. スマホでアクセスする**

この URL をスマホのブラウザ（Chrome / Safari）で開きます。
URL が長いので、PC で QR コードにするか、メッセージアプリで送ると確実です。

初回は ngrok の警告ページが出ます。**「Visit Site」を押す**と本アプリに進みます。

**5. カメラとマイクを許可する**

録音ボタンを押すと許可を求められるので、**「許可」**を選びます。
一度拒否すると再度聞かれないため、その場合はブラウザの設定から許可し直してください。

#### 注意点

| 項目 | 内容 |
|------|------|
| URL は毎回変わる | 無料プランでは `ngrok http` を実行するたびに別の URL になります。参加者への共有はそのつど必要です |
| ターミナルを閉じない | ngrok を止めると URL が無効になります。アプリと ngrok の**両方**を起動したままにしてください |
| 通信が外部を経由する | 音声・映像は ngrok 社のサーバーを経由します。研究データを扱う場合は取扱いの確認が必要です（倫理審査資料 §4.4 案 D と同じ論点） |
| 動作が遅くなることがある | 解析はすべて PC 側で行われるため、回線が細いと録音の送信に時間がかかります |

> **同じ Wi-Fi 内だけで使いたい場合：**
> `http://<PCのIPアドレス>:5000` でページは開けますが、前述のとおり**録音できません**。
> 練習記録の閲覧だけなら使えます。録音するには ngrok（または別途 HTTPS の用意）が必要です。

#### 画面の色のルール

色の種類が多いと画面が騒がしく、どこを見ればよいか分かりにくくなります。一方で色をなくしすぎると、
できた／直すところが一目で分からなくなります。そこで**基本はテーマカラー（青紫）の濃淡**にし、
**意味を伝えるところだけ少ない色を足す**ようにしています（`web/static/css/base.css`）。

| 色 | 意味 | 例 |
|----|------|----|
| 青紫（`--brand-*` / `--navy` / `--grad-*`） | 画面の基本 | ボタン、タブ、グラフの「あなた」、練習した日、連続記録、マスター、S評価 |
| 緑（`--good`） | できている | ◎、のびている、正解、前回より＋、A評価 |
| 琥珀（`--mid`） | もう少し | ○、足ぶみ中、口と声の少しのズレ、B評価 |
| 橙（`--todo`） | ここを直す | △、不正解、口と声のズレが大きい、C・D評価 |
| 赤（`--rec` / `--danger`） | 録音・エラー | 録音するボタン（●）、録音中の印、マイクが使えない、削除の確認 |
| 灰色（`--ref-line`） | お手本 | くらべるグラフの「お手本」 |

- 緑・琥珀・橙は**小さな印・バッジ・棒にだけ**使い、大きな面（カード・見出し）は青紫と白に保つ
- グラデーションの面（`.aurora`）は、その画面の主役1つだけに使う（今日のれんしゅう・つぎは、ここだけ・最近の点数・クイズ／ドリルの見出し）
- 色だけで意味を伝えないよう、状態には必ず ◎○△ や「のびている」などの文字を添える
- テーマカラーを変えるときは `--brand-50`〜`--brand-900` と `--grad-brand` / `--grad-hero`（暗いテーマ用も）を差し替える

#### 見た目のルール（デザインシステム v5）

- 面は線で区切らず、やわらかい影（`--elev-1` / `--elev-2`）で浮かせる。角は大きめ（カード 24px 前後）
- ヘッダーと画面下のタブバーはすりガラス風。タブバーは画面の下に浮かせたピル型
- 大きな数字（点数・連続日数など）は欧文書体 Plus Jakarta Sans、日本語は Noto Sans JP
- 音が聞こえにくい人にも「押せた・結果が出た」が伝わるよう、押し込み・点数のカウントアップ・リングの伸び・
  カードの入場などの小さな動きを添える（`theme.js` の `SPMotion`）。端末で「視差効果を減らす」を選んでいれば動かさない
- 押すものは 48px 以上、スマホの文字は 12px 以上、1画面に主ボタンは1つ、はこれまでどおり

### 録音前後の画面の動き

聴覚に障害のある方は、発音中に自分の声でテンポを確認できません。そこで「耳の代わりを画面が担う」設計にしていますが、
**動く合図に合わせることを求めない**ことを原則にしています。採点は各音の長さの“比率”で決まり、合図に合わせたかどうかは一切見ていないためです。

| タイミング | 画面の動き |
|-----------|-----------|
| 「お手本を見る」 | 全画面で先生の口の動画＋音が再生され、音の長さのバーが同じ時刻で光る。途中でも「このまま録音する」、見おわれば「録音する」「もう一度見る」「とじる」を選べる |
| 「録音する」を押した直後 | 大きな **3・2・1** のカウントダウン（この間は録音されない）。自分の口を映して構えられる |
| 録音中 | 全画面表示に切り替わり、**自分の口（カメラ）**が主役。単語と「自分のペースで言ってください」を表示し、お手本の長さは**動かない帯**として置くだけ（「合わせなくてOK」と明記） |
| お手本の長さぶんの時間が過ぎた後 | 「言い終わったら『録音停止』を押してください」に変わる（無音が続けば自動停止） |

カウントダウンの ON / OFF は録音ページの「練習の設定」で切り替えられます（設定はブラウザに保存され、既定は ON）。
振動に対応した端末（Android の Chrome など。iPhone の Safari は非対応）では、3・2・1、録音の開始・終わり、クイズの正解を短い振動でも伝えます（設定で OFF にできます）。

> **自分の口の動画について**：録音と同時に撮った口の動画は、解析のためにサーバーへ送られ、解析が終わるとサーバーからは削除されます。
> 「ならべて再生」のために、直前の1本だけをその端末のブラウザ（IndexedDB）に保存します（次の録音で上書き・2時間より古いものは使いません）。

お手本の長さの帯は、お手本のアライメント結果を使うため、お手本が登録済みの単語でのみ表示されます。

### 5.2 1回の練習で行われる処理

単語を選んでから結果が出るまでの処理です（`web/static/js/main.js` と `app.py` の `record_audio()`・`upload_lip_video()`・`audio_analysis()`）。

#### ブラウザ側

| 順 | 処理 | 詳細 |
|----|------|------|
| 1 | 単語を選ぶ | `POST /`（または `GET /practice/word/<word_id>`）が `data/config/word_id.txt` に単語 ID を、`data/raw_audio/wav/test.txt` にひらがな読みを書き、録音ページを返す |
| 2 | カメラ・マイクを開く | `getUserMedia({video, audio})`。音声は `AudioContext({sampleRate: 16000})` と AudioWorklet で 32bit 浮動小数のまま集める |
| 3 | 録音開始 | お手本の口形データがある単語（`/api/lip_refs/<word_id>/ratios` が空でない）では、同時に映像だけの `MediaRecorder`（WebM / VP8）で口の動画も撮る |
| 4 | 無音自動停止 | 0.5 秒以上の発話を検出したあと、音量（RMS）が 0.03 未満の状態が 1.5 秒続くと自動で停止する |
| 5 | 送信 | 音声を 16kHz・モノラル・16bit PCM の WAV にして `POST /audio`、口の動画を `POST /upload_lip_video`（`mode=test`）。両方が終わると「結果を見る」が出る |
| 6 | 解析 | 「結果を見る」で `POST /graph` |

録音前の 1.5 秒間はマイクの平均音量を測り、小さすぎる（RMS 平均 < 0.002）・雑音が大きい（> 0.05）ときは注意を表示します（採点には使いません）。

#### サーバー側

**`POST /audio`**：`test.wav` として保存 → `convert_to_16kHz()`（16kHz・モノラル・16bit でなければ変換）→ `run_alignment()`（[§5.3](#53-julius-強制アライメント)）で `test.lab` / `test.log` を作ります。

**`POST /upload_lip_video`（test）**：動画を一時ファイルに保存し、そのパスをセッションに入れます（解析後に削除）。

**`POST /graph`** は次の順に処理します。

```
 1. 単語 ID（word_id.txt）とお手本の音声（audio.scp）・.lab・.log を特定する
 2. 口の動画から唇形状ベクトル・口の開き・フレーム時刻を取り出し、唇スコアを出す     … §7.2（表示のみ）
 3. お手本・録音それぞれの声の高さの範囲を推定し、Praat でピッチを測って 10ms に揃える … §6.2
 4. .lab（秒）・.log（フレーム）を読み、音素・モーラの区間を得る                     … §5.3
 5. 発話区間を切り出し、録音のピッチをお手本の音素の長さに合わせ、半音に変換する     … §6.2
 6. 録音の発話区間（前後 100ms 付き）を test2.wav に切り出し、全単語と音色を比べる   … §7.4（表示のみ）

 9. フォルマントを測って母音スコアを出す（長音はまとまりの区間で測る）               … §6.5
10. ジッター/シマー、発話速度を計算する                                             … §7.1（表示のみ）
11. アクセント・長さ・母音から合計点とフィードバックを出す                           … §6.1〜§6.7
12. モーラ別スコアを出し、かなを付ける                                               … §6.6
13. この単語の過去の合計点と合わせて信頼区間を出し、履歴に保存する                   … §7.5・§8.1
```

### 5.3 Julius 強制アライメント

#### 何をするのか

**強制アライメント（Forced Alignment）** とは、発話内容（ひらがな読み）が分かっている音声に対して、各音素がどの時刻に発音されているかを特定する処理です。
この結果がなければ「何秒目にどの音節が発音されているか」がわからないため、アクセント評価も長さの評価も口形分析も成立しません。

Julius は HMM（隠れマルコフモデル）の音響モデルと、発話内容だけを受け付ける文法を使って、Viterbi 探索で音声と音素列を最尤対応付けします。
音響モデルは Julius の音素セグメンテーションキットに含まれる `engine/models/hmmdefs_monof_mix16_gid.binhmm`（ファイル名のとおり monophone・16混合・性別非依存）です。
同じフォルダの triphone モデル（`hmmdefs_ptm_gid.binhmm`・`logicalTri`）は使っていません。

#### 実装の流れ

```
test.wav（16kHz・モノラル・16bit）
test.txt（「がっこう」）
  ↓
scripts/segment_julius.pl（core/alignment.py の _run_alignment_process() が perl で起動）
  ├ ひらがな → 音素列に変換（同スクリプト内の yomi2voca）
  │     がっこう → g a q k o u
  ├ 「silB 音素列 silE」だけを受け付ける文法（.dfa）と辞書（.dict）を作る
  ├ julius -h hmmdefs_monof_mix16_gid.binhmm -dfa test.dfa -v test.dict -palign -input file
  │     → test.log（音素ごとの開始・終了フレームと 1フレームあたりの平均対数尤度）
  └ test.log から test.lab（秒）を作る
        開始 = 開始フレーム × 0.01（0 フレーム以外は +0.0125）
        終了 = (終了フレーム + 1) × 0.01 + 0.0125
```

アプリは、**ピッチの対応付けには `.log` のフレーム番号**（`log_load()`）、**モーラの長さ・フォルマントの測定時刻・口形・同期分析には `.lab` の秒**（`lab_load()`）を使います。

`core/alignment.py` は外部プロセスまわりの失敗に次のように備えています。

| 対策 | 内容 |
|------|------|
| 古い結果の削除 | 実行前に前回の `test.lab` / `test.log` を消す（失敗時に前回の結果が返るのを防ぐ） |
| タイムアウト | 30 秒で打ち切り、perl と julius のプロセスツリーごと終了する |
| 再試行 | `.lab` が空だったら 0.6 秒あけて最大3回まで実行する（アンチウイルスの一時的なロックなど） |
| 診断情報 | 失敗時の例外に、ログのエラー行・perl の実行パス・perl の標準出力/標準エラーを含める |
| perl の種類 | Git 同梱の msys perl（`/` 区切り）とネイティブ Windows perl（`\` 区切り）を判別してパス形式を変える |

#### Julius 品質ゲート

`extract_julius_score()` は、`.log` の強制アライメント部にある音素ごとの **1フレームあたりの平均対数尤度**（`n_score`、silB / silE を除く）の平均を返します。

| Julius スコア（1フレームあたり） | 動作 |
|-------------|------------|
| -35 以上 | スコア計算を実行 |
| **-35 未満** | **スコア計算をスキップ・再録音ガイドを表示**（履歴にも保存しない） |

しきい値は `app.py` の `JULIUS_GATE_THRESHOLD` です。以前は -3000 でしたが、これは発話全体の合計スコア（`re-computed AM score`）の桁で、1フレームあたりの値とは単位が違うため**一度も発動していませんでした**。

2026-09-14 に実測した値：

| 音声 | 本数 | 1フレームあたりの平均 |
|------|-----|------|
| 過去にコミットされたお手本（人の録音・合成音声） | 86 | -25.8 〜 -30.3 |
| 生徒の録音 | 2 | -27.9 〜 -29.9 |
| わざと**別の単語の読み**でアライメントしたお手本 | 12 | -27.9 〜 -30.7 |
| 雑音・無音・150Hz の持続音 | 3 | アライメント自体が失敗（別のエラー処理で止まる） |

正しい単語と別の単語の値が重なっているため、**このスコアだけで「別の単語を言った」を見分けることはできません**。-35 は、観測した値より十分低い「明らかに異常な録音」だけを止める安全側の値です。音素ごとの最低値（別の単語 -28.8〜-37.9、生徒の録音で -35.7 の例あり）でも分離できませんでした。

#### 音素とモーラの変換

Julius は**音素**でアライメントしますが、日本語のリズム評価は**モーラ**（拍）単位で行います。`core/alignment.py` の `mora_time()` が変換します。

| ルール | 例 |
|--------|-----|
| 子音 + 直後の母音 → 1モーラ | `g` + `a` → `ga`（が）、`by` + `o:` → `byo:`（びょー） |
| 単独母音 → 1モーラ | `i` → `i`（い） |
| 撥音（ん）→ 1モーラ | `N` |
| 促音（っ）→ 1モーラ | `q` |

モーラのラベルは `core/utils.py` の `romaji_mora_to_kana()` でかなに直して画面に出します（`ko:` → 「こー」）。

#### 長音の書き方による違い

| 読みの書き方 | Julius の音素 | モーラ（`mora_time()`） |
|------------|-------------|------------------|
| がっこー | `g a q k o:` | `ga` `q` `ko:`（長音は1単位） |
| がっこう | `g a q k o u` | `ga` `q` `ko` `u`（「う」が別の単位） |

後者の `o` と `u` の境界には音響的な手がかりがなく、Julius はたいてい片方に最短の 3 フレーム（30ms）だけを割り当てます（例：お手本「がっこう」は `o` 500ms・`u` 30ms、生徒の録音は `o` 160ms・`u` 240ms）。
そのため長さ・母音の評価では、前のモーラと同じ母音をのばしているだけのモーラを1つのまとまりとして扱います（[§6.4](#長音のまとまり)）。アクセント（高さ）はまとめずにモーラごとに見ます。

Julius の単位は実際のモーラ数と一致しないことがあります（「がっこー」は3単位だが4モーラ）。MeCab のアクセント型（実際のモーラで数える）と Julius の単位の数えかたの違いは [§6.3](#基準正解の決め方) で扱います。

## 6. 発音評価（スコアに入るもの）

### 6.1 スコアの全体構成

合計点は、アクセント（50点）・モーラ長（30点）・母音品質（20点）の和です（`core/evaluate.py` の `calc_total_score()`）。

```
accent_raw  … calc_accent_score()  0〜60 の内部スコア
length_raw  … calc_length_score()  0〜40 の内部スコア
vowel_score … calc_vowel_score()   0.5〜20

アクセント点 = min(50, accent_raw × 50/60 + 3.0)
長さ点       = length_raw × 30/40
母音点       = vowel_score
合計点       = min(100, max(0, アクセント点 + 長さ点 + 母音点))   ※ 小数第1位で丸める

グレード：S ≥ 90 ／ A ≥ 75 ／ B ≥ 60 ／ C ≥ 40 ／ D < 40
```

アクセント点の `+3.0` は設計上の底上げで、内部スコアが 0 でも 3.0 点、56.4 以上なら満点 50 点になります（正解データで決めた値ではありません）。

#### 測れないときに使う値

| 状況 | 値 | 合計点での点数 |
|------|----|------------|
| モーラの区切りが無い | accent_raw = 30 | アクセント 28.0 |
| お手本の高さが測れず、アクセント型も不明 | accent_raw = 30 | アクセント 28.0 |
| 学習者の声の高さが測れない（有声フレーム 10 未満） | accent_raw = 0 | アクセント 3.0 |
| 長さのデータが無い | length_raw = 20 | 長さ 15.0 |
| 母音を比べられるモーラが1つも無い | vowel_score = 10.0 | 母音 10.0 |
| フォルマント測定でエラー | vowel_score = 10.0 | 母音 10.0 |

アライメントの品質が低いとき（Julius スコア < -35）は、合計点を出さず、履歴にも保存しません（[§5.3](#julius-品質ゲート)）。

#### 結果画面での見せ方

- 合計点とグレード、3軸の達成率（アクセント点/50、長さ点/30、母音点/20）を ◎（80% 以上）・○（55% 以上）・△ で示す
- 「つぎは、ここだけ」：モーラ別スコア（[§6.6](#66-モーラ別スコア音ごとのできばえ)）の合計がいちばん低いモーラが 75 未満のとき、そのモーラの3軸のうち最も低い軸（口の形 → 長さ → 高さの順に同点を優先）を1つだけ示す
- フィードバック文（[§6.7](#67-フィードバック文の選び方)）は、先生モードのときだけ開ける「くわしい分析（先生・研究用）」の中に表示する（生徒の画面の主役は ◎○△ と「つぎは、ここだけ」）

### 6.2 ピッチの抽出と前処理

アクセント評価とモーラ別の「高さ」は、お手本と録音のピッチを次の手順で揃えてから比べます（`core/pitch.py`、`app.py` `audio_analysis()`）。

| 順 | 処理 | 関数 | 内容 |
|----|------|------|------|
| 1 | 声の高さの範囲を推定 | `estimate_pitch_range()` | Praat の自己相関法（50〜700Hz）で一度測り、有声フレームの P10 × 0.75 を下限、P90 × 1.5 を上限にする（50Hz 以上・700Hz 以下）。有声フレームが 10 未満などのときは 70〜400Hz |
| 2 | ピッチ（F0）を測る | `praat_pitch()` | Praat `To Pitch (ac)`（下限・上限は 1 の値、silence threshold 0.01、voicing threshold 0.3、時間刻みは Praat の既定）。無声フレームは NaN |
| 3 | 10ms に揃える | `resample_to_10ms()` | Julius のフレーム（10ms）と同じ格子へ線形補間する。格子点に最も近い元のフレームが無声なら NaN のまま |
| 4 | 発話区間を切り出す | — | `.log` の最初の音素の開始フレーム〜最後の音素の終了フレーム（silB / silE を除く） |
| 5 | 時間正規化（録音のみ） | `length_arrange()` | 録音のピッチを、音素ごとにお手本のフレーム数へ線形補間でリサンプリングする（両隣が無声のフレームだけ NaN）。これでお手本と録音が同じ時間軸に並ぶ |
| 6 | 半音に変換 | `hz_to_semitone()` | `12 × log2(F / F_ref)`。`F_ref` はその話者の有声フレームの中央値（話者ごと） |

ここから2種類の配列を作ります。

| 配列 | 作り方 | 使い道 |
|------|--------|--------|
| NaN を保持した半音配列（`pitch_native_raw` / `pitch_user_raw`） | 6 の結果そのまま | モーラの高さ、ピッチ相関、安定度、平坦ゲート、有声率 |
| 補間・平滑化した配列（`pitch_fin` / `pitch_fin2`） | `comp()`（内部の NaN を線形補間、端の NaN は最寄りの値で埋める。全区間 NaN なら 0）→ `smooth(window=3)`（30ms 移動平均） | モーラ別「高さ」の比較、NaN 保持配列が無い呼び出し元の代わり |
| グラフ表示用 | `comp()` → `smooth(window=5)` → 0〜1 の min-max 正規化 | 結果画面のグラフのみ |

半音に変換するのは、Hz のままだと声域の違い（男性と女性など）がそのまま差として出るためです。対数スケールにして話者の中央値を 0 に揃えると、「どれだけ上がり、どれだけ下がったか」を話者によらず比べられます。

モーラの区間は、**お手本の `.log` のモーラ開始フレーム**（発話区間の先頭を 0 とした相対値）を、お手本と録音の両方に使います。5 で録音をお手本の時間軸に揃えているためです。

### 6.3 アクセント評価 — 50点

#### 背景

日本語のアクセントは音の高低による**ピッチアクセント**で、単語ごとに H（高）/ L（低）のパターンがあり、音が下がる位置（アクセント核）が意味の区別に関わります（例：「あめ（雨）」H-L と「あめ（飴）」L-H）。
本システムでは、お手本の録音から得た高低の形に、学習者の形がどれだけ近いかを4つの指標で評価します（`core/evaluate.py` の `calc_accent_score()`）。

#### アクセントのスコア計算

```
内部スコア（0〜60）=
  核位置スコア     × 0.40
+ ピッチ相関スコア × 0.28
+ H/L 一致率スコア × 0.22
+ 安定度スコア     × 0.10
```

ピッチ相関か安定度が計算できないときは、残りの指標で次の重みにします。

| 使える指標 | 重み |
|-----------|------|
| 4つすべて | 核 0.40 ／ 相関 0.28 ／ H/L 0.22 ／ 安定度 0.10 |
| 安定度なし | 核 0.45 ／ 相関 0.40 ／ H/L 0.15 |
| 相関なし | 核 0.50 ／ H/L 0.35 ／ 安定度 0.15 |
| 核と H/L のみ | 核 0.60 ／ H/L 0.40 |

重みは設計上の値で、正解データによる最適化はしていません。

#### 基準（正解）の決め方

**お手本の録音の高さの形を正解にします**（MeCab のアクセント型より優先）。DB に入っているアクセント型がお手本と違っていても、お手本どおりに言えば高く評価されます。

| 条件 | 基準の作り方 |
|------|------------|
| お手本の高さを測れる・アクセント型あり | お手本の各モーラの高さを H/L に分ける。H と L の数だけアクセント型から決める |
| お手本の高さを測れる・**アクセント型が不明** | お手本から検出した核の位置で H と L の数を決める |
| お手本の高さを測れない・アクセント型あり | アクセント型の H/L パターンそのものと比べる |
| どちらも無い | 評価できない（内部スコア 30） |

「お手本の高さを測れる」は、高さを測れたモーラが2つ以上あることです。

> **アクセント型とモーラ数の数え方の違い：** MeCab のアクセント型は実際のモーラで数えますが、評価は Julius の単位（[§5.3](#長音の書き方による違い)）で行います。「しょーめーしょ」のように長音を「ー」で書いた単語では単位の数が実際のモーラより少なくなり、アクセント型から作る H と L の数がずれることがあります。

#### モーラの高さ

各モーラの高さは、NaN を保持した半音配列の**有声フレームの中央値**です。有声フレームが 3 未満、またはモーラのフレーム数の 30% 未満のモーラ（「っ」や無声化した母音など）は「測れない」として、H/L 比較と核の検出から外します。

#### 各指標の詳細

**① 核位置スコア（重み 0.40）**

アクセント核は「音が下がる直前のモーラ」です。隣り合う（測れた）モーラ間でいちばん大きく下がる位置を核とし、下がり幅が **1 半音**（`NUCLEUS_DROP_ST`）未満なら「下がらない（0）」とします。測れないモーラは飛ばして、その前後を隣り合うものとして比べます。

```
核 = いちばん大きく下がる直前のモーラの番号（1始まり）。下がり幅 < 1.0 半音なら 0
核位置スコア = max(0, 60 − |学習者の核 − お手本の核| × 60 / max(モーラ数 + 1, 3))
```

1 半音は設計上の値です。平板型のお手本「がっこう」で測った語中の自然な下がり（約 0.3 半音）を核と数えないように置いています。

> **精度の限界：** アクセント型が分かっている過去のお手本 45 語で、検出した核とアクセント型を突き合わせると、一致は 15 語（しきい値を 0.25〜2.0 半音で変えても 11〜22 語）でした。単語を単独で言うと、平板型でも語末で声が大きく下がる（「やちん」で約 7 半音）ため、それを核と取り違えます。お手本と学習者を**同じ方法で**検出して比べているので形の比較としては働きますが、「何型か」の判定としては信頼できません。

**② ピッチ相関スコア（重み 0.28）**

お手本と学習者のピッチの上下の形を、**両方が有声のフレームだけ**を使った Pearson の相関係数 r で評価します。無声区間の補間値は実際のピッチではないため使いません。

```
score = max(0, (r + 1) / 2 × 60)

両方が有声のフレームが 4 未満 → 30（中間値）
どちらかのピッチが完全に平坦（標準偏差 < 1e-6）→ 9（60 × 0.15）
```

相関は線形変換に不変なので、声の高さや抑揚の大きさが違っても形が同じなら高くなります。

**③ H/L 一致率スコア（重み 0.22）**

お手本と学習者のモーラの高さを、それぞれ「高（H）」「低（L）」に分け、一致した割合を評価します。H と L の数は基準のパターン（上表）の L の割合から決め、**パーセンタイル閾値**で分けます。

```
threshold = percentile(測れたモーラの高さ, L の割合 × 100)
高さ > threshold → H、それ以外 → L

H/L 一致率スコア = 一致率 × 60   （お手本・学習者の両方で測れたモーラだけで数える。1つも無ければ一致率 0.5）
```

例：平板型（L-H-H-H）→ L の割合 25% → 25 パーセンタイルを閾値。学習者の声域に関わらず相対的な高低の並びを比べられます。

**④ 安定度スコア（重み 0.10）**

各モーラ内のピッチの揺れ（分散、半音²）のうち、**お手本より揺れた分**を評価します（`_mora_excess_variances()`）。

```
モーラの揺れ = max(0, 学習者のモーラ内分散 − お手本のモーラ内分散)   … 有声フレーム 3 以上のモーラのみ
安定度スコア = max(0, 60 × (1 − 揺れの平均 / 2.0))                       … 測れるモーラが無ければ 30
```

長音の中で下がる・平板型の1モーラ目から上がる、のようにモーラの中で高さが動くのが正しい発音のこともあるため、お手本と同じ動きは揺れとして数えません。

#### 平坦ゲート

学習者の声の高さがほとんど動いていない場合、パーセンタイル分割の H/L は偶然一致で得点してしまいます。そこで次の条件で「平坦」と判定し、内部スコアの上限を 25 にして専用のフィードバックを返します。

```
学習者の抑揚（有声フレームの P90 − P10） < min(1.5 半音, お手本の抑揚 × 0.5)
（有声フレームが 10 未満の側は抑揚を計算しない。お手本の抑揚が無いときは 1.5 半音だけで判定）
```

お手本自体の抑揚が小さい単語で、お手本どおりに言った学習者を平坦扱いしないよう、お手本の抑揚の半分も条件に入れています（過去のお手本 45 語の抑揚は 1.7〜19.3 半音）。

#### 声が出ていない録音

NaN を保持した録音の半音配列で、有声フレームが 10（100ms）未満なら、内部スコアを 0 にして「声の高さ（ピッチ）を測れませんでした」と返します。
`comp()` は全区間が無声の配列を 0 で埋めて返すため、補間後の配列だけではこの状態を見分けられません。

### 6.4 モーラ長評価 — 30点

#### 背景

日本語は**モーラ拍言語（mora-timed language）** であり、各モーラの持続時間がリズムの基本単位です。特に**長音（ー）・促音（っ）・撥音（ん）** は1モーラ分の長さを持ち、これらを正確に発音しないと意味が変わる場合があります（例：「おばさん（伯母）」と「おばあさん（祖母）」）。

#### 使うデータ

各モーラの長さは `.lab` の区間（秒）から出し、`pct_length()` で**発話全体に占める割合（%）**にしてからお手本と比べます（`core/evaluate.py` の `calc_length_score()`）。割合にするので、全体を速く・遅く言っても点は変わりません。発話全体の速さは表示だけの発話速度（[§7.1](#71-発話速度と声の揺れ)）で見ます。

#### 長音のまとまり

「こう」「せい」の「う」「い」のように、前のモーラの母音をのばしているだけのモーラは、前のモーラと**1つのまとまり（長音）**として比べます（`core/utils.py` の `long_vowel_groups()`）。

| 前のモーラの母音 | 次のモーラ | 例 |
|---|---|---|
| a | あ | おかあさん |
| i | い | おにいさん・かわいい |
| u | う | くうき |
| e | え・い | おねえさん・せんせい |
| o | お・う | とおり・がっこう |

Julius がこの2モーラの間に置く境界には音響的な根拠がないためです（[§5.3](#長音の書き方による違い)）。「おもう」のように長音でない場合もまとまりますが、長さはまとまりの合計で比べるだけなので評価が不当に下がることはありません。

#### 長さのスコア計算

```
重み：
  長音（「ー」を含む単位、または上のまとまり）・促音（q）→ 2.0
  撥音（N）                                          → 1.5
  通常モーラ                                          → 1.0

diff[i]       = |お手本の割合[i] − 学習者の割合[i]|                  … まとまりごと（%）
weighted_diff = Σ(diff[i] × 重み[i]) / Σ(重み[i])
avg_share     = 100 / まとまりの数                                  … 1まとまりあたりの平均の割合
内部スコア   = max(0, (1 − weighted_diff / avg_share) × 40)
長さ点       = 内部スコア × 30 / 40
```

長音・促音に高い重みをかけるのは、これらの誤りが意味の区別に関わりやすいためです（重みの値は設計上のもの）。

`avg_share` で割るのは、まとまりの数によって点の厳しさが変わらないようにするためです。以前の式（`weighted_diff / 25`）は割合の差をそのまま使っていたため、半分のモーラが 20% 長く、残りが 20% 短くなった同じずれ方でも、2モーラの単語は 18.0 点、4モーラは 24.0 点、8モーラは 27.0 点（30点満点）と差が出ていました。いまはどれも 24.0 点です（4まとまりの単語では以前と同じ点）。

#### 長音・促音のチェック（お手本の比率と比べる）

フィードバック用に、長音・促音の「通常モーラの平均長さに対する比」を**お手本の同じ比**と比べます（点数には入りません）。

```
比 = (学習者の長さ / 学習者の通常モーラの平均) ÷ (お手本の長さ / お手本の通常モーラの平均)

長音：比 < 0.75 → 「短すぎます」、比 > 1.6 → 「長すぎます」
促音：比 < 0.6  → 「短すぎます」、比 > 1.8 → 「長すぎます」
```

許容幅は、以前の固定の目安（長音は通常モーラの 1.5〜3.2 倍、促音は 0.6〜1.8 倍）を、それぞれの目安の比（長音 2 倍・促音 1 倍）で割ったものです。
以前は固定の目安で直接判定していましたが、Julius は促音の閉鎖を `q` と次の子音（`k` など）に分けるので `q` の区間は短く出やすく、**お手本を自分自身と比べても「っが短すぎます」と出ていました**（過去のお手本 52 語中 13 語）。

### 6.5 母音品質評価 — 20点

#### 背景

**フォルマント**は声道の共鳴によって生じるスペクトルのピークで、第1フォルマント（F1）は口の開き（舌の高さ）と、第2フォルマント（F2）は舌の前後位置と対応します。F1/F2 の組み合わせが母音を特徴づけます（Peterson & Barney, 1952）。
F1 と F2 では周波数の聞き分けの細かさが違うため、Hz を聴覚の尺度である **Bark** に変換してから比べます（Traunmüller, 1990 の近似式）。

```
Bark = 26.81 × F / (1960 + F) − 0.53
```

#### フォルマントの測定

`core/formant.py` の `extract_mora_formants()` です。

| 項目 | 値 |
|------|----|
| 手法 | Praat `To Formant (burg)` |
| 時間刻み / 窓長 | 5ms / 25ms |
| フォルマント数 | 5 |
| 最大フォルマント周波数 | 声の高さの上限（[§6.2](#62-ピッチの抽出と前処理) の推定値）が 400Hz を超えれば 5500Hz、それ以外は 5000Hz（お手本と録音で別々に決める） |
| プリエンファシス | 50Hz から |
| 測定時刻 | 各モーラの区間の 30% / 50% / 70% の3点 |
| 妥当性フィルタ | 150 ≤ F1 ≤ 1200Hz、400 ≤ F2 ≤ 3500Hz、F2 > F1 + 150Hz を満たす点だけを使う |
| 代表値 | 残った点の F1・F2 それぞれの**中央値** |

1点（中心のみ）だと子音から母音への渡り（例：/k/→/a/ の口の移動中）を拾うことがあるため、3点の中央値で遷移区間や外れ値の影響を抑えます。

「こう」の「う」のような長音の後半（[§6.4](#長音のまとまり)）は、前のモーラと**まとまり全体の区間**で測ります（`core/utils.py` の `long_vowel_spans()`）。お手本「がっこう」の `u` は 30ms しかなく、母音の終わりの崩れた部分（F1 約 900Hz・F2 約 2500Hz）を測っていたためです。

お手本のフォルマントは `data/config/formant_cache.json` にキャッシュします。キーには wav のパス・更新時刻・最大フォルマント周波数・**モーラ区間**を含めます（アライメントだけやり直したときに古い値が返らないように）。

#### 話者差の補正

男性と女性、大人と子どもでは声道の長さが違うため、同じ母音でもフォルマント周波数が違います。`speaker_formant_scale()` がこの録音ペア自体から補正係数を推定し、お手本の F1/F2 にかけてから比べます。

```
係数 = 同じ位置のモーラ同士の F1/F2 の比（学習者 / お手本）の中央値   … 0.80〜1.25 に制限
```

性別の2値判定だと、境界付近の話者で補正が ON/OFF に切り替わってしまうため、連続値にしています。**比が2つ未満しか取れないときだけ**、声の高さから推定した性別で補正します。

| お手本 | 学習者 | 係数（比が足りないときのみ） |
|-----------|--------|---------|
| 同性 | 同性 | 1.0（補正なし） |
| 女性 | 男性 | 0.85 |
| 男性 | 女性 | 1 / 0.85 ≒ 1.18 |

性別は、声の高さの上限の推定値（有声フレームの P90 × 1.5）が **300Hz 以下なら男性**と判定します（P90 が 200Hz 以下に当たる。この 200Hz も設計上の値）。0.85 は、成人男性のフォルマントが成人女性よりおおよそ 1〜2 割低いという報告（Peterson & Barney, 1952 など）を目安にした集団平均的な値で、個人差は吸収できません。

この係数は声道の長さの違いだけでなく、学習者の母音の系統的なずれも一部吸収しうる点に注意してください（中央値なので、1つの母音だけのずれには影響されにくい）。

#### 母音のスコア計算

```
各まとまり（長音はまとまりで1回）について：
  dist = √( ((Bark(お手本F1 × 係数) − Bark(学習者F1)) / 3.0)²
          + ((Bark(お手本F2 × 係数) − Bark(学習者F2)) / 4.0)² )
  重み = min(お手本の有効点数, 学習者の有効点数) / 3      … 3点すべて有効なら 1.0

mean_dist = Σ(dist × 重み) / Σ(重み)
母音点    = 20 × exp(−mean_dist)     … 0.5〜20 に制限（距離がどれだけ大きくても 0 点にはならない）
```

F1 の差を 3、F2 の差を 4 で割る値は設計上のもので、文献や正解データに基づいて決めたものではありません（F2 の差を F1 より小さく見積もる効果があります）。
母音を含まないモーラ（「ん」「っ」）と、F1/F2 のどちらかが測れなかったモーラは除きます。1つも比べられなければ 10.0 点です。

### 6.6 モーラ別スコア（音ごとのできばえ）

結果画面の「音ごとのできばえ」「つぎは、ここだけ」と、苦手な音の分析（[§8.2](#82-苦手な音の分析集中ドリルことば当てクイズ)）は、`calc_mora_scores()` のモーラごとの3軸（各 0〜100）を使います。**合計点とは別に計算しており、合計点には入りません。**

| 軸 | 計算 |
|----|------|
| 高さ（accent） | お手本・学習者のピッチ（`comp` + `smooth(3)` の配列）を、それぞれ「有声フレームの中央値 = 0、P10〜P90 の幅 = 1」に正規化する（幅の下限 3 半音）。そのモーラの**両方が有声のフレーム**での差の絶対値の中央値 d から `100 × exp(−4d)`。両方が有声のフレームが 3 未満、またはモーラの 30% 未満のモーラ（「っ」など）は測らない（None） |
| 長さ（length） | お手本との長さ（割合）の比 r から `100 × exp(−3 × \|1 − r\| × 重み)`（重みは [§6.4](#長さのスコア計算) と同じ）。長音のまとまりはまとめた長さで比べ、両方のモーラに同じ点を付ける |
| 口の形（vowel） | 話者差補正をかけた母音の距離 d（[§6.5](#母音のスコア計算)）から `100 × exp(−d)`。母音を含まないモーラは None |
| 合計（total） | 測れた軸の単純平均 |

「高さ」を以前の 0〜1 の min-max 正規化から変えたのは、抑揚のない声のわずかな揺れが 0〜1 いっぱいに拡大されて高く出たり、1フレームの外れ値（オクターブ誤検出など）で残りが潰れたりしていたためです。幅の下限を 3 半音にしたのは、抑揚の小さい声を大きな動きに見せないためです。

結果画面では、各モーラの3軸のうち最も良い軸が 75 以上なら「◎ その軸」、そうでなければ最も低い軸を「△ その軸」として示します。モーラのラベルは `romaji_mora_to_kana()` でかなにして履歴に保存します（[§11.3](#113-保存されるデータの形式)）。

### 6.7 フィードバック文の選び方

文は1つの軸につき1つだけ、上から順に最初に当てはまったものを出します。音は「2拍目」のような番号ではなく「「こ」」のように名指しします（同じかなが2回出る単語では「3番目の「こ」」）。

**アクセント**（`calc_accent_score()`）

| 順 | 条件 | 文の要旨 |
|----|------|---------|
| 1 | 平坦ゲートにかかった | 声の高さがほぼ一定（変化 ○半音）。高い拍と低い拍の差を大げさにつける練習から |
| 2 | 内部スコア ≥ 48 | アクセントがお手本どおり／（型が分かれば）○○型が正確 |
| 3 | 安定度 < 30 かつ、お手本より揺れた分が 2.0 以上のモーラがある | 「○」のピッチが不安定 |
| 4 | 核の位置が一致し、H/L 一致率 ≥ 0.6 | 核の位置は正しい。上げ下げをより明確に |
| 5 | 核の位置が違う | お手本が平板なら「途中で下げずに高さを保つ」、学習者が下げていなければ「下降が弱い」、早ければ「○まで高く保つ」、遅ければ「○のあとで下げる」 |
| 6 | H/L が逆のモーラがある | 「○」の高低が逆転。お手本のパターン（L H H …）を意識 |
| 7 | それ以外 | お手本の高低の形をもう少し意識 |

**長さ**（`calc_length_score()`）：お手本の比と比べた長音の誤り → 促音の誤り → 割合の差が平均の 16% を超える長音 → 同じく促音 → 全体のずれ（`weighted_diff / avg_share`）が 0.2 未満なら「とても良い」、0.4 未満なら最もずれたまとまりを「少し長い／短い」、それ以上なら「お手本より約○%長い／短い」。

**母音**（`calc_vowel_score()`）：`mean_dist` が 0.3 未満「正確」、0.7 未満「「○」が少しずれている」、1.2 未満「ずれている」、それ以上「大きくずれている」。「○」は距離が最大のまとまり。

**声の弱さ**（`_voiced_ratio_feedback()`）：有声フレームの割合が 45% 未満のモーラのうち最も低いものを「「○」の声が弱すぎます」と出します。**お手本でも 45% 未満のモーラ（「っ」や無声化した母音）は指摘しません。**

## 7. スコアに入らない分析と表示

この章の値はすべて**合計点に入りません**。結果画面の「口と声」タブや「くわしい分析（先生・研究用）」に表示するための参考情報です。

### 7.1 発話速度と声の揺れ

#### 発話速度（`core/evaluate.py` `calc_speaking_rate()`）

```
発話速度 = モーラ数 / 発話時間（秒）
  モーラ数 … mora_time() の単位の数（「ー」を含む長音は1つと数える。[§5.3]）
  発話時間 … .lab の最初の音素の開始 〜 最後の音素の終了（silB / silE を除く）
```

お手本の発話速度に対する比 r で次の文を出します（お手本の値が無いときは 4.0 / 5.5 / 9.0 / 11.0 モーラ/秒を境にする）。

| r | 表示 |
|---|------|
| < 0.70 | お手本より遅すぎる |
| 0.70〜0.85 | 少し遅め |
| 0.85〜1.15 | （表示なし） |
| 1.15〜1.30 | 少し速め |
| > 1.30 | 速すぎる |

長さの点はモーラの長さの**割合**で比べるので、全体の速さの違いは長さの点に入りません。速さはこの表示だけで伝えます。

#### 声の揺れ（`core/formant.py` `calc_voice_quality()`）

録音の発話区間から Praat で周期点列（`To PointProcess (periodic, cc)`、声の高さの範囲は [§6.2](#62-ピッチの抽出と前処理) の推定値）を作り、次を測ります。

| 指標 | Praat のコマンドと引数 | 注意を出す条件 |
|------|----------------------|--------------|
| ジッター（周期のゆらぎ） | `Get jitter (local)` 0, 0, 0.0001, 0.02, 1.3 | > 3.0% で「声のピッチが不安定」 |
| シマー（振幅のゆらぎ） | `Get shimmer (local)` 0, 0, 0.0001, 0.02, 1.3, 1.6 | > 8.0% で「声の音量が不安定」（ジッターの注意が無いとき） |

3.0% / 8.0% は設計上の目安です。単語1つ（1秒程度）の短い発話から測った値なので、声質の評価として使うときは慎重に扱ってください。

### 7.2 口形分析（MediaPipe Face Mesh）

録音と同時に撮った口元の映像を数値化し、お手本と比べます（`app.py`）。MediaPipe Face Mesh（`refine_landmarks=True`、検出・追跡の信頼度 0.5、1人）で顔の 468 点のランドマークを取り出します。

> 学習者の口の動画を撮るのは、**その単語にお手本の口形データがあるとき**だけです（[§5.2](#52-1回の練習で行われる処理)）。

#### 取り出す特徴量（`_extract_lip_data_timed()`）

| 特徴量 | 使うランドマーク | 計算 |
|--------|----------------|------|
| 唇形状ベクトル（20次元） | 唇の輪郭 20 点：61, 146, 91, 181, 84, 17, 314, 405, 321, 375, 291, 185, 40, 39, 37, 0, 267, 269, 270, 409 | 上唇内側（13）と下唇内側（14）の中点から各点までの距離を、両目の外側の端（33 と 263）の距離で割る（顔の大きさ・カメラとの距離の影響を除く） |
| 口の開き v_h_ratio | 13（上唇内側）・14（下唇内側）・61（左口角）・291（右口角） | `v_dist(13–14) / h_dist(61–291)`。大きいほど縦に開いている（/a/ 寄り）、小さいほど横に細い（/i/ 寄り） |
| フレーム時刻 | — | `フレーム番号 / fps`（fps が取れないか 120 を超えるときは 30。WebM では `CAP_PROP_POS_MSEC` が信頼できないため） |

顔を検出できなかったフレームは飛ばします（そのため時刻を明示的に記録します）。
**顔を検出できたフレームが 50 に達した時点で読み取りをやめます**（読み込んだフレームが 500 を超えたときも打ち切り）。30fps なら録画の先頭からおよそ 1.7 秒ぶんで、これより後ろの口の動きは唇スコアとクロスチェックに入りません（[§17](#17-既知の限界と今後の課題)）。

#### 唇スコア（`_compute_lip_score()`）

お手本と学習者の唇形状ベクトル列を fastdtw（ユークリッド距離）で対応付け、1ステップあたりの距離から点数にします。

```
d = DTW 距離 / 経路の長さ
唇スコア = clip(round(100 − d × 200), 0, 100)
（目安：d = 0.05 ほぼ一致 / 0.15 近い / 0.3 以上 大きく異なる。いずれも設計上の目安）
```

#### モーラごとの口の開き（`_extract_mora_lip_openness()`・`_build_lip_mora_comparison()`）

Julius アライメントのモーラ区間（秒）の **30% / 50% / 70%** の時刻に最も近いフレームの v_h_ratio を平均して、そのモーラの口の開きとします。
すでに取り出したフレーム（上の 50 フレーム）の範囲内ならその値を使い、範囲より後ろの時刻だけ動画をもう一度読んで補います（動画の最後を超える時刻は最後のフレームで代用）。

**お手本の口形データ（モーラごと）がある場合**は、同じ位置のモーラ同士を比べます。

```
正規化：各 v_h_ratio を、その人の全モーラの 95 パーセンタイルで割る（上限 1.5）
         … max() ではなく 95 パーセンタイルにして、瞬間的な外れ値（まばたき・顔の向き）の影響を減らす
判定  ：|学習者 − お手本| < 0.15 → 「良好」
         学習者 < お手本            → 「開きが足りない」
         学習者 > お手本            → 「開きすぎ」
```

**お手本のモーラごとのデータが無い場合**は、母音ごとの目安の開き（`_VOWEL_OPENNESS`：あ 1.0、え 0.55、お 0.45、い 0.15、う 0.10）を期待値にして同じ判定をします。この目安は設計上の値です。

#### お手本の口形データ（`data/config/lip_refs.json`）

```json
{
  "word54": {
    "schema_version": 2,
    "vectors":   [[0.31, 0.28, ...], ...],   ← 唇形状ベクトル（20次元 × 最大50フレーム）
    "ratios":    [0.13, 0.12, ...],           ← v_h_ratio の列（グラフ表示用）
    "times":     [0.0, 0.033, ...],           ← 各フレームの時刻（秒）
    "mora_data": [
      {"label": "ga", "v_h_ratio": 0.127},   ← モーラごとの口の開き（Julius アライメント由来）
      {"label": "q",  "v_h_ratio": 0.081},
      {"label": "ko", "v_h_ratio": 0.175},
      {"label": "u",  "v_h_ratio": 0.012}
    ]
  }
}
```

古い登録では `times` や `mora_data` が無いことがあります（`times` が無いときはクロスチェックで 30fps を仮定、`mora_data` が無いときは母音ごとの目安と比較）。

#### お手本動画そのものの保存・再生

登録時に録画した WebM 動画は `data/raw_audio/sound/{word_id}/{word_id}.webm` に保存され、`/sample_video/<word_id>` から配信されます。録音ページの「お手本を見る」、母音トレーナー、ことば当てクイズ（口の動きで当てる）で使います。

#### MediaPipe が使えない環境では

`mediapipe` / `opencv-python` が import できないと `MEDIA_PIPE_AVAILABLE = False` になり、唇スコア・口の開き・クロスチェックは計算されません（該当の表示が出ないだけで、採点は通常どおり行われます）。

### 7.3 音映像クロスチェック（口と声の同期）

#### 概要

**スコアには影響せず、表示のみ**（試験運用中）の機能です。「声から見つけた発音の瞬間」と
「口の動きから見つけた発音の瞬間」が一致するかを照合し、**声と口のタイミングのズレ**を
モーラごとにミリ秒で算出します。実装は `core/sync.py`。

聴覚に障害のある方は自分の声を聞いてタイミングを合わせることが難しく、
口の形は正しいのに声のタイミングだけがズレるケースがあります。
従来の3軸スコア（アクセント・長さ・母音）と唇スコアはこのズレを見逃すため、
それを補う指標として追加しました。

#### アイデアの出典

指導教員からの提案：お手本とユーザーの「音声同士の対応」と「映像同士の対応」という
2本の独立した対応線が同じ場所を指していれば、その発音は音・口の形・タイミングの
すべてが合っていると判断できる、という発想。

#### 2本の対応線

| 対応線 | 求め方 | 備考 |
|--------|-------|------|
| **声の対応線** | Julius 強制アライメントのモーラ境界（各録音の `.lab`、秒） | 同じモーラ同士が対応するという事実を使うため、生波形 DTW より頑健 |
| **映像の対応線** | 唇形状ベクトル列同士の `fastdtw` 経路 | 20次元 × フレーム数のベクトル列を DTW で対応づける |

#### 技術的な壁と3ステップの橋渡し

音声と映像では時間の測り方の細かさが違います（音声のフレーム周期は 10ms、映像は 30fps ＝
約 33ms/フレーム）。そのまま比較できないため、次の3ステップで時刻を橋渡しします。

```
① 口の動きどうしを比べて対応表を作る
     お手本の映像フレーム i ↔ ユーザーの映像フレーム j の対応（DTW 経路）

② 声の時刻を、その対応表で映像の時刻に変換する
     お手本のモーラ中心時刻
       → 最も近いお手本映像フレーム
       → (DTW) → ユーザーの映像フレーム
       → ユーザーの映像時刻 t_video

③ 実際の声の時刻と比べる
     t_audio = 音声アライメントが指すユーザーのモーラ中心時刻
     offset_ms = (t_video - t_audio) × 1000
```

#### 指標の読み方

| 指標 | 意味 |
|------|------|
| `offset > 0` | 口の動きが声より**遅れて**現れている |
| `offset < 0` | 口の動きが声より**先行して**いる |
| `median_offset_ms` | 発話全体の系統的なズレ。**録画開始タイミングの機材差も混入するため単体では参考値** |
| `spread_ms` | モーラ間のズレのばらつき（MAD＝中央絶対偏差）。機材差の影響を受けないため、発話内での不同期を測る**主指標** |

中央値ではなく MAD を主指標にしているのは、録画開始のズレ（機材差）が中央値そのものを
汚染してしまうためです。ばらつきであれば、全体が一律にずれていても値が大きくなりません。

#### しきい値の校正（2026-07-03 実施）

実データと合成ズレ注入による自己校正の結果です。

| テスト | 結果 |
|--------|------|
| 自己一致（測定ノイズ床） | spread 2〜9ms / median ±11ms |
| 一様ズレ注入 50 / 100 / 200ms | median が -61 / -111 / -211ms とほぼ線形に回復 |
| テンポ 1.5 倍（ズレなし） | spread 8ms → **誤検知しない** |
| 同話者・同単語の別テイク | spread 27〜83ms |
| 発話後半のみ +150ms の局所ズレ | spread 75ms |

```python
SYNC_OK_MS   = 70.0    # spread < 70ms       → ok
SYNC_WARN_MS = 140.0   # 70ms 〜 140ms       → warn
                       # 140ms 以上          → ng
```

#### 結果画面での表示

結果画面（生徒向けの本文）に「口と声のタイミング」カードとして出します。中身は3段です。

1. **判定** — そろっている / 少しばらついている / ずれている（`verdict`）
2. **ばらつきメーター** — `spread_ms` の数値と、校正済みしきい値のバンド（0–70 / 70–140 / 140ms 以上）上の位置。
   判定の根拠がその場で分かるようにしています。一律のズレ（`median_offset_ms`）は録画開始のタイミング差を含むため
   判定には使っていないことも、ここに明記しています
3. **モーラごとのズレ** — 中央＝声と同時、右＝口が遅い、左＝口が先の帯。色はズレの大きさ（30ms 未満 / 80ms 未満 / それ以上）

対応線グラフは、このカード内の「グラフで見る（声と口の位置・モーラごとのずれ）」を開くと表示されます
（X 軸＝ユーザーの時間、Y 軸＝お手本の時間）。2本の線を重ねて描画します。

- **青の実線**：口の動きの対応線（映像 DTW）
- **緑の破線**：声の対応線（音声アライメント）
- **● 緑の点**：声から特定した位置 / **◆ 青の点**：口の動きから予測した位置
- 同じモーラの2点を結ぶ線がそのモーラのズレそのもので、**線が短いほど同期**している
- ズレが 70ms 以上の箇所はオレンジで強調し、かなラベルと ±ms を併記

グラフは無音区間を除いた発話区間（前後 10% の余白つき）に絞って描画します。
映像 DTW 経路は録画全体を通っているため、絞らないとグラフの大半が無音区間の
「意味のない直線」で埋まってしまうためです。

#### 重要な限界

1. `median_offset_ms` はユーザーの音声と映像の**録画開始タイミング差（機材差）を含む**ため、
   単体では発音の良し悪しを断定できません。主指標は `spread_ms` です。
2. この指標が測るのは**タイミングの同期だけ**です。全く別の単語を発音しても、
   タイミングさえ揃っていれば `ok` になり得ます（校正テストで確認済み）。
   口の形の正しさは唇スコア・母音スコアが担当するため、**必ずそれらと並べて表示**しています。
3. 現状はスコアに反映していません（表示のみ）。実運用での判定基準は今後検証します。
4. 唇形状ベクトルは録画の先頭から顔を検出できた 50 フレーム（30fps でおよそ 1.7 秒）までしか取り出していません（[§7.2](#72-口形分析mediapipe-face-mesh)）。これより後ろにあるモーラの中心時刻は、いちばん近い（最後の）フレームに寄せられるため、発話の開始が遅い録画や長い単語ではズレが正しく測れない可能性があります（未検証）。

### 7.4 音色評価（MFCC + DTW）

#### 概要

「録音の音色（スペクトルの時間変化）が、登録済みのどの単語のお手本に近いか」を並べて表示します（`core/timbre.py`）。練習した単語のお手本がいちばん近ければ、別の単語に聞こえる発音にはなっていない、という目安です。

#### MFCC（メル周波数ケプストラム係数）

```
librosa.feature.mfcc(n_mfcc=13, n_fft=512, hop_length=160)   … 16kHz なら窓 32ms・刻み 10ms
0 次の係数（エネルギー）を除いた 12 次元 + Δ（12） + ΔΔ（12）= 36 次元
```

| 次元 | 種類 | 意味 |
|------|------|------|
| 1〜12 | 静的 MFCC | その瞬間のスペクトル包絡 |
| 13〜24 | Δ MFCC（1階差分） | 変化の速さ |
| 25〜36 | ΔΔ MFCC（2階差分） | 変化の加速度 |

お手本の MFCC は登録時に `data/mfcc/{word_id}.bin`（float32、36次元 × フレーム数）として保存します。

#### DTW（動的時間伸縮法）

2つの時系列を、時間の伸び縮みを許して最も近くなるように対応付ける方法です。発話速度の違いを吸収しながら距離を計算します。

```python
distance, _ = fastdtw(mfcc_録音, mfcc_お手本, dist=euclidean)
normalized_distance = distance / (len(mfcc_録音) + len(mfcc_お手本))
```

累積距離は音声の長さに比例して大きくなるため、両方のフレーム数の和で割ります。
録音は発話区間（前後 100ms 付き、`data/raw_audio/test2.wav`）を使い、`words_db.json` の全単語と比べて距離が小さい順に上位 20 語（練習した単語が入らなければ末尾に追加）を表示します。

#### グラフの見方

```
赤いバー ：今回練習した単語
青いバー ：その他の単語
バーが短い（距離が小さい）→ 音色が近い
```

### 7.5 スコアの信頼区間（ブートストラップ法）

#### 背景

1回の録音の点数は、その日の調子・録音環境・偶然に左右されます。同じ単語を3回以上録音していれば、**ブートストラップ法**（Efron & Tibshirani, 1993）で平均点の信頼区間を推定し、「68〜76点」のように幅で示します（`core/confidence.py`）。

#### アルゴリズム

```
対象 = この単語の過去の合計点 + 今回の合計点（N 個）
1. N 個から N 個を復元抽出し、平均を記録する
2. 1 を 2000 回繰り返す
3. 2000 個の平均の 2.5 〜 97.5 パーセンタイルを 95% 信頼区間とする（0〜100 に切り詰め）
標準誤差 = 2000 個の平均の標準偏差
```

| 録音回数 | 表示 | 信頼性の表示 |
|--------|------|-----------|
| 1〜2回 | 「あと○回録音すると信頼区間が計算できます」 | — |
| 3〜4回 | 区間を表示 | low |
| 5〜9回 | 区間を表示 | medium |
| 10回以上 | 区間を表示 | high |

区間は「その単語の平均点がどの範囲にありそうか」を表します。練習で上達している途中の点数を1つの分布とみなして計算しているため、上達の速い時期は幅が広く出ます。
2026-09-14 の評価ロジックの見直し（[§6.8](#68-評価ロジックの見直し2026-09-14)）の前後の点数も区別せずに混ざる点に注意してください。

### 8.2 苦手な音の分析・集中ドリル・ことば当てクイズ

#### 苦手な音の分析（`core/weakness.py` `get_weak_sounds()`）

履歴に保存したモーラ別スコア（[§6.6](#66-モーラ別スコア音ごとのできばえ)）を**かな単位で集計**し、繰り返し点数が低い音を並べます（ELSA Speak 等の「弱点の音の特定 → 集中練習」と同じ発想）。

```
対象   … 直近 60 回の記録に含まれるモーラ（「ん」「っ」「ー」は除く）
条件   … 2回以上出てきて、合計（total）の平均が 70 点未満
並び   … 平均の低い順
弱い軸 … 高さ・長さ・口の形のうち平均が最も低い軸（worst_axis）
```

「こう」の「う」のような長音の後半も「う」として数えます（長さと口の形はまとまりの点、高さは測らない）。

#### 集中ドリル（`core/drill.py` `get_drill_data()`、`/sound_drill/<kana>`）

言語聴覚士の構音指導で一般的な「音単独 → 音節 → 語頭 → 語中・語尾 → 単語」の順序を参考に、4段階（音だけ → のばす → ことばの先頭 → ことばの中）で練習します。

- 行ごとの構音のヒント（か行なら「舌の奥を上あごの奥につけて…」）を表示する
- 読みの先頭にその音がある単語（最大4語）と、途中・末尾にある単語（最大4語）を練習用に選ぶ
- 直近 30 回の記録でのその音の平均点を表示する

#### ことば当てクイズ（`core/drill.py` `build_listening_quiz()`、`/listening_quiz`）

- お手本の音声がある単語から出題し、1回に 8 問（画面側 `PER_ROUND`）を出す
- 選択肢は3つ。正解以外は、**読みの編集距離（レーベンシュタイン距離）が近い順**に選ぶ（びょういん／びよういん のような似た語を優先。同じ読み・同じ表記の単語は除く）
- 先生のお手本録画がある単語には動画を付け、「口の動きで当てる（音なし）」「口の動きと音で当てる」「音で当てる」を選べる

### 8.4 学習曲線分析

練習履歴に線形回帰を当てはめ、上達の速さや停滞を集計します（`core/analysis.py` `compute_learning_stats()`、記録ページの「分析」タブ）。削除済みの単語は集計から除きます。

| 分析 | 手法 | 条件・定義 |
|------|------|----------|
| 上達速度 | `scipy.stats.linregress`（x = 練習回数、y = 合計点） | 単語ごとに3回以上。傾き（点/回）・切片・r・R² |
| 停滞（プラトー） | 直近 10 回（5回以上あるとき）の回帰の傾き | \|傾き\| < 0.3 点/回 |

| アクセント型ごとの上達 | 型ごとの傾きの平均・中央値、S 到達率 | S 到達率＝その型の単語のうち自己ベストが 90 点以上の割合 |
| S ランク到達回数 | 単語ごとに初めて 90 点以上になった練習回数 | 平均・中央値・最少・最多・分布 |
| 全体の推移 | 全記録の合計点の 5 回移動平均 | — |

画面では、研究用の指標を生徒の言葉に置きかえて表示します（「1回練習するごとに平均 +○点」など）。練習が5回未満のあいだは分析を出しません。

### 8.5 母音トレーナー（ブラウザ内の口の形判定）

`/vowel_trainer/<word_id>` は、単語の母音ごとに口の形を作って保つ練習です。**判定はすべてブラウザ内**（MediaPipe Face Mesh の JavaScript 版）で行い、映像はサーバーに送りません（`web/templates/vowel_trainer.html`）。

| 項目 | 内容 |
|------|------|
| 特徴量 | 口の高さ h（13–14、82–87、312–317 の3組の縦方向の差の平均）、口の幅 w（61–291 の横方向の差）、いずれも両目の外側の端（33–263）の距離で割る。唇の突き出し zProt（口角の奥行き − 唇中央の奥行き） |
| 判定 | 母音ごとの中心値（キャリブレーションがあればその人の値、無ければ既定値）に対する h・w のガウス尤度の積が最大の母音。「う」は突き出しが大きいほど尤度を上げる。h < 0.025 は「閉じている」 |
| 平滑化 | 直近 12 フレームの多数決 |
| 合格 | 目標の母音を 1.5 秒保つ |
| キャリブレーション | 「あいうえお」をそれぞれ約 35 フレーム（約1.2秒）保ってもらい、h・w・zProt の中央値を端末（localStorage）に保存 |
| 先生との比較 | お手本の口形データ（[§7.2](#72-口形分析mediapipe-face-mesh)）がある単語では、口の開き v_h_ratio（指数移動平均）を先生の値の 0.72〜1.35 倍の帯と比べ、「閉じ気味／開きすぎ」を示す |

完走すると `/api/vowel_trainer/complete` が今日のレッスンの「口の形」ステップを完了にします。点数は履歴に保存しません。

## 9. 単語登録とお手本データ

### 9.1 登録の流れ

「単語を追加」（先生モード）で、**テキストとお手本録画を1回の `POST /admin/add_word`（multipart）でまとめて**登録します。途中で失敗した単語が残らないようにするためです。

```
POST /admin/add_word（display=表示テキスト, reading=ひらがな読み, file=お手本録画.webm）
  ↓
  1. _webm_to_wav()
     録画した WebM から音声を取り出し、16kHz / モノラル / 16bit PCM に変換（pydub + FFmpeg）

  2. register_word(display, reading, wav_path)            … core/vocab.py
     ├ get_next_word_id() … これまでに使われた最大の ID + 1（§9.4）
     ├ get_accent(display) … MeCab + UniDic でアクセント型を取得（§9.2）
     ├ data/raw_audio/sound/{word_id}/ に {word_id}.txt（読み）と {word_id}.wav を置く
     ├ run_alignment_on_file() … Julius で .lab・.log を作る（§5.3）
     ├ audio_mfcc() … MFCC（36次元）を data/mfcc/{word_id}.bin に保存（§7.4）
     └ words_db.json に追記し、audio.scp・words.txt を作り直す

  3. アライメント結果の確認
     .lab が作られなかった（発話を認識できなかった）ら delete_word() で登録ごと取り消し、
     422 と「録り直してください」を返す

  4. _persist_ref_video() … お手本動画を {word_id}.webm として保存

  5. 口形データ（MediaPipe が使えるとき）
     ├ _extract_mora_lip_openness() … .lab のモーラ区間で口の開きを測る
     └ _extract_lip_data_timed()   … 唇形状ベクトル・v_h_ratio・フレーム時刻
     → lip_refs.json に schema_version: 2 で保存（§7.2）
```

`words_db.json` の1単語は `display`（表示）・`reading`（読み）・`accent`（アクセント型、不明なら null）・`accent_source`（`mecab` / `manual` / `unknown`）・`source`（`manual`＝画面から登録、`recorded`＝初期収録）を持ち、メモ（`note`）とタグ（`tags`）を追加できます。
初期収録（`source: "recorded"`）の単語は削除できません。単語を削除すると音声・録画・アライメント・MFCC は消えますが、`lip_refs.json` の口形データは残ります（ID は再利用しないので混ざりません）。

### 9.2 アクセント型の取得（MeCab + UniDic）

`core/accent.py` の `get_accent()` は**表示テキスト**（漢字・カタカナ・ひらがな）を MeCab（UniDic 辞書）で解析し、次の条件でアクセント型を取ります。

- 解析結果が**1語（1形態素）のときだけ**取得する。「高速道路」のように複数の語に分かれる単語は「不明」（null）
- UniDic の素性の 25 番目（0 始まりで 24。アクセント型 aType）の、カンマ区切りの最初の値が数字ならそれを使う
- MeCab か UniDic が使えない環境では常に「不明」

管理画面の単語編集（`/admin/update_word`）でアクセント型に数字を入れると手動の値（`manual`）になり、空欄なら MeCab で取り直します。
アクセント型が不明でも、アクセントはお手本の録音から評価します（[§6.3](#基準正解の決め方)）。

録音ページに出す H/L の図（`_accent_pattern_for_word()`）は、アクセント型と**読みのかなの数**（小さい「ゃゅょ」などを除く。「ー」は1モーラ）から作ります。型が不明な単語では表示しません。

### 9.3 お手本の録り直し

先生モードで、単語カードの「お手本を録り直す」（`POST /api/lip_refs/overwrite`）または録音ページのお手本録画（`POST /upload_lip_video` の `mode=ref`、3秒）から録り直せます。どちらも次を作り直します。

- お手本の音声（`{word_id}.wav`）と動画（`{word_id}.webm`）
- MFCC（`{word_id}.bin`）
- アライメント（`{word_id}.lab` / `.log`）
- 口形データ（`lip_refs.json` の `vectors` / `ratios` / `times` / `mora_data`）

お手本の音声が変わると wav の更新時刻が変わるので、フォルマントのキャッシュと、録音ページのお手本ピッチのキャッシュは自動で作り直されます。
アライメントだけをやり直すときは `python scripts/repair_alignment.py <word_id>` を使います（口形データは作り直しません）。

### 9.4 単語 ID の採番

`get_next_word_id()` は words_db.json に現存する ID だけでなく、`web/static/sample/` と
`data/raw_audio/sound/` に残る痕跡も見て「これまでに一度でも使われた最大 ID + 1」を返します。

これは、単語を全削除した直後に再び `word1` から採番されると、初期データセット由来の
`web/static/sample/word1.wav`（VOICEVOX 合成の「おんど」）が新しい単語のサンプル音声として
誤って再生されてしまうためです。あわせて `/sample_audio` も、実際に録音された音声を
`static/sample` より優先して配信します。

## 10. 参加者アカウントとデータの分離

調査で複数の参加者が同じ環境を使うため、**練習記録を参加者ごとに分けて保存**します。
設計は倫理審査資料 SP-PS に準拠しています。

### アカウントの構造

`data/config/accounts.json` に保存します。

```json
{
  "A01": {
    "user_id":       "A01",
    "password_hash": "scrypt:...",
    "password_set":  true,
    "profile": {
      "grade":         "junior",
      "hearing_level": "moderate"
    },
    "created_at": "2026-08-31T12:00:00",
    "updated_at": "2026-08-31T12:00:00"
  }
}
```

| 項目 | 設計 | 理由 |
|------|------|------|
| `user_id` | **研究者が割り当てる**（`A01` 形式）。本人は自由入力できない | 本人が決めると氏名やあだ名が混入し、データ内に個人を識別できる文字列が残るため（倫理審査資料 §6.1） |
| `password_hash` | 本人が初回ログイン時に設定し、`werkzeug` でハッシュ化 | 平文では保持しない（倫理審査資料 §6.1） |
| `grade` | 学部単位（`junior` 中学部 / `senior` 高等部）に丸める | 「学校名 ＋ 学年 ＋ 障害の程度」の組み合わせによる再識別を防ぐ（倫理審査資料 §5.3） |
| `hearing_level` | 区分（`mild` / `moderate` / `severe` / `profound`）で保持し、dB 値は持たない | **要配慮個人情報**にあたるため（倫理審査資料 §5.2） |

`grade` と `hearing_level` は調査票由来のため、**研究者のみが管理画面から入力・変更**します。
参加者が初回ログインで設定するのはパスワードだけです。

> **要確認：** 倫理審査資料 §5.3 は聴覚障害の程度を「2〜3区分に集約して保持する」としていますが、実装（`core/accounts.py` の `HEARING_LEVEL_LABELS`）は 軽度・中等度・高度・重度 の4区分と「未回答」です。運用前に、資料か実装のどちらかに揃えてください。

### ログインの流れ

```
/login  ── ID + パスワードを送信
   │
   ├─ パスワード未設定（初回）─→ /first_login へ転送し、本人がパスワードを決める
   ├─ 認証成功 ─→ session["user_id"] に保存 → /select へ
   └─ 認証失敗 ─→ 401 とエラーメッセージ（ID の誤りかパスワードの誤りかは区別しない）
```

### リクエスト単位でのデータ切り替え

`core/history.py` や `core/lesson.py` は Flask のリクエストコンテキストを持たない
純粋なライブラリ層で、`session` を直接読めません。そこで薄い仲介役
`core/usercontext.py` を挟んでいます。

```
app.py の before_request
   └→ usercontext.set_current_user(session["user_id"])
          │
          ├→ history.history_path()  → data/users/<ID>/history.json
          └→ lesson の進捗ファイル    → data/users/<ID>/daily_lesson.json

app.py の teardown_request
   └→ usercontext.clear()   ← スレッド再利用で次のリクエストへ ID が漏れるのを防ぐ
```

未ログイン時や CLI スクリプト（`diagnose.py` 等）では `current_user()` が `None` を返し、
従来の共有パス（`data/config/history.json`）にフォールバックします。

### 認証の適用範囲

`before_request` で全リクエストを検査し、未ログインなら以下のように扱います。

| 対象 | 未ログイン時の挙動 |
|------|------------------|
| 通常のページ（GET） | `/login` へ転送 |
| `/api/` 配下・POST 等 | `401` と JSON エラーを返す |
| `/login` `/first_login` `/logout` `/teacher`・静的ファイル | 認証免除（そのまま処理） |
| **`/admin` 配下** | 参加者ログインではなく**先生モード**が必要（下記） |

セッションに残っている ID のアカウントが削除済みだった場合（参加撤回など）は、
セッションを破棄して `/login` へ戻します。

### 先生モード（先生だけの操作）

単語やお手本、参加者アカウントを変える操作は、生徒の端末から行われると練習の土台が壊れます。
ボタンを隠すだけでは URL を直接開けば使えてしまうため、**先生用パスワードで ON にしたセッション**でだけ受け付けます（`core/teacher.py`）。

| 対象 | 先生モードでないとき |
|------|------------------|
| `/admin` 配下（単語の追加・編集・削除、単語管理画面、参加者アカウント管理） | ページは `/teacher`（先生用パスワードの画面）へ転送、それ以外は `403` |
| `POST /api/lip_refs/overwrite`・`POST /api/lip_refs/delete`（お手本の録り直し・削除） | `403` |
| `POST /upload_lip_video` の `mode=ref`（録音画面からのお手本録画） | `403`（生徒自身の録画 `mode=test` はそのまま） |

- 先生用パスワードは `python scripts/set_teacher_password.py` で設定し、ハッシュだけを `data/config/teacher.json` に保存します。環境変数 `SP_PS_TEACHER_PASSWORD` があればそちらを優先します。どちらも無いときは誰も先生モードにできません
- 先生モードの期限（`session["teacher_until"]`）は、最後に先生の操作をしてから60分。ログアウト・ログインでも消えます
- 同じ接続元から5回続けて間違えると、60秒は受け付けません（総当たり対策）
- 画面の出し分けは、サーバーが `<html class="teacher-mode">` を付けて行います（以前は端末の保存値で決めていたため、生徒が設定から ON にできました）
- 最初の参加者アカウントを作る前にも使えるよう、`/admin` 配下は参加者ログインを求めません

> **セッションの署名鍵：** ログイン状態と先生モードは、署名つきのセッション Cookie に入っています。
> 環境変数 `FLASK_SECRET_KEY` が無いときは、ランダムな鍵を作って `data/config/flask_secret_key.txt` に保存します
> （以前は固定の文字列が既定値で、鍵を知っていれば Cookie を偽造できました）。
> この鍵を消す・変えると、全員がログインし直しになります。

| 2026-09-14 | Julius スコアの分布（お手本 86 本、生徒 2 本、別の単語の読み 12 本、雑音 3 本） | 別の単語を言ったかは見分けられない | §5.3 |
| 2026-09-14 | アクセント核の検出とアクセント型の一致（お手本 45 語） | 15 / 45（しきい値を変えても 11〜22） | §6.3 |

使ったお手本は、過去にコミットされた人の録音 30 語と合成音声（VOICEVOX）22 語、および現在の先生の録音です。生徒の録音は数本しかありません。

#### 検証していないこと（論文で主張する前に必要なもの）

- **点数の妥当性**：合計点・3軸・モーラ別スコアが、言語聴覚士や日本語教師などの人の評定と一致するか（相関・一致率）
- **信頼性**：同じ人が同じように発音したときに点数がどれだけぶれるか（再テスト信頼性）
- **重み・しきい値の最適化**：[§11.1](#111-手法とパラメータの一覧) で「設計」とした値すべて
- **対象者での性能**：聴覚に障害のある生徒の録音での、アライメント・ピッチ・フォルマントの測定精度
- **アクセント型の判定**：核の検出は単独発話の語末の下降に弱い（§6.3）
- **口形分析**：唇スコア・口の開きの判定が、人が見た口の形の正しさと一致するか。長い単語での 50 フレームの上限の影響
- **学習効果**：アプリを使った練習で発音が改善するか（本研究の調査の対象）

### 11.3 保存されるデータの形式

#### 練習履歴（`data/users/<利用者ID>/history.json`）

新しい順の配列で、1回の練習が1要素です（最大 500 件）。

```json
{
  "id":           "rec_1789362332123456789",
  "word_id":      "word54",
  "display":      "学校",
  "reading":      "がっこう",
  "timestamp":    "2026-09-14T08:25:13.123456",
  "total":        79.3,
  "accent_score": 38.5,
  "length_score": 26.9,
  "vowel_score":  13.9,
  "grade":        "A",
  "accent_label": "不明",
  "mora_scores": [
    {"kana": "が", "accent": 8.3,  "length": 61.9, "vowel": 94.4, "total": 54.9},
    {"kana": "っ", "accent": null, "length": 18.1, "vowel": null, "total": 18.1},
    {"kana": "こ", "accent": 77.2, "length": 63.9, "vowel": 51.5, "total": 64.2},
    {"kana": "う", "accent": null, "length": 63.9, "vowel": 51.5, "total": 57.7}
  ]
}
```

| フィールド | 意味 |
|-----------|------|
| `timestamp` | サーバーの現地時刻（ISO 8601、タイムゾーンなし） |
| `total` / `accent_score` / `length_score` / `vowel_score` | 合計点と3軸（[§6.1](#61-スコアの全体構成)）。0.1 点刻み |
| `accent_label` | 登録されているアクセント型の名前（「平板型」など、不明なら「不明」）。評価の基準はお手本の録音なので、この型と一致するとは限らない |
| `mora_scores` | モーラ別スコア（[§6.6](#66-モーラ別スコア音ごとのできばえ)）。測れない軸は `null` |

記録には**評価ロジックの版は保存していません**。2026-09-14 の見直し（§6.8）の前後を分けるときは `timestamp` で分けてください。
フィードバック文、発話速度、口形分析、クロスチェック、Julius スコアは保存しません（結果画面にだけ出ます）。

#### CSV（`/history/export.csv`）

`日時, 単語ID, 単語, 読み, 合計点, アクセント, 長さ, 母音, グレード`（BOM 付き UTF-8。モーラ別スコアは含みません）

#### そのほか

| ファイル | 形式の説明 |
|---------|----------|
| `data/config/words_db.json` | 単語データベース（§9.1） |
| `data/config/accounts.json` | 参加者アカウント（§10） |
| `data/config/lip_refs.json` | お手本の口形データ（§7.2） |
| `data/raw_audio/sound/<word_id>/<word_id>.lab` | 1行1音素：`開始秒 終了秒 音素`（silB / silE を含む。§5.3） |
| `data/raw_audio/sound/<word_id>/<word_id>.log` | Julius のログ。強制アライメント部に `[開始フレーム 終了フレーム] 1フレームあたり平均対数尤度 音素` |
| `data/mfcc/<word_id>.bin` | float32 のベクトル列（36次元 × フレーム数、ヘッダなし） |
| `data/users/<利用者ID>/daily_lesson.json` | その日のレッスン（`date`・`steps`・`mouth_done`） |

## 14. デプロイ（Docker / Railway）

研究参加者の端末から使うときは、PC で `python app.py` と ngrok（[§4](#スマートフォンで使うngrok)）を使う方法が基本です。クラウドに置くための設定もリポジトリにありますが、**2026-09-14 時点ではクラウド上で採点まで動くことを確認していません**（下の注意を参照）。

### 設定ファイル

| ファイル | 内容 |
|---------|------|
| `Dockerfile` | `python:3.12-slim` に MeCab・FFmpeg を入れ、`pip install -r requirements.txt` と `python -m unidic download` を実行。`gunicorn app:app --workers 1 --timeout 120` を `PORT`（既定 8080）で起動 |
| `railway.toml` | Railway で `Dockerfile` を使ってビルド。ヘルスチェックは `/select`、失敗時は最大3回再起動 |
| `Procfile` | gunicorn の起動コマンド（Heroku 形式） |
| `nixpacks.toml` | Dockerfile を使わず Nixpacks でビルドする場合の設定（apt で MeCab・FFmpeg・**Julius** を入れる） |
| `.dockerignore` | `data/` の利用者データ、`web/static/sample/`、`engine/bin/`（Windows 用 exe）などをイメージに入れない |

ワーカーを1つにしているのは、録音が共有ファイル（`test.wav`・`word_id.txt`）に上書きされる設計のためです（[§5.2](#52-1回の練習で行われる処理)）。

### 環境変数

| 変数 | 用途 | 既定 |
|------|------|------|
| `PORT` | 待ち受けポート | 5000（`python app.py`）/ 8080（Dockerfile） |
| `DATA_DIR` | 利用者データの置き場所（Railway では Volume をマウントした場所、例 `/app_data`） | リポジトリ内の `data/` |
| `FLASK_SECRET_KEY` | セッション Cookie の署名鍵 | 無ければ `DATA_DIR/config/flask_secret_key.txt` に自動生成 |
| `SP_PS_TEACHER_PASSWORD` | 先生用パスワード（ファイルより優先） | 無ければ `DATA_DIR/config/teacher.json` |
| `JULIUS_BIN` | Julius 実行ファイルのパス | 自動検出（[§3 ステップ 3](#ステップ-3--julius-をセットアップ)） |
| `FLASK_ENV` | `development` のときデバッグモード（`python app.py` のみ） | `development` |

### 注意（未解決）

- **`Dockerfile` は Julius を入れていません。** `.dockerignore` で `engine/bin/` も除外しているため、`railway.toml` の設定のままでは Julius が見つからず、録音の解析と単語登録が失敗すると考えられます（未検証）。Linux 用の Julius を入れるか、`nixpacks.toml`（apt で `julius` を入れる）を使う必要があります。
- **お手本フォルマントのキャッシュ**（`core/formant.py` の `_CACHE_PATH`）は `DATA_DIR` を見ず、常にリポジトリ内の `data/config/formant_cache.json` に書きます。Volume に保存されないため、再デプロイのたびに作り直しになります（採点結果は変わりません）。
- 音声・映像は外部のサーバーに送られます。研究データを扱う場合は、倫理審査資料 §4.4 の運用形態との整合を確認してください。

## 15. GitHub での開発方法

### ブランチ戦略

```
main          ← 動作する最新版を常に維持するブランチ
feature/xxx   ← 新機能の開発
fix/xxx       ← バグ修正
refactor/xxx  ← 動作を変えないコード整理
docs/xxx      ← ドキュメントのみの変更
```

**main ブランチには直接コミットしない**のが原則です。必ずブランチを切って作業し、動作確認後に main にマージします。

---

### 開発の基本的な流れ

```bash
# 1. main を最新にする（作業開始前に必ず実行）
git checkout main
git pull origin main

# 2. 作業ブランチを作る
git checkout -b feature/○○○

# 3. コードを変更する
# ... 作業 ...

# 4. 変更をステージング
git add web/templates/history.html core/analysis.py
# ※ git add . は避ける（不要なファイルが混入しやすい）

# 5. コミット（内容を具体的に書く）
git commit -m "feat: 記録・分析ページを2タブ構成に統合"

# 6. リモートにプッシュ
git push origin feature/○○○

# 7. main にマージ
git checkout main
git merge feature/○○○
git push origin main

# 8. 不要になったブランチを削除
git branch -d feature/○○○
git push origin --delete feature/○○○
```

---

### コミットメッセージの書き方

**フォーマット：`種類: 何をしたか（日本語でも OK）`**

| 種類 | 使う場面 | 例 |
|------|---------|-----|
| `feat:` | 新機能を追加した | `feat: 口形分析にモーラ単位比較を追加` |
| `fix:` | バグを修正した | `fix: モーラ別アクセントスコアが0になるバグを修正` |
| `refactor:` | 動作を変えずに整理した | `refactor: evaluate.py のスコア計算を関数化` |
| `docs:` | ドキュメントを更新した | `docs: README にセットアップ手順を追加` |
| `chore:` | 設定やビルドを変更した | `chore: requirements.txt を更新` |

**良いコミットメッセージの例**

```bash
feat: DTW 距離を音声長で正規化して公平に比較できるよう修正
fix: Jinja2 の sort フィルタで None 比較エラーが出る問題を修正
docs: Julius アライメントの仕組みをREADMEに追記
```

**悪いコミットメッセージの例**

```bash
update         # ← 何を更新したか不明
fix bug        # ← どのバグか不明
色々修正した   # ← 内容が不明・後から追いにくい
```

---

### ブランチ命名規則

- すべて小文字・単語はハイフン（`-`）でつなぐ
- 何をするブランチか3〜4単語で表現する

```
feature/lip-ref-alignment       ← 良い
feature/口形アライメント実装    ← 日本語は避ける
feature/fix                     ← 内容が不明
```

---

### やってはいけないこと

| NG 操作 | 理由 |
|---------|------|
| `main` に直接コミット・プッシュ | 変更履歴が追いにくくなる |
| 複数の無関係な変更を1つのブランチに混ぜる | 後から差し戻しが難しくなる |
| `git add .` を使いすぎる | `.env` や大きなバイナリが混入しやすい |
| コミットせずに何日も作業を続ける | 差分が大きくなりすぎてコンフリクトが起きやすい |
| バイナリファイル（.wav, .bin）をコミット | リポジトリが肥大化する（.gitignore で除外済み） |

---

### GitHub に上がらないファイル（.gitignore の設定）

以下のファイルは個人のデータや一時ファイルのため、`.gitignore` で除外されています。

```
data/                           ← ユーザーデータ一式（単語・履歴・お手本・録画）を丸ごと除外
web/static/sample/              ← ブラウザ再生用音声
web/static/distance_result/     ← 音色評価チャート（解析のたびに再生成）
```

`data/` はディレクトリごと除外しています。個別ファイル名を列挙する方式だと、
機能追加で新しいデータファイルが増えたときに `git add -A` で混入する余地があるためです。

**別の PC に引き継ぐ場合は、これらを手動でコピーしてください。**

---

### 便利な git コマンド

```bash
# 現在の状態を確認
git status

# 変更の差分を確認（コミット前に内容を確かめる）
git diff

# コミット履歴を確認
git log --oneline -10

# 特定のファイルの変更履歴を確認
git log --oneline -- core/evaluate.py

# 間違えたコミットを取り消す（まだプッシュしていない場合）
git reset --soft HEAD~1

# ブランチの一覧を確認
git branch -a
```

## 16. よくあるトラブルと対処法

### Julius が見つからない / アライメントが失敗する

```bash
# diagnose.py で Julius のパスを確認
python diagnose.py

# 環境変数で直接指定する場合
$env:JULIUS_BIN = "C:\path\to\julius.exe"   # Windows PowerShell
export JULIUS_BIN="/usr/local/bin/julius"    # Linux/Mac
```

---

### 単語登録で「発音が認識できませんでした」が出る

お手本録画からの Julius アライメントが失敗しています。単語は登録されず取り消されます。
サーバーのコンソールに `[register_word] アライメント失敗 ...` と `[診断情報]` が出るので、
まずそれを確認してください。切り分けは以下の順です。

| 診断情報の内容 | 原因と対処 |
|--------------|-----------|
| `perl stderr` に `'C:' は、内部コマンドまたは...` | Windows のネイティブ perl（Strawberry Perl 等）と msys perl でパス形式の要求が逆。最新版では自動判別するため、**`git pull` で最新化**すれば解消する |
| ログに `WARNING: input too short (0 samples)` | 録音が実質無音。マイクの接続・入力デバイスの選択・ミュート設定を確認する（録画画面の `MIC` バーが反応するか） |
| `Julius 実行ファイルが存在しません` | `engine/bin/julius-4.3.1.exe` がアンチウイルスに隔離・削除された可能性。`git checkout -- engine/bin/julius-4.3.1.exe` で復元する |
| `（ログが空＝julius が起動していない可能性）` | 上記いずれか。`perl実行パス` と `perl stdout/stderr` の行が手がかりになる |

一過性の失敗（アンチウイルスの一瞬のロック等）に備え、結果が空だった場合は
自動的に最大3回まで再試行します。3回とも失敗した場合のみエラーになります。

---

### 解析すると「うまく録音できませんでした」になる

Julius スコア（1フレームあたりの平均対数尤度）が -35 未満だったため、採点をやめています（[§5.3](#julius-品質ゲート)）。
先生モードで結果画面の「先生用：解析データ」を開くと値が見られます。正常な録音は -25〜-31 くらいです。
マイクを近づける・静かな場所で録る・単語を途中で切らずに言う、を試してください。

### アクセント型が「不明」のままになっている

単語を登録したときに MeCab・UniDic が使えなかった単語は、あとで MeCab を入れても `accent` が `null` のままです。

1. `python test_mecab.py` で MeCab が動くか確認する（UniDic が無ければ `python -m unidic download`。Windows で失敗する場合は下の囲み）

「高速道路」のように MeCab で複数の語に分かれる単語は、MeCab では取得できません（[§9.2](#92-アクセント型の取得mecab--unidic)）。手動で型を入れてください。
なお、アクセント型が不明でもアクセントの点はお手本の録音から計算されます（[§6.3](#基準正解の決め方)）。

>

> 部分だけなので、内部関数を直接呼べば取得できます（約 526MB）。
>
> ```bash

### 口形分析の表示が出ない / 映像アップロードが 500 になる

コンソールに次のエラーが出ている場合は、**MediaPipe のバージョンが新しすぎます**。

```
AttributeError: module 'mediapipe' has no attribute 'solutions'
```

MediaPipe は 0.10.30 以降で旧 API（`mp.solutions.face_mesh`）を廃止しましたが、
本アプリはこの API を使っています。**Python 3.12 + `mediapipe==0.10.21`** で動作します。

```bash
python -V                        # 3.12 系であることを確認
pip install "mediapipe==0.10.21"
```

`python -V` が 3.13 の場合、3.13 向けには旧 API を持つ MediaPipe が存在しないため
**Python 3.12 を別途インストール**してください（[§2](#2-動作環境と必要ソフトウェア) 参照）。

エラーが出ていないのに口形の比較が出ない場合は、その単語にお手本の口形データが無い可能性があります（学習者の口の動画は、お手本の口形データがある単語でだけ撮ります）。先生モードでお手本を録り直してください。

### diagnose.py で `[NG]` や `[!!]` が出る

「4. 基準音声ファイルの確認（word1）」「5. .lab ファイルの中身を確認（word1）」は初期データセットの `word1` を、「8. VOICEVOX の確認」は現在使っていない VOICEVOX を調べる古い項目です。単語を新しく登録した環境ではここが `[NG]` / `[!!]` になっても、採点には影響しません。

### ページが 500 エラーになる / グラフが表示されない

練習履歴や単語が空の状態で発生していた不具合は修正済みです（`git pull` で最新化してください）。
それでも発生する場合は、サーバーのコンソールに出る Python のトレースバックを確認してください。

## 17. 既知の限界と今後の課題

### 評価の限界

| 限界 | 詳細 | 将来の改善案 |
|------|------|------------|
| **点数の妥当性が未検証** | 点数が人（言語聴覚士・日本語教師など）の評定と一致するか、同じ人の再録音でどれだけぶれるかを調べていない（[§11.2](#112-検証したことしていないこと)） | 評定つきの録音を集めて相関・一致率・再テスト信頼性を測る |
| **パラメータが未検証** | 重み（0.40 / 0.28 / 0.22 / 0.10）、核の下降しきい値（1 半音）、長音・促音の許容幅、母音距離の正規化（3 / 4）などを正解データで最適化していない | 評価付き録音データを集めてチューニング |
| **参照音声が1本** | 単語ごとに登録された1本の録画が唯一の正解になる。お手本自体の言い方（語末の下がりなど）がそのまま基準になる | 複数話者・複数テイクの平均化 |
| **アクセント核の判定精度** | 単独で言った単語は語末で声が下がるため、それを核と取り違える。アクセント型が分かっているお手本 45 語での一致は 15 語（しきい値を変えても 11〜22 語） | 語末の下降を別に扱う・文の中（「〜が」を付けて）で録る |
| **アクセント型と Julius の単位の数え方** | 「ー」で書いた長音は Julius では1単位なので、MeCab の型（実際のモーラで数える）から作る H/L の数がずれることがある | 読みから実際のモーラ位置を対応付ける |
| **Julius スコアで別の単語を見分けられない** | 別の単語の読みでアライメントしても 1フレームあたりの値は -27.9〜-30.7 で、正しい単語（-25.8〜-30.3）と重なる。品質ゲート（-35）は明らかな異常しか止めない | 認識（読みを与えない）結果との照合、音素ごとの尤度の分布の利用 |
| **促音の長さ** | Julius は促音の閉鎖を `q` と次の子音に分けるので、「っ」のモーラの長さは閉鎖の一部だけ。モーラ別の「っ」の長さは低く出やすい | 音素単位で `q` + 次の子音の閉鎖をまとめて測る |
| **長音のまとまりは表記から推定** | 「おう」「えい」などを表記だけで長音とみなすため、「おもう」のような長音でない並びもまとまる | 読みの登録時に長音を「ー」で指定できるようにする |
| **話者差補正の限界** | 補正係数は録音ペアの F1/F2 比の中央値。学習者の母音の系統的なずれも一部吸収しうる。比が足りないときの性別補正（0.85）は集団平均 | 個人単位の話者正規化（VTLN など） |
| **口形分析のフレーム上限** | 唇形状ベクトルは顔を検出できた 50 フレーム（30fps でおよそ 1.7 秒）まで。発話の開始が遅い録画や長い単語では、唇スコアとクロスチェックに後半が入らない | 発話区間に合わせて抽出範囲を決める |
| **クロスチェックが未反映** | 同期のズレを表示するだけで、スコアには反映していない。中央値は録画開始タイミングの機材差を含む | 実運用データで判定基準を検証してから採点へ統合 |
| **録音にノイズ除去をかけていない** | 背景雑音は録音前の注意表示だけで、ピッチ・フォルマントの測定にそのまま影響する | 雑音下での測定精度を調べてから前処理を検討 |
| **過去の記録は再計算していない** | 2026-09-14 の見直し前の点数が履歴に残り、苦手音分析・信頼区間に混ざる。記録に評価ロジックの版を保存していない | 版の番号を記録に保存する・保存済みの録音から再計算する |

### システム・運用の限界

| 限界 | 詳細 | 将来の改善案 |
|------|------|------------|
| **同時に1人しか解析できない** | `test.wav`・`word_id.txt` を全利用者で共有しており、同時に録音すると結果が混ざる | セッション ID でファイルを分ける |
| **クラウドで採点まで動くか未確認** | `Dockerfile` に Julius が入っていない。フォルマントのキャッシュが `DATA_DIR` を見ない（[§14](#14-デプロイdocker--railway)） | Linux 用 Julius の導入、キャッシュを `DATA_DIR` へ |
| **倫理審査資料と実装の区分数** | 資料 §5.3 は聴覚障害の程度を「2〜3区分」とするが、実装は4区分＋未回答（[§10](#10-参加者アカウントとデータの分離)） | 運用前にどちらかに揃える |
| **依存パッケージのバージョンが固定されていない** | `requirements.txt` は MediaPipe 以外を固定していない | 研究で使った環境の `pip freeze` を残す |
| **使われていないコード** | `reduce_noise_wav()`・`word_select()`・`librosa_pitch()`・`normalize_zscore()`、`check.html`・`lip_refs_admin.html`、ルート直下の `compare_lips.py` など | 整理して削除 |

### 解決済みの限界

| 問題 | 対応内容 |
|------|---------|
| ~~話者性別補正なし~~ | 録音ペアのフォルマント比から話者差の補正係数を推定（足りないときは性別で補正） |
| ~~DTW 距離が音声長に依存~~ | `(len(mfcc1) + len(mfcc2))` で正規化 |
| ~~モーラ別アクセントスコアが常に 0~~ | 半音の値を話者ごとに正規化して比較（2026-09-14 に min-max から中央値・P10〜P90 の正規化へ変更） |
| ~~アクセント型が不明な単語のアクセント点が 28.0 に固定~~ | お手本の録音から高低の形を作って評価（[§6.8](#68-評価ロジックの見直し2026-09-14)） |
| ~~Julius 品質ゲートが発動しない~~ | しきい値を 1フレームあたりの値（-35）に修正 |
| ~~お手本を自分自身と比べても満点にならない~~ | 長音・促音をお手本の比率と比べ、「こう」の「う」を前のモーラとまとめて評価（52 語すべて 100 点） |
| ~~長さの点がモーラ数で変わる~~ | 1まとまりあたりの平均の割合で割って点数化 |
| ~~モーラ別の「口の形」に話者差補正なし~~ | 合計の母音点と同じ補正をかける |
| ~~`repair_alignment.py` が起動しない・時刻がずれる~~ | 単語登録と同じ `run_alignment_on_file()` で作り直すように修正 |
| ~~管理機能に認証なし~~ | 先生用パスワードで ON にする先生モードを導入し、サーバー側で確認（[§10](#10-参加者アカウントとデータの分離)） |
| ~~分析ページで Jinja2 クラッシュ~~ | Python 側で事前ソートして渡す方式に変更 |
| ~~単語がテキストだけで登録できてしまう~~ | テキストとお手本録画を1回のリクエストでまとめて登録する方式に変更 |
| ~~アライメント失敗時に空の .lab を持つ単語が残る~~ | 結果の中身を検証し、失敗した登録は自動で取り消す |
| ~~Julius がハングして解析が永久に詰まる~~ | 30秒タイムアウト + プロセスツリーの強制終了 |
| ~~perl の種類でアライメントが失敗する~~ | msys / ネイティブ Windows perl を自動判別してパス形式を切り替え |
| ~~削除した単語の ID が再利用され音声が混線~~ | 過去に使用した ID を避けて採番し、実録音を優先配信 |
| ~~声と口のタイミングのズレを検出できない~~ | 音映像クロスチェック（[§7.3](#73-音映像クロスチェック口と声の同期)）を実装 |
