# SP-PS — 日本語発音練習・評価システム

> 「声（口）のかたちを綺麗にする一歩を踏める嬉しさを届ける」

録音した日本語単語の発音をネイティブ音声（VOICEVOX 合成）と比較し、**アクセント・モーラ長・母音品質の3軸**でスコアを算出してフィードバックを提供する Flask ベースの Web アプリケーションです。Julius 音声認識エンジンによる強制アライメント、MediaPipe FaceMesh による口形分析、スペクトル分析（MFCC + DTW）、学習曲線の統計分析など、音声科学・言語学習研究の知見を実装しています。

## 1. プロジェクト概要

### 何ができるシステムか

SP-PS は、日本語を学ぶ学習者が**自分の発音をネイティブ音声と客観的に比較する**ためのシステムです。

| 機能カテゴリ | 内容 |
|------------|------|
| **発音スコアリング** | アクセント・モーラ長・母音品質の3軸を数値化（100点満点） |
| **口形分析** | MediaPipe で口の縦横比（v_h_ratio）を検出し、お手本との差を可視化 |
| **音色評価** | MFCC + DTW でスペクトルの類似度を評価 |
| **学習分析** | 練習履歴から上達速度・停滞期を統計的に自動検出 |
| **クエスト機能** | 弱点に合わせた練習目標を自動生成・間隔反復で復習提案 |

### 論文・研究での参照について

このシステムは以下の音声科学的手法を実装しています。
各節の「学術的背景」に参照理論と実装の対応を記載しています。

- **強制アライメント**（Julius, HMM-Viterbi）
- **ピッチ分析**（Praat/parselmouth, 半音スケール, Pearson 相関）
- **フォルマント分析**（F1/F2 Bark スケール, Peterson & Barney 1952）
- **スペクトル類似度**（MFCC 36次元, DTW）
- **ブートストラップ統計**（95% 信頼区間推定）
- **学習曲線分析**（線形回帰, プラトー検出）

### 5.2 Julius 強制アライメント

#### 何をするのか

**強制アライメント（Forced Alignment）** とは、既知のテキスト（ひらがな読み）が音声のどのタイムスタンプで発音されているかを特定する処理です。

例えば「びょういん」と録音した音声に対して：

```
0.000〜0.075秒: 無音（silB）
0.075〜0.150秒: 「びょ」
0.150〜0.250秒: 「う」（長音）
0.250〜0.300秒: 「い」
0.300〜0.375秒: 「ん」
0.375〜0.450秒: 無音（silE）
```

というタイムスタンプを出力します。この結果がなければ「何秒目にどの音節が発音されているか」がわからないため、アクセント評価も口形分析も成立しません。

#### 技術的背景

Julius は **HMM（隠れマルコフモデル）** を使った Viterbi アルゴリズムで、入力音声とテキストを最尤対応付けします。音響モデル（`hmmdefs_monof_mix16_gid.binhmm`）は日本語音素を表す HMM のパラメータ集です。

#### 実装の流れ

```
test.wav（録音音声）
test.txt（「びょういん」）
  ↓
scripts/segment_julius.pl
  ├ ひらがな → Julius 音素列に変換
  │   びょういん → "by o: i N"
  ├ Julius を実行（Viterbi アルゴリズム）
  └ test.lab（タイムスタンプ）・test.log（対数尤度）を生成
```

#### Julius 品質ゲート

Julius は発音の品質をスコア（対数尤度）で返します。

| Julius スコア | 状態 | SP-PS の動作 |
|-------------|------|------------|
| -1000 以上 | 良好 | スコア計算を実行 |
| -1000 〜 -3000 | やや不安定 | スコア計算を実行（注意） |
| **-3000 以下** | **不安定** | **スコア計算をスキップ・再録音ガイドを表示** |

対数尤度が極端に低い場合は「マイクに近づく・はっきり発音する・静かな環境で試す」という案内を表示します。ピッチグラフはアライメントと独立して計算されるため引き続き表示されます。

#### 音素とモーラの変換

Julius は**音素**（音声学的最小単位）でアライメントしますが、日本語のリズム評価は**モーラ**（拍）単位で行います。`mora_time()` が変換します。

| ルール | 例 |
|--------|-----|
| 子音 + 直後の母音 → 1モーラ | `by` + `o:` → `びょ（byo:）` |
| 単独母音 → 1モーラ | `i` → `い（i）` |
| 撥音（ん）→ 1モーラ | `N` → `ん（N）` |
| 促音（っ）→ 1モーラ | `q` → `っ（q）` |

### 5.3 アクセント評価（ピッチ分析）— 50点

#### 学術的背景

日本語アクセントは**ピッチアクセント**（音の高低による区別）です。各単語に固有の H（高）/ L（低）パターンがあり、アクセント核（音が下がる位置）が意味の区別に関わります（例：「あめ（雨）」L-H vs「あめ（飴）」H-L）。

本システムでは**半音（semitone）スケール**を使用します。Hz のまま比較すると話者の声域の違い（男性 vs 女性 など）が「誤差」として混入するため、対数スケールである半音に変換して「上下パターン」のみを評価します。

```
半音 = 12 × log2(F / F_ref)
F_ref = 録音区間の有声フレームの中央値（話者ごとに自動設定）
```

#### スコア計算

4つの指標の加重平均で「内部スコア（最大60点）」を算出し、50点満点に正規化します。

```
内部スコア（0〜60）=
  核位置スコア     × 0.40
+ ピッチ相関スコア × 0.35
+ H/L 一致率スコア × 0.15
+ 安定度スコア     × 0.10

アクセントスコア = min(50, 内部スコア × 50/60 + 3.0)
```

#### 各指標の詳細

**① 核位置スコア（重み 0.40）**

アクセント核とは「音が急激に下がる直前の音節」のことです。ネイティブと学習者の核位置が一致しているかを評価します。動的閾値で核を検出します。

```python
DROP_THRESHOLD = max(0.05, min(0.25, ピッチ範囲 × 0.15))
```

ピッチ範囲が狭い（声が単調）場合は閾値を小さく、広い場合は大きくすることで、話者の声域の違いに対応します。

**② ピッチ相関スコア（重み 0.35）**

ネイティブと学習者のピッチの「上下パターンの相関」を Pearson 相関係数で評価します。有声フレーム（NaN でないフレーム）のみを使用します。無声区間の補間値がノイズとして混入しないようにするためです。

```
r = Σ(xi − x̄)(yi − ȳ) / (n × σx × σy)

r = +1.0：ネイティブと同じタイミングで上下（完全一致）
r =  0.0：無相関
r = -1.0：完全に逆パターン

score = max(0, (r + 1) / 2 × 60)
```

DTW からピアソン相関に変えた理由：日本語アクセントの本質は「いつ上がって・いつ下がるか（パターンと方向性）」であり、Pearson 相関はこれを直接測れます。また線形変換不変のため追加の正規化が不要です。

**③ H/L 一致率スコア（重み 0.15）**

各モーラを「高（H）」か「低（L）」に二値化し、ネイティブとの一致率を評価します。アクセント型に応じた**パーセンタイル閾値**を使用します。

```python
threshold = percentile(mora_pitches, L比率 × 100)
```

例：平板型（L-H-H-H）→ L 比率 25% → 25 パーセンタイルを閾値  
こうすることで、学習者の声域に関わらず相対的な高低パターンを評価できます。

**④ 安定度スコア（重み 0.10）**

各モーラ内でのピッチの揺れ（標準偏差）を評価します。値が小さいほど安定した発音です。

#### 時間正規化（length_arrange）

ネイティブと学習者の発話速度が異なるため、ピッチを重ね合わせる前に**モーラ長を揃える**必要があります。

```
例：「か」音素
  ネイティブ：8フレーム
  学習者    ：5フレーム → 末尾に NaN を3つ追加して8フレームに伸張

例：「い」音素
  ネイティブ：6フレーム
  学習者    ：9フレーム → 末尾3フレームを削除して6フレームに短縮
```

#### ピッチ処理パイプライン

```
praat_pitch()              Hz 配列（NaN = 無声区間）
  ↓
resample_to_10ms()         Julius の 10ms フレームに揃える
  ↓
発話区間のみ切り出し（silB〜silE の外を除去）
  ↓
hz_to_semitone()           Hz → 半音変換（NaN 保持）

  ┌────────────────────┐     ┌────────────────────┐
  │   スコア計算用      │     │   グラフ表示用      │
  ├────────────────────┤     ├────────────────────┤
  │ length_arrange()   │     │ comp()  NaN を補間  │
  │ comp()  NaN 補間   │     │ smooth() window=5  │
  │ smooth() window=3  │     │ scale()  0〜1 正規化 │
  └────────────────────┘     └────────────────────┘
```

### 5.4 モーラ長評価 — 30点

#### 学術的背景

日本語は**モーラ拍言語（mora-timed language）**であり、各モーラの持続時間がリズムの基本単位です。特に**長音（ー）・促音（っ）・撥音（ん）** は通常モーラの約2倍の長さを持ちます。これらを正確に発音しないと意味が変わる場合があります（例：「おばさん（伯母）」vs「おばあさん（祖母）」）。

#### スコア計算

各モーラの「全発話時間に占める割合」を計算し、ネイティブとの差を重み付き誤差でスコア化します。

```
モーラ重み：
  長音（ー）・促音（っ）→ 2.0倍
  撥音（ん）           → 1.5倍
  通常モーラ           → 1.0倍

weighted_diff = Σ(|native[i] - user[i]| × weight[i]) / Σ(weight[i])
内部スコア   = max(0, (1.0 - weighted_diff / 25.0) × 40)
長さスコア   = 内部スコア × 30 / 40
```

長音・促音に高い重みをかけるのは、これらの誤りが聞き取りへの影響が大きいためです。

#### 絶対時間チェック

長音・促音については割合比較に加えて「通常モーラの平均長さとの比率」も確認します。

```
長音（ー）の適正範囲：通常モーラ平均の 1.5〜3.0 倍
促音（っ）の適正範囲：通常モーラ平均の 0.6〜1.8 倍
```

この範囲を外れた場合はモーラ別フィードバックに警告を表示します。

### 5.5 母音品質評価（フォルマント分析）— 20点

#### 学術的背景

**フォルマント**（formant）とは、声道の共鳴によって生じる音のスペクトルピークです。第1フォルマント（F1）は口の開き度と相関し、第2フォルマント（F2）は舌の前後位置と相関します。F1/F2 の組み合わせが母音を特徴づけます（Peterson & Barney, 1952）。

**Bark スケール**は Hz を知覚的に均等なスケールに変換したものです。F1（低周波数域）と F2（高周波数域）では人間の知覚感度が異なるため、Hz のまま差を計算すると「聞こえ方の差」を正確に反映できません。

```
Bark = 26.81 × F / (1960 + F) − 0.53
```

#### スコア計算

```
F1, F2 を Bark スケールに変換
  ↓
正規化距離を計算：
  dist = √( (ΔBark_F1 / 3.0)² + (ΔBark_F2 / 4.0)² )
  ↓
指数減衰スコア：
  score = 20 × exp(−1.0 × dist)
  （距離がどれだけ大きくても0点にならない設計）
```

#### フォルマント抽出の 3点サンプリング

各モーラの **30% / 50% / 70%** の3時刻でフォルマントを測定し、有効値の平均を使用します。

```python
_SAMPLE_RATIOS = [0.30, 0.50, 0.70]
```

1点（中心のみ）だと、子音から母音への遷移区間（例：/k/→/a/ の口の移動中）を誤って拾うことがあります。3点平均で遷移区間の影響を緩和し、母音の安定した「核」を評価します。

#### 有効サンプル数による信頼度重み付け

```
3点すべて有効 → weight = 1.0
2点有効       → weight = 0.67
1点のみ有効   → weight = 0.33

mean_dist = Σ(dist × weight) / Σ(weight)  ← 加重平均
```

#### 話者性別によるフォルマント補正

男性と女性では声道の長さが異なるため、同じ母音でもフォルマント周波数が違います。ネイティブ音声（VOICEVOX ずんだもん：女性）と学習者（男性の場合）を直接比較すると、正しく発音していてもスコアが低くなります。

`estimate_pitch_range()` が返す `pitch_ceiling` の値（≤200Hz → 男性）で自動判定し、補正します。

| ネイティブ | 学習者 | 補正係数 |
|-----------|--------|---------|
| 女性 | 女性 | 1.0（補正なし） |
| 男性 | 男性 | 1.0（補正なし） |
| 女性 | 男性 | ネイティブ F1/F2 × 0.85 |
| 男性 | 女性 | ネイティブ F1/F2 × 1.18（÷0.85） |

補正係数 0.85 の根拠：Peterson & Barney (1952) ほか複数の音響音声学研究で男性フォルマントは女性の約 82〜87% と報告されており、保守的な値として 0.85 を採用しています。

### 5.6 口形分析（MediaPipe FaceMesh）

#### 概要

**スコアには影響せず、フィードバックのみ** を目的とした機能です。録音時に同時に録画した口元映像から、モーラごとの口の開き度合いを数値化し、お手本と比較します。

#### 使用するランドマーク

MediaPipe FaceMesh は顔に 468 個のランドマーク（特徴点）を検出します。口形評価には以下の4点のみを使用します。

| ランドマーク番号 | 部位 |
|---------------|------|
| 13 | 上唇（内側） |
| 14 | 下唇（内側） |
| 61 | 口の左端 |
| 291 | 口の右端 |

#### 評価指標：v_h_ratio（縦横比）

```
v_dist = ランドマーク 13（上唇）と 14（下唇）の距離
h_dist = ランドマーク 61（左端）と 291（右端）の距離
v_h_ratio = v_dist / h_dist

値が大きい → 口が縦に大きく開いている（/a/ のような音に近い）
値が小さい → 口が横に細く開いている（/i/ のような音に近い）
```

#### お手本との比較方式

**お手本登録あり（schema_version: 2 + mora_data）の場合**

Julius アライメントで特定したモーラの時刻を基準に、同じ位置のモーラ同士を直接比較します。

```
正規化：各 v_h_ratio を 95 パーセンタイル値で割り 0〜1.5 にスケール
  ← max() の代わりに 95 パーセンタイルを使う理由：
     瞬間的な外れ値（まばたき・顔の向き変化）の影響を除くため

判定：|actual - expected| < 0.15 → 「良好」
      actual < expected           → 「口の開きが足りない」
      actual > expected           → 「開きすぎ」
```

**お手本未登録の場合**

日本語音素ごとの典型的な口の開き度（音韻テーブル `_VOWEL_OPENNESS`）を期待値として使用します。

#### お手本データの内部構造（lip_refs.json）

```json
{
  "word1": {
    "schema_version": 2,
    "vectors": [[0.31, 0.28, ...], ...],   ← DTW 用全フレームベクトル
    "ratios":  [0.31, 0.28, ...],           ← グラフ表示用 v_h_ratio 列
    "mora_data": [
      {"label": "o",  "v_h_ratio": 0.42},  ← Julius アライメントで特定
      {"label": "N",  "v_h_ratio": 0.18},
      {"label": "do", "v_h_ratio": 0.31}
    ]
  }
}
```

`schema_version: 2` + `mora_data` あり → Julius アライメント付き新形式（高精度）  
`schema_version` なし → 旧形式（全フレーム平均、後方互換）

#### mediapipe が使えない環境では

`pip install mediapipe` がない環境では `MEDIA_PIPE_AVAILABLE = False` となり、口形分析タブが自動的に非表示になります。スコア評価など他の機能は通常通り使えます。

### 5.7 音色評価（MFCC + DTW）

#### 概要

発音スコアとは別に、「声の音色がネイティブに近いか」を評価します。スコアとは独立したグラフとして表示されます。

#### MFCC（メル周波数ケプストラム係数）

MFCC は声道の形（スペクトル包絡）を表す特徴量です。36次元で構成されます。

| 次元 | 種類 | 意味 |
|------|------|------|
| 1〜12 | 静的 MFCC | 音の瞬間的な断面 |
| 13〜24 | Δ MFCC（1階微分） | 音の変化の速さ |
| 25〜36 | ΔΔ MFCC（2階微分） | 音の変化の加速度 |

Δ・ΔΔ を加えることで「音の動き」も比較できます。静的 MFCC だけでは「ある瞬間の音の形」しか捉えられないためです。

#### DTW（動的時間伸縮法, Dynamic Time Warping）

2つの時系列の「最も近い対応付け」を動的計画法で求めるアルゴリズムです。発話速度の違いを自動的に吸収しながら距離を計算します。

**スコア正規化について**

累積 DTW 距離は音声の長さに比例して大きくなるため、音声の長さで割って正規化します。

```python
normalized_distance = dtw_distance / (len(mfcc1) + len(mfcc2))
```

これにより、短い単語と長い単語を公平に比較できます。

#### グラフの見方

```
赤いバー ：今回練習した単語
青いバー ：その他の単語

バーが左（距離が小さい）→ 音色がネイティブに近い
理想    ：赤いバーが最も左にある状態
```

### 5.8 スコアの信頼区間（ブートストラップ法）

#### 学術的背景

1回の録音で出たスコアは「その日の調子・録音環境・偶然」に左右されます。3回以上の録音データがあれば**ブートストラップ法**で統計的な信頼区間を推定し、「68〜76点（±4点）」のように表示します。

#### アルゴリズム

```
1. N 個のスコアリストから N 個をランダムに復元抽出（1試行）
2. その試行の平均を記録
3. 1〜2 を 2000 回繰り返す
4. 2000 個の平均の 2.5〜97.5 パーセンタイルが 95% 信頼区間
```

| 録音回数 | 表示 |
|--------|------|
| 1〜2回 | 「あと○回録音すると実力範囲が計算できます」 |
| 3回以上 | 「68〜76点（±4点）」のように幅で表示 |

信頼区間の幅が**発音の安定性**の指標になります（幅が狭い = 毎回安定して発音できている）。

### 5.9 学習支援機能（クエスト・間隔反復・学習曲線分析）

#### クエストシステム（core/quest.py）

録音後に自動的に弱点を分析し、練習目標（クエスト）を最大3つ発行します。

**難易度と目標増分**

| 軸 | 現在スコア | 難易度 | 目標増分 |
|----|-----------|--------|---------|
| アクセント | < 20点 | 上級 | +12点 |
| アクセント | < 35点 | 中級 | +8点 |
| アクセント | ≥ 35点 | 初級 | +5点 |
| 長さ | < 12点 | 上級 | +7点 |
| 長さ | < 22点 | 中級 | +5点 |
| 長さ | ≥ 22点 | 初級 | +3点 |
| 母音 | < 8点 | 上級 | +5点 |
| 母音 | < 14点 | 中級 | +4点 |
| 母音 | ≥ 14点 | 初級 | +2点 |

#### 間隔反復（Spaced Repetition）

エビングハウスの忘却曲線に基づき、一定期間練習していない単語を復習クエストとして提案します。

```python
get_spaced_repetition_candidates(
    min_days  = 3.0,    # 最終練習から3日以上経過した単語
    max_score = 85.0,   # スコアが85点未満の単語のみ対象
    limit     = 5,
)
```

#### 学習曲線分析（core/analysis.py）

練習履歴に線形回帰を当てはめ、上達速度・停滞期を自動検出します。

| 分析 | 手法 | 意味 |
|------|------|------|
| 上達速度 | `scipy.stats.linregress` | 回帰直線の傾き（点/回） |
| プラトー検出 | 直近10回の傾きが ±0.3 未満 | 停滞中かどうかの判定 |
| アクセント型難易度 | 型ごとの平均傾き・Sランク到達率 | どの型が学習者に難しいか |
| Sランク到達回数 | 平均・中央値・最少/最多 | 何回練習すれば上達するかの定量化 |

これらのデータは `/history` の「分析」タブで確認できます。

## 8. GitHub での開発方法

### ブランチ戦略

```
main          ← 動作する最新版を常に維持するブランチ
feature/xxx   ← 新機能の開発
fix/xxx       ← バグ修正
refactor/xxx  ← 動作を変えないコード整理
docs/xxx      ← ドキュメントのみの変更
```

**main ブランチには直接コミットしない**のが原則です。必ずブランチを切って作業し、動作確認後に main にマージします。

---

### 開発の基本的な流れ

```bash
# 1. main を最新にする（作業開始前に必ず実行）
git checkout main
git pull origin main

# 2. 作業ブランチを作る
git checkout -b feature/○○○

# 3. コードを変更する
# ... 作業 ...

# 4. 変更をステージング
git add web/templates/history.html core/analysis.py
# ※ git add . は避ける（不要なファイルが混入しやすい）

# 5. コミット（内容を具体的に書く）
git commit -m "feat: 記録・分析ページを2タブ構成に統合"

# 6. リモートにプッシュ
git push origin feature/○○○

# 7. main にマージ
git checkout main
git merge feature/○○○
git push origin main

# 8. 不要になったブランチを削除
git branch -d feature/○○○
git push origin --delete feature/○○○
```

---

### コミットメッセージの書き方

**フォーマット：`種類: 何をしたか（日本語でも OK）`**

| 種類 | 使う場面 | 例 |
|------|---------|-----|
| `feat:` | 新機能を追加した | `feat: 口形分析にモーラ単位比較を追加` |
| `fix:` | バグを修正した | `fix: モーラ別アクセントスコアが0になるバグを修正` |
| `refactor:` | 動作を変えずに整理した | `refactor: evaluate.py のスコア計算を関数化` |
| `docs:` | ドキュメントを更新した | `docs: README にセットアップ手順を追加` |
| `chore:` | 設定やビルドを変更した | `chore: requirements.txt を更新` |

**良いコミットメッセージの例**

```bash
feat: DTW 距離を音声長で正規化して公平に比較できるよう修正
fix: Jinja2 の sort フィルタで None 比較エラーが出る問題を修正
docs: Julius アライメントの仕組みをREADMEに追記
```

**悪いコミットメッセージの例**

```bash
update         # ← 何を更新したか不明
fix bug        # ← どのバグか不明
色々修正した   # ← 内容が不明・後から追いにくい
```

---

### ブランチ命名規則

- すべて小文字・単語はハイフン（`-`）でつなぐ
- 何をするブランチか3〜4単語で表現する

```
feature/lip-ref-alignment       ← 良い
feature/口形アライメント実装    ← 日本語は避ける
feature/fix                     ← 内容が不明
```

---

### やってはいけないこと

| NG 操作 | 理由 |
|---------|------|
| `main` に直接コミット・プッシュ | 変更履歴が追いにくくなる |
| 複数の無関係な変更を1つのブランチに混ぜる | 後から差し戻しが難しくなる |
| `git add .` を使いすぎる | `.env` や大きなバイナリが混入しやすい |
| コミットせずに何日も作業を続ける | 差分が大きくなりすぎてコンフリクトが起きやすい |
| バイナリファイル（.wav, .bin）をコミット | リポジトリが肥大化する（.gitignore で除外済み） |

---

### GitHub に上がらないファイル（.gitignore の設定）

以下のファイルは個人のデータや一時ファイルのため、`.gitignore` で除外されています。

```
data/config/words_db.json       ← 登録単語データベース
data/config/history.json        ← 練習履歴
data/config/lip_refs.json       ← お手本口形データ
data/config/quest_progress.json ← クエスト進捗
data/raw_audio/sound/           ← ネイティブ音声
data/mfcc/                      ← MFCC バイナリ
web/static/sample/              ← ブラウザ再生用音声
```

**別の PC に引き継ぐ場合は、これらを手動でコピーしてください。**

---

### 便利な git コマンド

```bash
# 現在の状態を確認
git status

# 変更の差分を確認（コミット前に内容を確かめる）
git diff

# コミット履歴を確認
git log --oneline -10

# 特定のファイルの変更履歴を確認
git log --oneline -- core/evaluate.py

# 間違えたコミットを取り消す（まだプッシュしていない場合）
git reset --soft HEAD~1

# ブランチの一覧を確認
git branch -a
```

## 9. よくあるトラブルと対処法

### Julius が見つからない / アライメントが失敗する

```bash
# diagnose.py で Julius のパスを確認
python diagnose.py

# 環境変数で直接指定する場合
$env:JULIUS_BIN = "C:\path\to\julius.exe"   # Windows PowerShell
export JULIUS_BIN="/usr/local/bin/julius"    # Linux/Mac
```

---

### 単語を追加したらサンプル音声が出ない

MFCC バイナリを再生成するのを忘れている可能性があります。

```bash
python scripts/regenerate_mfcc.py
```

---

### 特定の単語のアライメントが失敗する

```bash
# 1単語の修復
python scripts/repair_alignment.py word35

# 複数単語の修復
python scripts/repair_alignment.py word35 word36 word37
```

---

### モーラ別スコアが全部 0 になる

スコアには Julius のアライメント結果が必要です。以下を確認してください。

1. `python diagnose.py` でエラーが出ていないか確認
2. `data/raw_audio/wav/test.lab` が生成されているか確認
3. 録音が短すぎる・マイクが遠すぎると Julius スコアが低くなる

---

### 口形分析タブが表示されない

MediaPipe がインストールされていない可能性があります。

```bash
pip install mediapipe
```

インストール後にサーバーを再起動してください。

---

### VOICEVOX でサンプル音声が生成されない

VOICEVOX アプリが起動していない可能性があります。

```bash
# VOICEVOX の動作確認
python test_voicevox.py
```

---

### MeCab でアクセント型が取得できない

```bash
# MeCab の動作確認
python test_mecab.py

# UniDic がない場合
python -m unidic download
```

## 10. 既知の限界と今後の課題

### 現在の限界

| 限界 | 詳細 | 将来の改善案 |
|------|------|------------|
| **参照音声が1本** | 同一話者（VOICEVOX ずんだもん）の音声が唯一の正解になる | 複数話者の平均化、実際のネイティブ話者の録音に切り替え |
| **パラメータが未検証** | 重み係数（0.40 / 0.35 等）を正解データで最適化できていない | 評価付き録音データ 20〜30 例収集でチューニング |
| **性別補正は集団平均** | 補正係数 0.85 は個人差を完全には吸収できない | 個人単位の話者正規化（VTLN）の実装 |
| **シングルユーザー設計** | `test.wav` が上書きされると以前の録音が消える | セッション ID でファイルを分けるマルチユーザー対応 |
| **MFA は精度が低い** | MFA の音素ラベル体系が Julius と異なるためスコアが大幅低下（`USE_MFA = False` 推奨） | パイプライン全体を MFA 向けに書き直す |

### 解決済みの限界

| 問題 | 対応内容 |
|------|---------|
| ~~話者性別補正なし~~ | ネイティブ・学習者両方の性別を自動判定し補正 |
| ~~DTW 距離が音声長に依存~~ | `(len(mfcc1) + len(mfcc2))` で正規化 |
| ~~モーラ別アクセントスコアが常に 0~~ | 生の半音値の代わりに 0-1 正規化後の値を使用 |
| ~~分析ページで Jinja2 クラッシュ~~ | Python 側で事前ソートして渡す方式に変更 |
