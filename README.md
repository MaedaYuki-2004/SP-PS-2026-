# SP-PS — 日本語発音練習・評価システム

> 「声（口）のかたちを綺麗にする一歩を踏める嬉しさを届ける」

録音した日本語単語の発音をお手本音声と比較し、**アクセント・モーラ長・母音品質の3軸**でスコアを算出してフィードバックを提供する Flask ベースの Web アプリケーションです。Julius 音声認識エンジンによる強制アライメント、MediaPipe FaceMesh による口形分析、スペクトル分析（MFCC + DTW）、学習曲線の統計分析など、音声科学・言語学習研究の知見を実装しています。

単語は**テキストとお手本録画（動画）をセットで登録**し、その動画から音声と口の動きの両方を取り込みます。声だけ・口だけでは分からない「声と口のタイミングのズレ」を検出する**音映像クロスチェック**を搭載しており、聴覚に障害のある方の発音練習を主な想定利用者としています。

## 1. プロジェクト概要

### 何ができるシステムか

SP-PS は、学習者が**自分の発音をお手本と客観的に比較する**ためのシステムです。
お手本は、指導者が単語登録時に録画した音声・映像をそのまま使います。

| 機能カテゴリ | 内容 |
|------------|------|
| **発音スコアリング** | アクセント・モーラ長・母音品質の3軸を数値化（100点満点） |
| **口形分析** | MediaPipe で口の縦横比（v_h_ratio）を検出し、お手本との差を可視化 |
| **音映像クロスチェック** | 声と口の動きが同じ瞬間を指しているかを照合し、同期のズレをミリ秒で表示（試験運用中・スコアには非影響） |
| **音色評価** | MFCC + DTW でスペクトルの類似度を評価 |
| **お手本動画の再生** | 登録時に録画した口の動きを、録音ページ・母音トレーナーで見ながら練習できる |
| **録音タイミングガイド** | 録音前のカウントダウンと、お手本のテンポに合わせたカラオケ式のモーラ点灯（聴覚障害のある方向け） |
| **学習分析** | 練習履歴から上達速度・停滞期を統計的に自動検出 |
| **今日のレッスン** | 履歴から当日の練習メニュー（復習・苦手音・口の形・挑戦）を自動編成 |
| **苦手音ドリル** | モーラ別スコアから弱点の音を特定し、集中ドリル・聞き分けテストを生成 |

### 論文・研究での参照について

このシステムは以下の音声科学的手法を実装しています。
各節の「学術的背景」に参照理論と実装の対応を記載しています。

- **強制アライメント**（Julius, HMM-Viterbi）
- **ピッチ分析**（Praat/parselmouth, 半音スケール, Pearson 相関）
- **フォルマント分析**（F1/F2 Bark スケール, Peterson & Barney 1952）
- **スペクトル類似度**（MFCC 36次元, DTW）
- **ブートストラップ統計**（95% 信頼区間推定）
- **学習曲線分析**（線形回帰, プラトー検出）
- **音映像同期分析**（唇形状ベクトル列の DTW × 強制アライメント時刻の照合, MAD による頑健なばらつき評価）

```
④ 記録・分析ページ（/history）
    ├ 「練習ログ」タブ：過去のスコア推移・アクセント型別の平均
```

### 録音タイミングガイド

聴覚に障害のある方は、発音中に自分の声でテンポを確認することができません。そこで「耳の代わりを画面が担う」ガイドを用意しています。

| タイミング | 画面の動き |
|-----------|-----------|
| 録音開始ボタンを押した直後 | 大きな **3・2・1** のカウントダウン（この間は録音されないので準備できる） |
| カウントダウン終了と同時 | 実際の録音が始まり、お手本のモーラ時刻に合わせてチップが**カラオケ式に点灯** |
| 全モーラの終了後 | 「✓ 言い終わったら録音停止」を表示 |

録音ボタン下の **⏱ タイミングガイド** で ON / OFF を切り替えられます（設定はブラウザに保存され、既定は ON）。
このガイドはお手本のアライメント結果を使うため、お手本が登録済みの単語でのみ表示されます。

### 5.2 Julius 強制アライメント

#### 何をするのか

**強制アライメント（Forced Alignment）** とは、既知のテキスト（ひらがな読み）が音声のどのタイムスタンプで発音されているかを特定する処理です。

例えば「びょういん」と録音した音声に対して：

```
0.000〜0.075秒: 無音（silB）
0.075〜0.150秒: 「びょ」
0.150〜0.250秒: 「う」（長音）
0.250〜0.300秒: 「い」
0.300〜0.375秒: 「ん」
0.375〜0.450秒: 無音（silE）
```

というタイムスタンプを出力します。この結果がなければ「何秒目にどの音節が発音されているか」がわからないため、アクセント評価も口形分析も成立しません。

#### 技術的背景

Julius は **HMM（隠れマルコフモデル）** を使った Viterbi アルゴリズムで、入力音声とテキストを最尤対応付けします。音響モデル（`hmmdefs_monof_mix16_gid.binhmm`）は日本語音素を表す HMM のパラメータ集です。

#### 実装の流れ

```
test.wav（録音音声）
test.txt（「びょういん」）
  ↓
scripts/segment_julius.pl
  ├ ひらがな → Julius 音素列に変換
  │   びょういん → "by o: i N"
  ├ Julius を実行（Viterbi アルゴリズム）
  └ test.lab（タイムスタンプ）・test.log（対数尤度）を生成
```

#### Julius 品質ゲート

Julius は発音の品質をスコア（対数尤度）で返します。

| Julius スコア | 状態 | SP-PS の動作 |
|-------------|------|------------|
| -1000 以上 | 良好 | スコア計算を実行 |
| -1000 〜 -3000 | やや不安定 | スコア計算を実行（注意） |
| **-3000 以下** | **不安定** | **スコア計算をスキップ・再録音ガイドを表示** |

対数尤度が極端に低い場合は「マイクに近づく・はっきり発音する・静かな環境で試す」という案内を表示します。ピッチグラフはアライメントと独立して計算されるため引き続き表示されます。

#### 音素とモーラの変換

Julius は**音素**（音声学的最小単位）でアライメントしますが、日本語のリズム評価は**モーラ**（拍）単位で行います。`mora_time()` が変換します。

| ルール | 例 |
|--------|-----|
| 子音 + 直後の母音 → 1モーラ | `by` + `o:` → `びょ（byo:）` |
| 単独母音 → 1モーラ | `i` → `い（i）` |
| 撥音（ん）→ 1モーラ | `N` → `ん（N）` |
| 促音（っ）→ 1モーラ | `q` → `っ（q）` |

### 5.3 アクセント評価（ピッチ分析） — 50点

#### 学術的背景

日本語アクセントは**ピッチアクセント**（音の高低による区別）です。各単語に固有の H（高）/ L（低）パターンがあり、アクセント核（音が下がる位置）が意味の区別に関わります（例：「あめ（雨）」L-H vs「あめ（飴）」H-L）。

本システムでは**半音（semitone）スケール**を使用します。Hz のまま比較すると話者の声域の違い（男性 vs 女性 など）が「誤差」として混入するため、対数スケールである半音に変換して「上下パターン」のみを評価します。

```
半音 = 12 × log2(F / F_ref)
F_ref = 録音区間の有声フレームの中央値（話者ごとに自動設定）
```

#### スコア計算

4つの指標の加重平均で「内部スコア（最大60点）」を算出し、50点満点に正規化します。

```
内部スコア（0〜60）=
  核位置スコア     × 0.40
+ ピッチ相関スコア × 0.35
+ H/L 一致率スコア × 0.15
+ 安定度スコア     × 0.10

アクセントスコア = min(50, 内部スコア × 50/60 + 3.0)
```

#### 各指標の詳細

**① 核位置スコア（重み 0.40）**

アクセント核とは「音が急激に下がる直前の音節」のことです。ネイティブと学習者の核位置が一致しているかを評価します。動的閾値で核を検出します。

```python
DROP_THRESHOLD = max(0.05, min(0.25, ピッチ範囲 × 0.15))
```

ピッチ範囲が狭い（声が単調）場合は閾値を小さく、広い場合は大きくすることで、話者の声域の違いに対応します。

**② ピッチ相関スコア（重み 0.35）**

ネイティブと学習者のピッチの「上下パターンの相関」を Pearson 相関係数で評価します。有声フレーム（NaN でないフレーム）のみを使用します。無声区間の補間値がノイズとして混入しないようにするためです。

```
r = Σ(xi − x̄)(yi − ȳ) / (n × σx × σy)

r = +1.0：ネイティブと同じタイミングで上下（完全一致）
r =  0.0：無相関
r = -1.0：完全に逆パターン

score = max(0, (r + 1) / 2 × 60)
```

DTW からピアソン相関に変えた理由：日本語アクセントの本質は「いつ上がって・いつ下がるか（パターンと方向性）」であり、Pearson 相関はこれを直接測れます。また線形変換不変のため追加の正規化が不要です。

**③ H/L 一致率スコア（重み 0.15）**

各モーラを「高（H）」か「低（L）」に二値化し、ネイティブとの一致率を評価します。アクセント型に応じた**パーセンタイル閾値**を使用します。

```python
threshold = percentile(mora_pitches, L比率 × 100)
```

例：平板型（L-H-H-H）→ L 比率 25% → 25 パーセンタイルを閾値  
こうすることで、学習者の声域に関わらず相対的な高低パターンを評価できます。

**④ 安定度スコア（重み 0.10）**

各モーラ内でのピッチの揺れ（標準偏差）を評価します。値が小さいほど安定した発音です。

#### 時間正規化（length_arrange）

ネイティブと学習者の発話速度が異なるため、ピッチを重ね合わせる前に**モーラ長を揃える**必要があります。

```
例：「か」音素
  ネイティブ：8フレーム
  学習者    ：5フレーム → 末尾に NaN を3つ追加して8フレームに伸張

例：「い」音素
  ネイティブ：6フレーム
  学習者    ：9フレーム → 末尾3フレームを削除して6フレームに短縮
```

#### ピッチ処理パイプライン

```
praat_pitch()              Hz 配列（NaN = 無声区間）
  ↓
resample_to_10ms()         Julius の 10ms フレームに揃える
  ↓
発話区間のみ切り出し（silB〜silE の外を除去）
  ↓
hz_to_semitone()           Hz → 半音変換（NaN 保持）

  ┌────────────────────┐     ┌────────────────────┐
  │   スコア計算用      │     │   グラフ表示用      │
  ├────────────────────┤     ├────────────────────┤
  │ length_arrange()   │     │ comp()  NaN を補間  │
  │ comp()  NaN 補間   │     │ smooth() window=5  │
  │ smooth() window=3  │     │ scale()  0〜1 正規化 │
  └────────────────────┘     └────────────────────┘
```

### 5.4 モーラ長評価 — 30点

#### 学術的背景

日本語は**モーラ拍言語（mora-timed language）**であり、各モーラの持続時間がリズムの基本単位です。特に**長音（ー）・促音（っ）・撥音（ん）** は通常モーラの約2倍の長さを持ちます。これらを正確に発音しないと意味が変わる場合があります（例：「おばさん（伯母）」vs「おばあさん（祖母）」）。

#### スコア計算

各モーラの「全発話時間に占める割合」を計算し、ネイティブとの差を重み付き誤差でスコア化します。

```
モーラ重み：
  長音（ー）・促音（っ）→ 2.0倍
  撥音（ん）           → 1.5倍
  通常モーラ           → 1.0倍

weighted_diff = Σ(|native[i] - user[i]| × weight[i]) / Σ(weight[i])
内部スコア   = max(0, (1.0 - weighted_diff / 25.0) × 40)
長さスコア   = 内部スコア × 30 / 40
```

長音・促音に高い重みをかけるのは、これらの誤りが聞き取りへの影響が大きいためです。

#### 絶対時間チェック

長音・促音については割合比較に加えて「通常モーラの平均長さとの比率」も確認します。

```
長音（ー）の適正範囲：通常モーラ平均の 1.5〜3.0 倍
促音（っ）の適正範囲：通常モーラ平均の 0.6〜1.8 倍
```

この範囲を外れた場合はモーラ別フィードバックに警告を表示します。

### 5.5 母音品質評価（フォルマント分析） — 20点

#### 学術的背景

**フォルマント**（formant）とは、声道の共鳴によって生じる音のスペクトルピークです。第1フォルマント（F1）は口の開き度と相関し、第2フォルマント（F2）は舌の前後位置と相関します。F1/F2 の組み合わせが母音を特徴づけます（Peterson & Barney, 1952）。

**Bark スケール**は Hz を知覚的に均等なスケールに変換したものです。F1（低周波数域）と F2（高周波数域）では人間の知覚感度が異なるため、Hz のまま差を計算すると「聞こえ方の差」を正確に反映できません。

```
Bark = 26.81 × F / (1960 + F) − 0.53
```

#### スコア計算

```
F1, F2 を Bark スケールに変換
  ↓
正規化距離を計算：
  dist = √( (ΔBark_F1 / 3.0)² + (ΔBark_F2 / 4.0)² )
  ↓
指数減衰スコア：
  score = 20 × exp(−1.0 × dist)
  （距離がどれだけ大きくても0点にならない設計）
```

#### フォルマント抽出の 3点サンプリング

各モーラの **30% / 50% / 70%** の3時刻でフォルマントを測定し、有効値の平均を使用します。

```python
_SAMPLE_RATIOS = [0.30, 0.50, 0.70]
```

1点（中心のみ）だと、子音から母音への遷移区間（例：/k/→/a/ の口の移動中）を誤って拾うことがあります。3点平均で遷移区間の影響を緩和し、母音の安定した「核」を評価します。

#### 有効サンプル数による信頼度重み付け

```
3点すべて有効 → weight = 1.0
2点有効       → weight = 0.67
1点のみ有効   → weight = 0.33

mean_dist = Σ(dist × weight) / Σ(weight)  ← 加重平均
```

#### 話者性別によるフォルマント補正

男性と女性では声道の長さが異なるため、同じ母音でもフォルマント周波数が違います。お手本の話者と学習者の性別が異なる場合、正しく発音していてもスコアが低くなります。

`estimate_pitch_range()` が返す `pitch_ceiling` の値（≤200Hz → 男性）で自動判定し、補正します。

| ネイティブ | 学習者 | 補正係数 |
|-----------|--------|---------|
| 女性 | 女性 | 1.0（補正なし） |
| 男性 | 男性 | 1.0（補正なし） |
| 女性 | 男性 | ネイティブ F1/F2 × 0.85 |
| 男性 | 女性 | ネイティブ F1/F2 × 1.18（÷0.85） |

補正係数 0.85 の根拠：Peterson & Barney (1952) ほか複数の音響音声学研究で男性フォルマントは女性の約 82〜87% と報告されており、保守的な値として 0.85 を採用しています。

### 5.6 口形分析（MediaPipe FaceMesh）

#### 概要

**スコアには影響せず、フィードバックのみ** を目的とした機能です。録音時に同時に録画した口元映像から、モーラごとの口の開き度合いを数値化し、お手本と比較します。

#### 使用するランドマーク

MediaPipe FaceMesh は顔に 468 個のランドマーク（特徴点）を検出します。口形評価には以下の4点のみを使用します。

| ランドマーク番号 | 部位 |
|---------------|------|
| 13 | 上唇（内側） |
| 14 | 下唇（内側） |
| 61 | 口の左端 |
| 291 | 口の右端 |

#### 評価指標：v_h_ratio（縦横比）

```
v_dist = ランドマーク 13（上唇）と 14（下唇）の距離
h_dist = ランドマーク 61（左端）と 291（右端）の距離
v_h_ratio = v_dist / h_dist

値が大きい → 口が縦に大きく開いている（/a/ のような音に近い）
値が小さい → 口が横に細く開いている（/i/ のような音に近い）
```

#### お手本との比較方式

**お手本登録あり（schema_version: 2 + mora_data）の場合**

Julius アライメントで特定したモーラの時刻を基準に、同じ位置のモーラ同士を直接比較します。

```
正規化：各 v_h_ratio を 95 パーセンタイル値で割り 0〜1.5 にスケール
  ← max() の代わりに 95 パーセンタイルを使う理由：
     瞬間的な外れ値（まばたき・顔の向き変化）の影響を除くため

判定：|actual - expected| < 0.15 → 「良好」
      actual < expected           → 「口の開きが足りない」
      actual > expected           → 「開きすぎ」
```

**お手本未登録の場合**

日本語音素ごとの典型的な口の開き度（音韻テーブル `_VOWEL_OPENNESS`）を期待値として使用します。

#### お手本データの内部構造（lip_refs.json）

```json
{
  "word1": {
    "schema_version": 2,
    "vectors": [[0.31, 0.28, ...], ...],   ← DTW 用全フレームベクトル
    "ratios":  [0.31, 0.28, ...],           ← グラフ表示用 v_h_ratio 列
    "times":   [0.0, 0.033, 0.066, ...],    ← 各フレームの時刻（秒・クロスチェック用）
    "mora_data": [
      {"label": "o",  "v_h_ratio": 0.42},  ← Julius アライメントで特定
      {"label": "N",  "v_h_ratio": 0.18},
      {"label": "do", "v_h_ratio": 0.31}
    ]
  }
}
```

`schema_version: 2` + `mora_data` あり → Julius アライメント付き新形式（高精度）  
`schema_version` なし → 旧形式（全フレーム平均、後方互換）

#### フレーム時刻を保存する理由（times）

顔検出に失敗したフレームはスキップされるため、ベクトルの並び順から時刻を復元することはできません。
音映像クロスチェック（[§5.11](#511-音映像クロスチェック口と声の同期分析)）は正確な時刻対応を必要とするため、
`frame_index / fps` で算出した各フレームの時刻を明示的に記録しています
（WebM では `CAP_PROP_POS_MSEC` が信頼できないため fps ベースで計算）。

#### お手本動画そのものの保存・再生

登録時に録画した WebM 動画は `data/raw_audio/sound/{word_id}/{word_id}.webm` に保存され、
`/sample_video/<word_id>` から配信されます。抽出データだけでなく動画自体を残すことで、
学習者が「先生の実際の口の動き」を見ながら練習できます。

| 表示場所 | 内容 |
|---------|------|
| 録音ページ | 「🎥 先生の口の動きを見る」ボタンで再生 |
| 母音トレーナー | 🖼 イラスト / 🎥 先生の実写 をタブで切り替え |

#### mediapipe が使えない環境では

`pip install mediapipe` がない環境では `MEDIA_PIPE_AVAILABLE = False` となり、口形分析タブが自動的に非表示になります。スコア評価など他の機能は通常通り使えます。

### 5.7 音色評価（MFCC + DTW）

#### 概要

発音スコアとは別に、「声の音色がネイティブに近いか」を評価します。スコアとは独立したグラフとして表示されます。

#### MFCC（メル周波数ケプストラム係数）

MFCC は声道の形（スペクトル包絡）を表す特徴量です。36次元で構成されます。

| 次元 | 種類 | 意味 |
|------|------|------|
| 1〜12 | 静的 MFCC | 音の瞬間的な断面 |
| 13〜24 | Δ MFCC（1階微分） | 音の変化の速さ |
| 25〜36 | ΔΔ MFCC（2階微分） | 音の変化の加速度 |

Δ・ΔΔ を加えることで「音の動き」も比較できます。静的 MFCC だけでは「ある瞬間の音の形」しか捉えられないためです。

#### DTW（動的時間伸縮法, Dynamic Time Warping）

2つの時系列の「最も近い対応付け」を動的計画法で求めるアルゴリズムです。発話速度の違いを自動的に吸収しながら距離を計算します。

**スコア正規化について**

累積 DTW 距離は音声の長さに比例して大きくなるため、音声の長さで割って正規化します。

```python
normalized_distance = dtw_distance / (len(mfcc1) + len(mfcc2))
```

これにより、短い単語と長い単語を公平に比較できます。

#### グラフの見方

```
赤いバー ：今回練習した単語
青いバー ：その他の単語

バーが左（距離が小さい）→ 音色がネイティブに近い
理想    ：赤いバーが最も左にある状態
```

### 5.8 スコアの信頼区間（ブートストラップ法）

#### 学術的背景

1回の録音で出たスコアは「その日の調子・録音環境・偶然」に左右されます。3回以上の録音データがあれば**ブートストラップ法**で統計的な信頼区間を推定し、「68〜76点（±4点）」のように表示します。

#### アルゴリズム

```
1. N 個のスコアリストから N 個をランダムに復元抽出（1試行）
2. その試行の平均を記録
3. 1〜2 を 2000 回繰り返す
4. 2000 個の平均の 2.5〜97.5 パーセンタイルが 95% 信頼区間
```

| 録音回数 | 表示 |
|--------|------|
| 1〜2回 | 「あと○回録音すると実力範囲が計算できます」 |
| 3回以上 | 「68〜76点（±4点）」のように幅で表示 |

信頼区間の幅が**発音の安定性**の指標になります（幅が狭い = 毎回安定して発音できている）。

### 5.9 学習支援機能（今日のレッスン・苦手音ドリル・学習曲線分析）

#### 今日のレッスン（core/lesson.py）

Duolingo / ELSA Speak の「デイリーレッスン」方式です。アプリ側が練習履歴からその日のメニューを
1本道で組み立て、ユーザーは上から順に進めるだけにします。進捗は `data/config/daily_lesson.json` に
日付キーで保存されます。

| ステップ | 内容 | 選ばれる条件 |
|---------|------|------------|
| `review` | 間隔反復による復習 | 3日以上練習していない単語 |
| `sound` | 苦手音を含む単語の録音練習 | 苦手音ランキング上位の音を含む単語 |
| `mouth` | 母音トレーナーで口の形を練習 | 口形お手本が登録済みの単語 |
| `challenge` | 練習回数が少ない単語への挑戦 | 練習回数が少ない単語 |

ステップは最大4つで、データに応じて可変です。

#### 苦手音の分析とドリル（core/weakness.py / core/drill.py）

練習履歴に蓄積されたモーラ別スコアを**かな単位で集計**し、繰り返しスコアが低い音を
ランキングで返します（ELSA Speak 等の「弱点フォニーム特定 → 集中ドリル」と同じ発想）。
「ん」「っ」「ー」は単独で練習対象にしません。

特定した苦手音は、言語聴覚士の構音指導の標準ステップに沿ったドリルに展開されます。

```
音単独 → 音節（のばす・くりかえす） → 語頭 → 語中・語尾 → 単語
```

聞き分けテスト（`/listening_quiz`）も同モジュールが生成します。
似ている音を聞き分ける力は発音改善の土台になるという考えに基づく機能で、
サンプル音声つきの単語が3語以上必要です。

#### 間隔反復（Spaced Repetition）

エビングハウスの忘却曲線に基づき、一定期間練習していない単語を復習として提案します。

```python
get_spaced_repetition_candidates(
```

| 分析 | 手法 | 意味 |

| 上達速度 | `scipy.stats.linregress` | 回帰直線の傾き（点/回） |

```
     .lab が空（＝発話を認識できなかった）の場合は
```

#### 単語 ID の採番について

`get_next_word_id()` は words_db.json に現存する ID だけでなく、`web/static/sample/` と

### 5.11 音映像クロスチェック（口と声の同期分析）

#### 概要

**スコアには影響せず、表示のみ**（試験運用中）の機能です。「声から見つけた発音の瞬間」と
「口の動きから見つけた発音の瞬間」が一致するかを照合し、**声と口のタイミングのズレ**を
モーラごとにミリ秒で算出します。実装は `core/sync.py`。

聴覚に障害のある方は自分の声を聞いてタイミングを合わせることが難しく、
口の形は正しいのに声のタイミングだけがズレるケースがあります。
従来の3軸スコア（アクセント・長さ・母音）と唇スコアはこのズレを見逃すため、
それを補う指標として追加しました。

#### アイデアの出典

指導教員からの提案：お手本とユーザーの「音声同士の対応」と「映像同士の対応」という
2本の独立した対応線が同じ場所を指していれば、その発音は音・口の形・タイミングの
すべてが合っていると判断できる、という発想。

#### 2本の対応線

| 対応線 | 求め方 | 備考 |
|--------|-------|------|
| **声の対応線** | Julius 強制アライメントのモーラ境界（各録音の `.lab`） | 同じモーラ同士が対応するという事実を使うため、生波形 DTW より頑健 |
| **映像の対応線** | 唇形状ベクトル列同士の `fastdtw` 経路 | 20次元 × フレーム数のベクトル列を DTW で対応づける |

#### 技術的な壁と3ステップの橋渡し

音声と映像では時間の測り方の細かさが違います（音声のフレーム周期は 10ms、映像は 30fps ＝
約 33ms/フレーム）。そのまま比較できないため、次の3ステップで時刻を橋渡しします。

```
① 口の動きどうしを比べて対応表を作る
     お手本の映像フレーム i ↔ ユーザーの映像フレーム j の対応（DTW 経路）

② 声の時刻を、その対応表で映像の時刻に変換する
     お手本のモーラ中心時刻
       → 最も近いお手本映像フレーム
       → (DTW) → ユーザーの映像フレーム
       → ユーザーの映像時刻 t_video

③ 実際の声の時刻と比べる
     t_audio = 音声アライメントが指すユーザーのモーラ中心時刻
     offset_ms = (t_video - t_audio) × 1000
```

#### 指標の読み方

| 指標 | 意味 |
|------|------|
| `offset > 0` | 口の動きが声より**遅れて**現れている |
| `offset < 0` | 口の動きが声より**先行して**いる |
| `median_offset_ms` | 発話全体の系統的なズレ。**録画開始タイミングの機材差も混入するため単体では参考値** |
| `spread_ms` | モーラ間のズレのばらつき（MAD＝中央絶対偏差）。機材差の影響を受けないため、発話内での不同期を測る**主指標** |

中央値ではなく MAD を主指標にしているのは、録画開始のズレ（機材差）が中央値そのものを
汚染してしまうためです。ばらつきであれば、全体が一律にずれていても値が大きくなりません。

#### しきい値の校正（2026-07-03 実施）

実データと合成ズレ注入による自己校正の結果です。

| テスト | 結果 |
|--------|------|
| 自己一致（測定ノイズ床） | spread 2〜9ms / median ±11ms |
| 一様ズレ注入 50 / 100 / 200ms | median が -61 / -111 / -211ms とほぼ線形に回復 |
| テンポ 1.5 倍（ズレなし） | spread 8ms → **誤検知しない** |
| 同話者・同単語の別テイク | spread 27〜83ms |
| 発話後半のみ +150ms の局所ズレ | spread 75ms |

```python
SYNC_OK_MS   = 70.0    # spread < 70ms       → ok
SYNC_WARN_MS = 140.0   # 70ms 〜 140ms       → warn
                       # 140ms 以上          → ng
```

#### 結果画面での表示

対応線グラフ（X 軸＝ユーザーの時間、Y 軸＝お手本の時間）に2本の線を重ねて描画します。

- **青の実線**：口の動きの対応線（映像 DTW）
- **緑の破線**：声の対応線（音声アライメント）
- **● 緑の点**：声から特定した位置 / **◆ 青の点**：口の動きから予測した位置
- 同じモーラの2点を結ぶ線がそのモーラのズレそのもので、**線が短いほど同期**している
- ズレが 70ms 以上の箇所はオレンジで強調し、かなラベルと ±ms を併記

グラフは無音区間を除いた発話区間（前後 10% の余白つき）に絞って描画します。
映像 DTW 経路は録画全体を通っているため、絞らないとグラフの大半が無音区間の
「意味のない直線」で埋まってしまうためです。

#### 重要な限界

1. `median_offset_ms` はユーザーの音声と映像の**録画開始タイミング差（機材差）を含む**ため、
   単体では発音の良し悪しを断定できません。主指標は `spread_ms` です。
2. この指標が測るのは**タイミングの同期だけ**です。全く別の単語を発音しても、
   タイミングさえ揃っていれば `ok` になり得ます（校正テストで確認済み）。
   口の形の正しさは唇スコア・母音スコアが担当するため、**必ずそれらと並べて表示**しています。
3. 現状はスコアに反映していません（表示のみ）。実運用での判定基準は今後検証します。

**main ブランチには直接コミットしない**のが原則です。必ずブランチを切って作業し、動作確認後に main にマージします。

---

### 開発の基本的な流れ

```bash
# 1. main を最新にする（作業開始前に必ず実行）
git checkout main
git pull origin main

# 2. 作業ブランチを作る
git checkout -b feature/○○○

# 3. コードを変更する
# ... 作業 ...

# 4. 変更をステージング
git add web/templates/history.html core/analysis.py
# ※ git add . は避ける（不要なファイルが混入しやすい）

# 5. コミット（内容を具体的に書く）
git commit -m "feat: 記録・分析ページを2タブ構成に統合"

# 6. リモートにプッシュ
git push origin feature/○○○

# 7. main にマージ
git checkout main
git merge feature/○○○
git push origin main

# 8. 不要になったブランチを削除
git branch -d feature/○○○
git push origin --delete feature/○○○
```

---

### コミットメッセージの書き方

**フォーマット：`種類: 何をしたか（日本語でも OK）`**

| 種類 | 使う場面 | 例 |
|------|---------|-----|
| `feat:` | 新機能を追加した | `feat: 口形分析にモーラ単位比較を追加` |
| `fix:` | バグを修正した | `fix: モーラ別アクセントスコアが0になるバグを修正` |
| `refactor:` | 動作を変えずに整理した | `refactor: evaluate.py のスコア計算を関数化` |
| `docs:` | ドキュメントを更新した | `docs: README にセットアップ手順を追加` |
| `chore:` | 設定やビルドを変更した | `chore: requirements.txt を更新` |

**良いコミットメッセージの例**

```bash
feat: DTW 距離を音声長で正規化して公平に比較できるよう修正
fix: Jinja2 の sort フィルタで None 比較エラーが出る問題を修正
docs: Julius アライメントの仕組みをREADMEに追記
```

**悪いコミットメッセージの例**

```bash
update         # ← 何を更新したか不明
fix bug        # ← どのバグか不明
色々修正した   # ← 内容が不明・後から追いにくい
```

---

### ブランチ命名規則

- すべて小文字・単語はハイフン（`-`）でつなぐ
- 何をするブランチか3〜4単語で表現する

```
feature/lip-ref-alignment       ← 良い
feature/口形アライメント実装    ← 日本語は避ける
feature/fix                     ← 内容が不明
```

---

### やってはいけないこと

| NG 操作 | 理由 |
|---------|------|
| `main` に直接コミット・プッシュ | 変更履歴が追いにくくなる |
| 複数の無関係な変更を1つのブランチに混ぜる | 後から差し戻しが難しくなる |
| `git add .` を使いすぎる | `.env` や大きなバイナリが混入しやすい |
| コミットせずに何日も作業を続ける | 差分が大きくなりすぎてコンフリクトが起きやすい |
| バイナリファイル（.wav, .bin）をコミット | リポジトリが肥大化する（.gitignore で除外済み） |

---

### GitHub に上がらないファイル（.gitignore の設定）

以下のファイルは個人のデータや一時ファイルのため、`.gitignore` で除外されています。

```
data/                           ← ユーザーデータ一式（単語・履歴・お手本・録画）を丸ごと除外
web/static/sample/              ← ブラウザ再生用音声
web/static/distance_result/     ← 音色評価チャート（解析のたびに再生成）
```

`data/` はディレクトリごと除外しています。個別ファイル名を列挙する方式だと、
機能追加で新しいデータファイルが増えたときに `git add -A` で混入する余地があるためです。

**別の PC に引き継ぐ場合は、これらを手動でコピーしてください。**

---

### 便利な git コマンド

```bash
# 現在の状態を確認
git status

# 変更の差分を確認（コミット前に内容を確かめる）
git diff

# コミット履歴を確認
git log --oneline -10

# 特定のファイルの変更履歴を確認
git log --oneline -- core/evaluate.py

# 間違えたコミットを取り消す（まだプッシュしていない場合）
git reset --soft HEAD~1

# ブランチの一覧を確認
git branch -a
```

## 9. よくあるトラブルと対処法

### Julius が見つからない / アライメントが失敗する

```bash
# diagnose.py で Julius のパスを確認
python diagnose.py

# 環境変数で直接指定する場合
$env:JULIUS_BIN = "C:\path\to\julius.exe"   # Windows PowerShell
export JULIUS_BIN="/usr/local/bin/julius"    # Linux/Mac
```

---

### 単語登録で「発音が認識できませんでした」が出る

お手本録画からの Julius アライメントが失敗しています。単語は登録されず取り消されます。
サーバーのコンソールに `[register_word] アライメント失敗 ...` と `[診断情報]` が出るので、
まずそれを確認してください。切り分けは以下の順です。

| 診断情報の内容 | 原因と対処 |
|--------------|-----------|
| `perl stderr` に `'C:' は、内部コマンドまたは...` | Windows のネイティブ perl（Strawberry Perl 等）と msys perl でパス形式の要求が逆。最新版では自動判別するため、**`git pull` で最新化**すれば解消する |
| ログに `WARNING: input too short (0 samples)` | 録音が実質無音。マイクの接続・入力デバイスの選択・ミュート設定を確認する（録画画面の `MIC` バーが反応するか） |
| `Julius 実行ファイルが存在しません` | `engine/bin/julius-4.3.1.exe` がアンチウイルスに隔離・削除された可能性。`git checkout -- engine/bin/julius-4.3.1.exe` で復元する |
| `（ログが空＝julius が起動していない可能性）` | 上記いずれか。`perl実行パス` と `perl stdout/stderr` の行が手がかりになる |

一過性の失敗（アンチウイルスの一瞬のロック等）に備え、結果が空だった場合は
自動的に最大3回まで再試行します。3回とも失敗した場合のみエラーになります。

---

### 登録した単語を再生すると別の単語の音声が流れる

単語を全削除した後に登録し直すと、以前は ID が `word1` から再利用され、初期データセットの
`web/static/sample/word1.wav`（VOICEVOX 合成の「おんど」）と衝突していました。
**最新版で修正済み**です（過去に使われた ID を避けて採番し、実録音を優先配信）。
古いバージョンで作った単語が残っている場合は、その単語を削除して登録し直してください。

---

### MFCC を再生成したいとき

単語登録時に自動計算されますが、手動で一括再生成する場合は以下を実行します。

```bash
python scripts/regenerate_mfcc.py
```

---

### 特定の単語のアライメントが失敗する

```bash
# 1単語の修復
python scripts/repair_alignment.py word35

# 複数単語の修復
python scripts/repair_alignment.py word35 word36 word37
```

---

### モーラ別スコアが全部 0 になる

スコアには Julius のアライメント結果が必要です。以下を確認してください。

1. `python diagnose.py` でエラーが出ていないか確認
2. `data/raw_audio/wav/test.lab` が生成されているか確認
3. 録音が短すぎる・マイクが遠すぎると Julius スコアが低くなる

---

### 口形分析タブが表示されない

MediaPipe がインストールされていない可能性があります。

```bash
pip install mediapipe
```

インストール後にサーバーを再起動してください。

---

### ページが 500 エラーになる / グラフが表示されない

練習履歴や単語が空の状態で発生していた不具合は修正済みです（`git pull` で最新化してください）。
それでも発生する場合は、サーバーのコンソールに出る Python のトレースバックを確認してください。

## 10. 既知の限界と今後の課題

### 現在の限界

| 限界 | 詳細 | 将来の改善案 |
|------|------|------------|
| **参照音声が1本** | 単語ごとに登録された1本の録画が唯一の正解になる | 複数話者・複数テイクの平均化 |
| **パラメータが未検証** | 重み係数（0.40 / 0.35 等）を正解データで最適化できていない | 評価付き録音データ 20〜30 例収集でチューニング |
| **性別補正は集団平均** | 補正係数 0.85 は個人差を完全には吸収できない | 個人単位の話者正規化（VTLN）の実装 |
| **シングルユーザー設計** | `test.wav` が上書きされると以前の録音が消える | セッション ID でファイルを分けるマルチユーザー対応 |
| **クロスチェックが未反映** | 同期のズレを表示するだけで、スコアには反映していない | 実運用データで判定基準を検証してから採点へ統合 |
| **クロスチェックの中央値** | 録画開始タイミングの機材差を含むため単体では判断材料にならない | 音声・映像の開始時刻を厳密に揃える仕組みの検討 |
| **管理機能に認証なし** | 誰でも単語の追加・削除ができる | 公開運用する場合はパスワード保護等が必要 |

### 解決済みの限界

| 問題 | 対応内容 |
|------|---------|
| ~~話者性別補正なし~~ | ネイティブ・学習者両方の性別を自動判定し補正 |
| ~~DTW 距離が音声長に依存~~ | `(len(mfcc1) + len(mfcc2))` で正規化 |
| ~~モーラ別アクセントスコアが常に 0~~ | 生の半音値の代わりに 0-1 正規化後の値を使用 |
| ~~分析ページで Jinja2 クラッシュ~~ | Python 側で事前ソートして渡す方式に変更 |
| ~~単語がテキストだけで登録できてしまう~~ | テキストとお手本録画を1回のリクエストでまとめて登録する方式に変更 |
| ~~アライメント失敗時に空の .lab を持つ単語が残る~~ | 結果の中身を検証し、失敗した登録は自動で取り消す |
| ~~Julius がハングして解析が永久に詰まる~~ | 30秒タイムアウト + プロセスツリーの強制終了 |
| ~~perl の種類でアライメントが失敗する~~ | msys / ネイティブ Windows perl を自動判別してパス形式を切り替え |
| ~~削除した単語の ID が再利用され音声が混線~~ | 過去に使用した ID を避けて採番し、実録音を優先配信 |
| ~~声と口のタイミングのズレを検出できない~~ | 音映像クロスチェック（[§5.11](#511-音映像クロスチェック口と声の同期分析)）を実装 |
